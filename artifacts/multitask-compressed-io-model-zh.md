# 多任务 guest 的前端扩展与任务链模型

状态：本次研究的候选架构，尚未实现或端到端验收。本文按用户对任务链、NTCON 接管与生命周期的最新澄清，取代本文件此前以“最近多任务祖先 / 压缩 I/O 调度”为中心的表述。项目正式架构与当前实现仍以仓库权威文档和代码为准；本文不声称现有 NTSRV、NTVDM 或 NTVWM 已经支持这里的扩展。

本质上的改变是**扩展前端的定义，让多任务型载荷内部的每个 VDM（DOS VM）成为一个前端**。前端不是整个多任务载荷，也不是承载该载荷的 worker；一个载荷内有多个 VDM，就对应多个相互独立的内部前端。NTCON 实例仍是另一类前端。

**单任务或多任务描述载荷当前的运行阶段，不是 worker 的类型，也不是必须在整个 task 生命周期内固定的标签。** 同一个 DOS 载荷可能先处于普通 DOS 阶段，再进入 guest 多任务环境，退出该环境后继续运行 DOS；同一个 worker 也可按既有规则先后承载不同载荷。当载荷处于多任务阶段时，承载它的 worker 负责提供该阶段内各 VDM 的前端连接能力及 guest 适配。NTSRV 管理前端与任务链、worker 的关联、授权、交接与生命周期；worker 按 NTSRV 指令连接分配给自己的前端进行 I/O。内部 VDM 前端不产生新的宿主用户界面，也不取得 NTCON 的接管权。

## 前端、后端与所有权

| 概念 | 定义和职责 |
| --- | --- |
| NTCON 前端 | 一个 NTCON 实例对应一个外部前端；NTCON 是整个交互会话的用户界面。 |
| VDM 内部前端 | 多任务型载荷内的一个 VDM（DOS VM）是一个前端；承载该载荷的 worker 提供它的 I/O 端点。它连接该 VDM 的任务链，不直接接管 NTCON。同一载荷内不同 VDM 是不同前端。 |
| 后端 worker | NTVDM 或 NTVWM 按原有职责承载任务，在 NTSRV 的指令下连接自己被分配的前端；后端无需把上游视为 NTCON。是否能以现有 I/O 契约透明实现，须验证。 |
| NTSRV | 负责认证、准入、前端关联、任务链交接、生命周期与退出决策，连接和撤销由其协调；不转发输入、画面或 DOS 窗口文本。 |
| 承载多任务型载荷的 worker | 在上游作为后端，同时为载荷内多个 VDM 提供下游前端端点；负责 guest 侧 VDM 身份、窗口 I/O 适配，并向 NTSRV 报告 VDM 前端及载荷生命周期。worker 本身没有单任务或多任务之分。 |
| guest Windows | 继续管理自己的 DOS VM、窗口绘制、焦点和桌面；不能由 NTSRV 代替其窗口管理。 |

因此，VDM 是内部前端，worker 是承载它的载荷并提供前端连接能力的进程；载荷和 worker 都不是这些内部前端本身。这也不表示 NTSRV 转发 I/O。NTSRV 可以将所需端点能力交给后端，实际用户 I/O 直接在后端 worker 和分配给它的前端之间传递；具体连接方式和 Console 语义仍待设计与验证。

16 位文本程序仍需要 NTVDM worker 承载，且该 worker 所承载的载荷可能自己是多任务 task；32/64 位文本程序仍使用项目的 NTVWM 路径，必须保留其真实 Console 的输入、屏幕和生命周期语义，不能用普通字节管道假定等价。16 位窗口程序（NEW）与 32/64 位窗口程序按既有宿主窗口启动路径处理，启动后返回，不属于本文的持续文本 I/O 交接范围。重定向、GUI 分类与既有行为仍须保持原有语义。

## 任务链、分支与 NTCON

一条任务链的最内层 task 是该链的当前活动 task；链上等待子任务的其他父 task 的当前载荷处于单任务等待状态。task 的载荷处于 guest 多任务阶段时，该 task 继续作为其所在链的活动 task，不因其内部 DOS VM 启动任务而整体挂起；进入或退出该阶段不是另建 task 的必然条件。

多任务 task 的每个 DOS VM 是一条**独立子任务链的起点**。这些子链归属于相应内部前端，而不延长多任务 task 所在的上游任务链。一个 DOS VM 的链内仍按相同规则运行：单任务父级等待时交接到子级；若活动 task 的载荷是多任务型，其内部每个 VDM 又分别成为前端，并各自拥有下一级 VM 子链。多条链可以并发，但每条链各自只有一个活动端。

NTCON 在一个交互会话中只有一个接管者：没有多任务边界时，外层任务链的最内层活动 worker 按现有规则接管；遇到该链上最外层活动的多任务 task 后，由其 worker 持续接管 NTCON。其内部 VM 子链和承载更深层多任务载荷的 worker 不直接接管 NTCON；这些链在各自内部前端上独立交接。前端内的交接不改变真实父子任务关系，完成、退出码和等待结果仍交还真实调用者。

```text
NTCON 外部前端
  └─ 外层任务链：单任务父 task（等待）
       └─ NTVDM worker M（承载活动的多任务载荷，接管 NTCON）
            ├─ 内部前端 A / DOS VM A
            │    └─ 任务链 A：NTVWM → 32/64 位文本程序
            └─ 内部前端 B / DOS VM B
                 └─ 任务链 B：NTVDM worker N（承载活动的多任务载荷）
                      ├─ 内部前端 C / DOS VM C → 任务链 C → …
                      └─ 内部前端 D / DOS VM D → 任务链 D → …
```

图展示逻辑归属，不假定每个箭头都对应新的 OS 进程、线程或特定 pipe。M 与 N 分别解释和合成各自 guest 的输入、显示；子任务的内容不能绕过对应 guest 直接覆盖外层桌面。M 持续承载其上游 NTCON 交互，N 持续服务它所承载载荷内的 VDM 前端。

## COMMAND 宿主执行请求的共同判断与交接

不要求 run16 增加 multi-task 命令行 flag，也不要求给 worker 或 task 贴永久的单任务 / 多任务标签。package-owned COMMAND 发起宿主执行的已确认入口至少有两个：`54:08`（`SVC_CMDEXEC`，包括直接命令与 COMSPEC `/c` 分支）和 `54:0A`（`SVC_EXECCOMSPEC32`，启动交互式宿主 COMSPEC）。两者在现有源码中分别经 `cmdExec`、`cmdExecComspec32` 汇入 `cmdExec32`，再由 `cmdCreateProcess` 进入宿主启动路径。因此**多任务环境判断、VM 身份绑定、请求状态和前端 / 任务链选择必须是两者共用的一套逻辑**，不能只在 `54:08` 分支实现。它不是整个系统所有启动路径的完整清单；WOW 的进程创建等路径须另行审计。

设计上以两服务汇合的 `cmdExec32` / 宿主执行边界为共同接入候选，必须在阻塞、创建子进程或修改共享执行状态之前完成判断，并在进入任何会切换 guest 上下文的操作之前保留本次 BOP 的服务号及精确上下文。最终挂点须实证：若 `cmdExec32` 已经太晚，或无法让未返回的 `CmdDispatch` / `MS_bop_4` 栈脱离等待，就在更早的 BOP 分发边界捕获所需信息并调用同一判断组件，同时相应改变返回边界；不能因为函数汇合就断言只改 `cmdExec32` 足够。各入口仍保留各自命令、环境、标准句柄、COMSPEC 交互 / `/c`、进位标志、返回值和重入语义；服务号、请求 ID、原始现场及续体都须属于各自请求。

每次上述宿主执行请求到达共同判断路径时，NTVDM 根据当前 guest 环境的**已确认生命周期状态**检查 VxD callback 是否已注册且对当前 VMM 实例有效；如有效，在与该调用精确对应的 guest 上下文进入 callback，由 VMM 提供当前 VM handle。以 worker 实例、VMM 阶段、VM handle/generation 和 request ID 绑定本次调用；不能用 CR3、焦点、PID 或最近运行的 VM 猜测。

- **已可靠确认处于普通 DOS、无活动 guest VMM 环境**：新文本子任务归属当前前端的原任务链。NTSRV 按既有单任务规则安排交接，当前载荷等待子任务完成；子任务结束后恢复真实调用者。
- **有效 callback 确认当前是受支持的非系统 DOS VDM**：该 VDM 是内部前端，新文本子任务属于此 VDM 的任务链，由 NTSRV 准入并交接到该前端。承载 Windows 的载荷保持运行；VxD 可请求 VMM 挂起发起调用的 VM，但须检查返回值，完成时在合法上下文请求恢复并处理失败。其他 VDM 和上游前端不应被整个载荷的等待阻塞。
- **callback 确认当前是系统 VM**：系统 VM 不因为有 handle 就成为内部 VDM 前端。它的 `54:08` 或 `54:0A` 若实际出现，具体发起任务、既有前端、等待和交接语义都需单独查明；不能对系统 VM 套用非系统 VM 的 `Suspend_VM` 操作，也不能默认挂起整个载荷。VMM 的 `Suspend_VM` 对系统 VM 返回失败，对临界区等条件下的其他 VM 也可能失败。
- **未知、初始化 / 退出中、callback 失效、驱动缺失或身份无法证明**：不能因没有 callback 就推断为普通 DOS，更不能猜测某个内部 VDM；需要明确的转换期处理或可诊断失败。允许走普通单任务路径的判据、驱动加载失败和失去通知的恢复机制尚待研究。

VxD 加载和回调注册可为 guest VMM 存在提供证据，但不单独证明所有桥接准备就绪、两种服务调用都来自非系统 VM，或缺少回调必然意味着普通 DOS。进入、退出及再次进入多任务环境时，worker 与 NTSRV 必须协调 VDM 前端的创建与撤销、既有子链、在途完成和 generation；驱动正常退出、异常退出、VxD 动态卸载以及 worker 死亡需要分别验证。相同载荷回到普通 DOS 后，已确认内部前端按协议撤销，后续调用才可按其现有上游前端的普通任务链交接。

以上是候选决策模型，不是已实现的自动环境检测。此前隔离实验证明在指定 Win95 和 Win3.1 386 增强模式的非系统 DOS VDM 中可从真实调用进入 VxD callback 并取得身份；**尚未证明**普通 DOS 与驱动失败可可靠区分、`54:0A` 的同等运行时证据、系统 VM 中真实服务调用的来源及等待方式、全生命周期切换，或 NTSRV 已能连接和管理内部前端。

## 身份与请求

外部前端以经过认证的 NTCON 实例身份识别；PID 可以用于关联或核对，但必须处理 PID 复用，不能把裸 PID 当作永久身份或授权。

内部前端至少须能区分：**承载 worker 的实例、该 worker 当前多任务载荷实例、guest DOS VM handle/ID 与生命周期 generation**。VM handle 仅在相应 worker 的 guest 内有意义，可能复用；一个 worker 进程也可先后承载多个载荷。前端 ID、能力和代次的具体编码仍待设计，不能以可伪造的公开 ID 或参数代替认证。

对于已确认属于非系统 DOS VDM 的真实 `54:08` 或 `54:0A`，必须在该调用的正确 VM 上下文取得身份，并以 request ID 与内部前端及本次调用绑定；普通 DOS 和系统 VM 的判断与处理遵循前节，不要求为系统 VM 创建内部前端。NTSRV 根据受认证的前端和任务关系分配、交接 worker；不能把内部 VM 归属通过全局“当前前端”推断。迟到的输入、输出、完成、定时器和重复通知必须经过代次与所有权验证，不能送入复用后的端点。

## 生命周期与交接

NTSRV 是关联、handoff 和生命周期决策的权威。启动同一前端任务链上的子 worker 时，仍由 NTSRV 按该链的规则交接：等待中的单任务父级让出该前端，子级完成后按规定返回父级；其他前端不受影响。多任务边界的子链使用其内部前端，不触发上游 NTCON 的重新接管。

需要分别定义并验证以下情形，不能一律等同于杀掉进程：

1. **单个 DOS VM 关闭**：宿主 worker 向 NTSRV 报告该 VM / 前端的失效；NTSRV 停止该端点的新关联，并协调其子链及更深层后代按适用语义结束、取消或清理。其他 VM 的端点与任务链继续工作。
2. **多任务载荷结束，worker 进程仍存活**：worker 通知 NTSRV 自己失去该载荷的前端宿主职能；NTSRV 撤销该载荷拥有的全部内部前端，协调其子链和后代完成必要清理。worker 后续可以按现有任务规则继续承载单任务或另一个多任务载荷；新载荷必须有新实例与新前端身份。后续可用时点、未决完成和资源释放的精确顺序须由协议确定。
3. **承载 VDM 前端的 worker 死亡**：NTSRV 使用进程观察等权威事实处理该 worker 托管的所有内部端点及后代任务链，不能依赖已死亡 worker 发送通知；对仍在等待的调用和子 worker 给出规定的故障或取消语义。
4. **子 worker 完成、异常或创建中取消**：NTSRV 将结果关联到正确前端和真实调用链，协调最终输出、未消费输入、断连和资源释放；guest 恢复、返回值和显示访问只能在正确 VM 上下文进行。完成、关闭、断线和迟到通知可能竞速，必须可重复处理且不会复活已撤销端点。

关联建立、端点准备、连接授权、交接确认、关闭和失败恢复的具体状态机，以及后代何时正常结束、取消或释放，均未确定；不能仅凭本文推断现有协议已经具备这些保证。NTSRV 不负责模拟 Windows 焦点，也不把键盘记录和画面作为 RPC 中转。

## 实现边界与未决问题

这项扩展必须先核对现有 NTSRV frontend 身份和 capability 是否硬编码 NTCON PID / 唯一根，现有 task / worker 与 Console 的关联是否只支持单链、单活动连接，以及 NTVDM、NTVWM 的连接、交接和 Console I/O 契约能否接受内部前端。不能仅增加管道、线程或标识字段，就声称现有 handoff 和生命周期已支持并发分支。NTSRV 管理的是认证后的前端与任务链，不是 guest Windows 内部的绘制和焦点调度器。

`54:08` 与 `54:0A` 的等待状态都必须能够脱离未返回的 `host_simulate()` 调用栈，保存为每请求状态，并在正确 VM 上下文恢复；若现有调用边界不允许，须改变该边界。后台 I/O 不得直接访问不属于当前上下文的 guest 内存、CPU 或显示。宿主 NTVWM 的 Console 记录、屏幕、光标、控制事件、编码、窗口及重定向语义是否能通过内部前端等价表达，尚未证明。焦点输入、重复按键、背压、定时器撤销、VM 销毁、worker 复用和嵌套关闭也都须单独验证。

Win3.1 只研究 386 增强模式；标准模式不在本任务范围。Win95 与 Win3.1 的驱动装载和兼容性须分别验证，不能假设同一 VxD 二进制直接通用。不得修改 guest Windows 或加入常驻 DOS 代理。

## 验证要求和证据状态

候选验收应覆盖：普通 DOS → guest VMM 就绪 → 退出回 DOS → 再次进入的可靠状态判断，以及驱动缺失、系统 VM、切换期和挂起 / 恢复失败；`54:08` 和 `54:0A` 分别在真实 DOS VM 中的精确请求身份、原有 COMSPEC / 返回及重入语义；两个 VM 对不同 NTVDM / NTVWM 子链的输入、输出、真实 DOS 调用者恢复和退出码；两种完成顺序；错误和失效身份；各前端独立交接；VM 关闭、载荷结束但 worker 复用、worker 死亡与后代清理；两个以上层级的多任务嵌套；现有单任务、GUI 和重定向回归。每项要区分子进程退出和 guest 调用者确实恢复，不能仅凭内部退出码、BIOS 读回或截图宣称全链路通过。

已有 `54:08` 隔离实验证明了一些受限条件下的 VM 身份关联、独立续体、固定合成测试键和错误身份拒绝；不得将其外推为 `54:0A` 已通过相同验证；也发现 VKD 路径可能重复投递，且受限消费实验不证明符合 VKD API 契约。这些结果详见 [桥接实施设计与验证记录](win31-win95-vxd-bridge-design-zh.md)。它们使用实验子程序和有限通道，**尚未证明真实子 NTVDM / NTVWM 对内部前端的连接、NTSRV 生命周期协调、完整交互或所需嵌套**。本文架构是设计方向，不是已交付能力。
