# M0 T310 S8 P2 — original VGLOB provider selection

## Question

Can the large unresolved video-accessor cluster be removed by selecting its
existing original SoftPC owner rather than by adding fixture-local stubs or a
new adapter implementation?

## Inputs

- `mvdm-host/softpc.new/base/ccpu386/vglob.c` — the original CCPU-root VGLOB
  accessor carrier.
- `mvdm-host/softpc.new/base/cpu/src/evid/vglob.c` — byte-identical historical
  duplicate; it is not selected, so the formal archive has one owner.
- Original video callers selected by the existing video manifest.
- Formal x86/x64 source graphs generated by
  `tools/build/New-T310OriginalSoftpcNinja.ps1`.

## Procedure

The CCPU archive selection adds only the original `ccpu386/vglob.c` carrier.
No source body, function signature, call site, adapter, or fixture is added.
The formal whole-archive forced-link graph is then regenerated and linked for
both supported host architectures. `Export-T310ForcedLinkLedger.mjs` reads
the fresh linker log and writes the architecture-specific physical-form
ledgers.

## Observations

- x86 formal forced-link unresolved forms fell from 262 to 187: 75 physical
  video-accessor forms are now supplied by the selected original owner.
- x64 formal forced-link unresolved forms fell from 263 to 188 after a fresh
  serial rebuild. The initial unchanged result was a stale generated-graph
  observation, not an ABI conclusion.
- The x64 compiler reports original `vglob.c` native-pointer truncation
  warnings around `IUH`/`IHP` casts. The source selection is therefore a
  source/link-closure result, not evidence that the old 32-bit VGLOB backing
  representation is safe to execute on x64.

## Interpretation

This is the intended package-first recovery pattern: select the original
carrier which owns a coherent cluster before considering any replacement.
It removes a large class of artificial missing interfaces without expanding a
fixture or introducing a second video implementation.

The remaining x64 width issue belongs to the original video-state/physical
backing composition audit. It must preserve the original VGLOB interface and
use the admitted fixed-width/mapping boundary only where an identity crosses
that boundary; it must not be hidden by a fixture stub or treated as a reason
to reintroduce Bochs.

## Follow-up

Continue with owner-package selection from the reduced ledger. The next
candidate is the original video/graphics composition group; EMS/EMM source
selection remains separately admitted because its original `LIM` conditional
profile must not be enabled merely to reduce unresolved-symbol counts.
