# M0 T318 S2 P17 — Incremental GDP generator timestamp closure

## Question

Can a formal-graph configure preserve Ninja's ordinary incremental behavior
when the generated GDP-carrier header has not changed?

## Inputs

- `tools/build/Generate-T310GdpSlots.mjs`;
- the selected x86 CPU40 graph at
  `build/M0-T318/S2/cpu40-v7vga-r4`; and
- its generated `mvdm_gdp_slots.h` carrier.

## Change

The generator now compares the complete generated byte text with the existing
header before writing. It reports whether the output changed, and writes only
when it did. The generated contents, source input, compiler flags, selected
CPU40 source set and link graph are unchanged.

## Procedure and observations

1. Regenerated the formal x86 graph and ran its external `run-ninja-parallel`
   runner for `original-softpc-process.exe`.
2. The required cold/invalidated product rebuild completed 215 Ninja actions
   under the runner's bounded parallel scheduler.
3. Regenerated the same graph a second time without changing any input.
4. A Ninja dry run then returned `ninja: no work to do`.

The earlier full invalidation was caused by the generator rewriting an
otherwise identical header, making its modification time newer than all
dependent objects. The new content-preserving write removes that false input
change while leaving real source/header dependency changes visible through
MSVC `/showIncludes` and Ninja `deps = msvc`.

## Boundary

This is build-graph hygiene only. It does not suppress a diagnostic, change an
OpenNT/SoftPC mirror, alter GDP semantics, or establish guest runtime
continuity. Package-only targets remain the normal development path; full
product rebuilds remain integration evidence.
