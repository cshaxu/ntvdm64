# T209 S1 — boot-namespace/startup-configuration construction map

## Question

How can a declared but not-yet-bound CONFIG/AUTOEXEC pair be a valid
boot-namespace provider state without restoring synthetic bytes or changing
BOP semantics?

T204's retained source and test evidence establishes the governing
intent: before binding, CONFIG/AUTOEXEC have declared path and metadata but
zero content; after binding, the startup-configuration provider is the sole
byte owner.  No historical OpenNT or external host API is required to reach
this conclusion.

## Required state transitions

| State | Namespace entries | Search snapshot | Command boot input | Provider validity | Owner |
| --- | --- | --- | --- | --- | --- |
| `declared-unbound` | COMMAND and target have payload; CONFIG/AUTOEXEC have canonical paths, metadata, `bytes == NULL`, `byte_count == 0` | Four/five metadata entries, with CONFIG/AUTOEXEC length zero | Canonical CONFIG/AUTOEXEC paths only | valid with `has_startup_configuration == 0` | readonly namespace owns declarations; startup provider owns no bytes yet |
| `bound-ready` | CONFIG/AUTOEXEC point to bounded startup-provider images | Same entries with generated byte counts | Same canonical paths, copied into the provider's input record | valid with `has_startup_configuration == 1` and image-pointer identity checks | startup-configuration provider owns bytes |
| `teardown` | Provider/session releases owned startup images and overlay/session state together | no externally retained host pointer or raw handle | no guest-visible backing pointer | invalid/zeroed object after owner teardown | session lifecycle |

The provider currently attempts this sequence:

```text
readonly namespace (correctly creates declared zero-byte CONFIG/AUTOEXEC)
  -> command boot input (path-only; valid)
  -> profile search snapshot (rejects zero bytes)     <-- contradiction
  -> provider becomes valid
  -> later bind_startup_configuration (currently unreachable)
```

`bx_ntvdm_profile_search_snapshot_v1_set` rejects `file->bytes == 0` for
every entry.  That rule is sound for the COMMAND/target payload entries but
incorrect for the two explicitly declaration-only startup files.  As a
result, `boot_namespace_provider_initialize` returns failure and
`bind_startup_configuration` cannot satisfy its own `provider_valid`
precondition.

## Owner-preserving repair design

S2 will make the snapshot builder distinguish **payload-required** entries
(COMMAND, target and optional QUIT) from **declared startup entries**
(CONFIG/AUTOEXEC):

1. The shared metadata helper accepts a consistent empty file only when
   `bytes == NULL && byte_count == 0`; mismatched pointer/count remains
   rejected.
2. Snapshot construction requires payload for COMMAND/target/QUIT, but permits
   empty CONFIG/AUTOEXEC declarations.  Their metadata and canonical DOS name
   remain present with size zero.
3. `bind_startup_configuration` rebuilds the snapshot after it installs the
   provider-owned generated images, so bound lengths replace zero lengths
   atomically with existing object ownership.
4. Tests cover unbound construction, bound re-projection, pointer/count
   mismatch rejection, and the dependent DEM PDB lifecycle fixture.

This design changes no external fixed-width ABI, no BOP dispatch or service
result, no host policy, no Bochs code and no startup-byte materialization.
It does not make an unbound configuration readable: a zero-length declared
entry remains distinct from a ready provider-owned image.

## Rejected alternatives

- Restore synthetic CONFIG/AUTOEXEC bytes: contradicts T204's sole-byte-owner
  decision and hides source provenance.
- Defer all search snapshot creation until bind: makes unbound provider state
  invalid and shifts a configuration lifecycle problem into unrelated
  callers.
- Ignore startup files in the unbound snapshot: changes the declared DOS
  namespace and makes FCB/search results depend on initialization timing.
- Solve it through a DEM/COMMAND BOP special case: violates owner boundaries
  and recreates the trace-led endpoint pattern.

S1 therefore admits S2 as one bounded `src/bx-vdm` construction repair plus
cross-package regression; it does not admit any BOP implementation.
