# S10 WOW16 original recipe and host/guest boundary follow-up

The machine-readable [per-file observations](s10-followup-wow16-recipe-roles.csv) cover all 240 C/H rows in the earlier [ownership follow-up](s10-followup-wow16-ownership.md), with current file SHA-256, exact original recipe path/line and recipe hash where a matching source/object token exists, earlier guest witness, and known host same-basename collisions. These are historical source roles, not claims of current product inclusion or behavior. Nothing in this follow-up modifies or builds guest binaries or changes the shared audit inventory.

* **19 DDEML test C files have both Win16 and Win32 recipes.** `wow16/ddeml/tests/{ddestrs,src/client,src/server,src/ddemo}/sources` defines `WIN32` and names the Windows test programs; the corresponding `makefile.dos` compiles Win16. For `ddestrs`, the latter uses source-name variables, explicitly resolved in the report. Therefore a WOW16 directory alone cannot establish guest-only ownership. These are historical test tools, not proof a test ran or that the tested DDEML host/guest behavior is restored; S14 retains DDEML lifecycle, identity and behavior.
* **11 local DDEML test headers** have quoted local includes from those dual-target C files or their headers; activation by preprocessor and actual current consumers are not proven.
* **25 C files have references in recipes identifying a 16-bit toolchain.** The CSV supplies the exact reference; a reference to an `.obj` alone does not prove that a particular `.c` wins over assembler or another source in every conditional configuration. These are bounded candidate roles, not final exclusion of host use or assertions about the installed guest.
* **66 headers retain the prior direct guest-build candidates** including cited guest C witness, while exact conditional preprocessing and all host/alternate configurations remain unverified.
* **119 rows have no additional sufficient recipe evidence**, including both C and headers. Keep pending. Same-basename host includes are not proof of including the particular WOW16 header; the seven collisions listed by the earlier follow-up need actual include-path resolution. Conversely absence of a direct recipe token is not proof the source is unused; indirect rules and variables occur in these makefiles.

The earlier evidence records four graph/dependency snapshots. It does not prove other target graphs or configuration resolution. Historical source availability and code hash matching are not runtime coverage. No shared file classification is changed on this evidence alone; do not discard or rewrite guest code. Original guest behavior remains within its owning functional stages.
