# CPU40 CCPU host access-vector investigation

Read-only inspection against current source and cached x86 NTVDM. No runtime or guest change is made and no direct-call replacement was built or tested.

## Original and current ownership

Original OpenNT `base/support/main.c` calls `cpu_init()`. CPU40's `base/inc/cpu4.h` includes generated `base/ccpu386/cpu4gen.h`, whose selected CCPU macros map `cpu_init` and register access to `c_cpu_init` and `c_get*`/`c_set*`. Original `host/inc/host_cpu.h` wraps its CPU30 register-vector macros in `#ifdef CPU_30_STYLE`, and original `host/src/nt_cpu.c` defines `host_simulate()` calling `cpu_simulate()` directly. Therefore original CPU40 initialization is present, and that source evidence does not establish a CPU40 requirement for the CPU30 vector table.

The current `host_cpu.h` lacks the original outer CPU30 guard. Its `get*`/`set*` and `host_simulate()` macros consequently expose pointer indirection to CPU40 sources. T318 commit `7c8928d92` selected the CPU30-gated CCPU vector initializer for CPU40 (DIV-151); T336 commit `be06ac898` added its call immediately after `cpu_init` (DIV-182). Current `nt_cpu.c` locally undefines the macro when defining the direct external `host_simulate` wrapper (DIV-150). Together these form a plausible self-induced compatibility dependency; this is a design finding, not proof that all original profile logic can simply be deleted.

## Actual current object references

Parsed the COFF undefined external-symbol tables in the cached x86 worker build, excluding generic unrelated `_func` names. `obj/keymouse/keybd_io.obj` references 17 register get/set vector slots and `_host_simulate_func`; `obj/video/video.obj` references 28 register get/set vector slots and `_host_simulate_func`. `obj/bios/rtc_bios.obj`, `obj/ccpu/ccpusas4.obj`, `obj/disks/floppy.obj`, `obj/disks/floppy_i.obj`, `obj/keymouse/mouse_io.obj` and `obj/system/rom.obj` each reference `_host_simulate_func`. `obj/support/main.obj` references `_load_sw_cpu_access_functions`. The NTVDM link map contains representative linked symbols for these object families and the initializer; undefined object symbols show a static link dependency, not proof every reference executes at runtime. Fixture objects also explicitly reference the table and initializer and must be migrated if the contract changes.

Key evidence identities (SHA-256): `host_cpu.h` BC4882CF190665B3E964E105995DED7FA0322C275B19A2560EB73759C990EB02; `nt_cprgs.c` 0ECFF32268A9856ECF03B40B30B6B950BF0C3384AAF5B6F029961D11A2903C54; `base/support/main.c` B23B3B8384885D92589F1A64A5B30185FCBEF30B1C1631E02E4394F7B1774E9E; `keybd_io.obj` D8A28279E47538FCA54FA3F7F850B0B2BD254AE4F70AFC738DB754683F50B5CE; `video.obj` D6B7700592EF979E901541324CC364BD2669F0048D2DBECC348F20F6C8CB9DA7; linked `ntvdm.exe` 8B49213483F4F92EB9A8C3A5740C88DEDF56AA0C6E924341BF09EE8DE68D0AE6. The latter is the local linked image, not asserted to be byte-identical to the stamped release.

## Candidate and unresolved proof

A finite cleanup candidate is to restore the original CPU30 guard on `host_cpu.h`, use the original CPU40 generated direct register interface for actual CPU40 consumers, keep the original direct `host_simulate` wrapper and original `cpu_init`, and remove the now-unneeded table installation and CPU40 initializer selection only after every compiled caller and dependent fixture migrates. Sources built with `MONITOR` must be audited separately: `cpu.h` selects a different declaration/profile branch there, and restoring the guard without providing the correct original CPU40 interface can produce missing declarations or expose old register globals. The existing `MONITOR` selection for other features is not permission to introduce the retired hardware V86 monitor.

This is a source-supported design possibility, not a verified drop-in equivalence. It must prove getter/setter widths, segment-load fault behavior, callback and recursive execution ordering, hardware interrupt/ICA locking, both machine widths and fixture contracts. Compile-only success is insufficient; compare actual object references, map/link, CCPU exception and recursive BIOS probes, DOS/WOW and Win3.1 lifecycle, including input and display. Only then measure final mirror diff and net code. If an existing consumer cannot use the direct original interface without a new adaptation, account for that dependency before deciding whether the overall change is actually simpler.

## Isolated direct-interface compile experiment

In an uninstalled test-owned source copy, restored a CPU30 guard around the existing `host_cpu.h` body and selected the original `cpu4.h` interface in place of `CpuH`'s current MONITOR-dependent selection, without changing the MONITOR flags themselves. Replayed the real x86 worker compiler commands for nine key production sources (the eight vector consumers above plus `nt_cpu.c`): eight of nine compiled initially. Their COFF undefined-symbol tables no longer reference the CPU register-vector slots or `_host_simulate_func`; their generated register calls use `c_get*`/`c_set*` and recursive calls use `_host_simulate`. This is object-level compile/reference evidence, not link or runtime equivalence.

The remaining `floppy.c` failed because two local `reg byte_count` variables relied on the now-hidden CPU30 `reg` union. In the disposable copy only, using an `IU16` count and explicit low/high byte extraction allowed the same real compiler command to succeed. Original selected NT host defines `LITTLEND`, and `IU16` is an unsigned 16-bit type; the proposed arithmetic still needs behavioral and all-profile verification. The temporary experiment did not alter production source, fixtures, guest, installed files, or the published package. Results and compiler logs were produced under `build/t473-s13/cpu40-vector-probe/`.

The experiment covers only nine hand-picked x86 sources, not every build command or x64 path. Replacing MONITOR-dependent `CpuH` selection can change declarations and selected behavior beyond register access, and the softpc floppy byte-count change itself is a mirror diff. A complete comparison must include all actual consumers, direct-vs-vector ABI, ISA behavior, exception delivery, and lifecycle before treating this as a clean replacement or measuring net diff. No production change is proposed as proven solely by these compiles.
