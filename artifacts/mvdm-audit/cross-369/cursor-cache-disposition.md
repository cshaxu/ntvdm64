# S10 part 9: cursor/icon cache owner and disposition

This review is restricted to the two owned pending files `wow32/wcurcash.c` and `wow32/wcurcash.h`; other paths are read as dependencies and do not receive ledger changes. `cursor-cache-observer.py` records source hashes, exact static references and the current cached WOW32 graph edges in `cursor-cache-observations.json`. Reproduce from repository root with `PYTHONDONTWRITEBYTECODE=1 python -B artifacts/mvdm-audit/cross-369/cursor-cache-observer.py`. No guest, product, build graph or shared ledger was changed or executed.

## Original and current call chain

Both owned cache files are byte-identical in the current tree and both comparison editions. `wcurcash.c` maintains its own `pCurIconFirst` list, keyed by resource type, instance and string/integer name; it associates returned Win16 resource/icon handles with a task thread and supplies resource and task removal. Its `wcurcash.h` describes that list and five functions. The current original `wow32/sources` does **not** list `wcurcash.c`; the observed formal WOW32 graph likewise contains no `wcurcash` source edge. The bounded search of `src/mvdm` and `src/wow32-dll` finds legacy function names only in `wcurcash.c` and `wcurcash.h`; this is a source-reference observation, not proof about external binaries or generated/unsearched consumers.

The selected current original path is separate: `wutbl2.h` routes Win16 LoadIcon/LoadCursor to `WU32LoadCursor` in `wucursor.c`. That function maps the guest name/resource, calls `pfnOut.pfnServerLoadCreateCursorIcon`, and calls `SetupResCursorIconAlias` on success. `wcuricon.c` owns `lpCIAlias`, looks up existing resource handles in `SetupResCursorIconAlias`, creates Win16 aliases when absent, and `wuser.c` calls `FreeCursorIconAlias` for task/module retirement. These three C bodies have independent selected x86 graph edges. Historical `wcurcash.c:46` calls `SetupResCursorIconAlias` with four arguments whereas the current selected `wcuricon.c:552` definition has five, including resource name; blindly adding the old list would neither be a drop-in link nor a demonstrated recovery.

## Concrete unresolved failure/lifecycle boundaries

In the **selected** source, `AllocCursorIconAlias` can return NULL after allocation failure, whereas `SetupCursorIconAlias` immediately dereferences its result; this is a source-level counterexample conditional on that allocation failure, not a reproduced crash. `SetupCursorIconAlias` also marks the alias in use before `RealLockResource16` and returns zero if locking fails; determine the exact reusable-slot/resource ownership outcome and whether callers release the already-created native/guest resources. The original historical list has distinct failure behavior, including name allocation before list-node allocation; it is not evidence that the selected provider handles such failures. The `CIALIAS_TASKISGONE` branch explicitly avoids guest callbacks and comments on possible leaked guest-side memory; distinguish legitimate already-dead-guest cleanup from live-task leaks.

The same NULL dereference occurs independently at `GetCursorIconAlias32` (`wcuricon.c:210`): it first obtains a guest resource lock and mapped pointer, then dereferences `AllocCursorIconAlias` without checking. The preceding invalid-stride early return also occurs after that lock and mapping and before the normal `GlobalUnlock16`/`FREEVDMPTR`; establish the actual lock/mapping semantics before calling it a measured leak. If `W32CreateCursorIcon32` fails after `pbDataOld` allocation, the path marks the alias unused, while the later allocation routine initializes a reused slot's `pbDataOld` to NULL; audit whether any other owner releases that buffer. These are distinct static failure-path risks, not reproduced defects. A repair must account for both caller paths and each acquired guest lock/mapping, alias slot, native cursor/icon and backup allocation without destroying borrowed handles.

Required S14/S15 evidence: actual Win16 LoadIcon/LoadCursor with integer and string names, shared vs private resources and repeated-load stable guest-handle identity; module/task-specific normal close, task loss and handle reuse; caller-owned host/guest icon destruction; controlled allocation and resource-lock failure with rollback; nested callbacks/reentry and no double-free. Use selected-source focused fault fixtures plus an unmodified guest behavior test, binding tested DLL and guest image identities. No such fixture was run in this review, and no defect is asserted for unobserved user workloads.
