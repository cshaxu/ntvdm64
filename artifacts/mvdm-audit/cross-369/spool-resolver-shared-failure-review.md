# Shared spool resolver: failure and ownership audit

This extends `shard-3/wow-print-setup-failure-review.md` and `cross-369/spool-header-disposition.md`; it is a source review, not a reproduced incident. The original `wgprnset.c:24` owns one `spoolerapis` table. `LoadLibraryAndGetProcAddresses` at 525-541 loads `WINSPOOL.DRV`, writes each resolved entry in sequence, and returns TRUE even when an individual `GetProcAddress` returned NULL. The native provider owns printer handles and jobs; original WOW paths own conversion buffers and host-to-16-bit handle aliases.

| Consumer | Entry check and subsequent dependency | Failure/lifetime boundary to verify |
| --- | --- | --- |
| `wgprnset.c:89-96,174-186,305-331` | Individual setup API checked before loading, then called through table | Module failure skips `malloc_w` copies' cleanup as already described in the linked report; individual missing export can produce a NULL call. |
| `wspool.c:75-94` `WG32OpenJob` | Checks `OpenPrinterA`, then also calls `StartDocPrinterA`; `GetDefaultDevMode32` separately checks `EXTDEVICEMODE` | A successful module load does not establish both exports. An opened printer followed by failed StartDoc reaches error without an apparent `ClosePrinter` in this function. Verify provider-handle and alias counts; do not claim product failure without the injected route. |
| `wspool.c:127-216` | Page/end/write/delete entries are used through the shared table following an existing job | They rely on the earlier setup rather than revalidating their own exports; test missing individual exports and success/failure retirement separately. |
| `wgdi.c:2363-2375` | Checks `EXTDEVICEMODE` after copying a guest string into `psz1` | Module-load failure returns immediately before normal cleanup. Verify the specific successful-copy condition and allocated-buffer count, not merely API return. |
| `wow32fax.c:899-957` | Checks `GetPrinterDriverDirectory`, then also calls `AddPrinterDriver`, `AddPortEx`, and `AddPrinter` | Missing later exports and partial native install require explicit bounded tests; no rollback or installation behavior is established by ordinary print witnesses. |

Publishing a partially initialized shared table may be significant under reentry/concurrency, but the actual WOW execution/locking contract has not been established here. Do not assert a race from source shape alone. A finite test matrix should use a controlled provider/resolver boundary: module-load failure; each relevant missing export; OpenPrinter success followed by StartDoc failure; setup/fax conversion allocation failures; and nested or concurrent entry only where lifecycle rules permit. Check guest return/error, native handle counts, WOW aliases, copied buffers and module reference lifetime after each case. Preserve original WOW conversions and callbacks; native Windows remains the provider authority. Any original-source changes require registered exceptions. Existing T468 PDF evidence and raw-spool negative tests do not cover this matrix. No product, guest, shared ledger or test state was changed.
