## Original entry and ownership

`wkman.c::WK32RegisterShellWindowHandle` handles the original WOWEXEC shell registration and calls `WOW32FaxHandler(WM_DDRV_SUBCLASS, HWND32(hwndFax))`. The handler installs `WowFaxWndProc` only for non-null `hwndFax`, then calls `GetSupportedFaxDrivers` **even for a null fax window**. The support list is read from the WOW fax registry value, while mapped fax-driver messages are transformed and dispatched to the guest procedure. Its printer-installation path uses the shared `spoolerapis`/`WINSPOOL.DRV` resolver also used by `wgprnset.c`. The modern registry, native window and provider own their real system resources; the original WOW code owns conversion, mapped-view bookkeeping and the callback boundary. `m0-t468-s1-printing-spool-owner-matrix.md` explicitly distinguishes fax installation from ordinary raw/HDC printing, whose witnesses do not prove fax behavior.

## Per-file recommendation and bounded evidence

`wow32/wow32fax.c`: **partial / selected original functionality**. Keep it as the original fax and shell-registration call owner until the real feature and failure paths are verified; do not classify it as an unused stub or infer fax success from normal print-to-PDF. Existing source, graph and map establish selection and an entry path; they do not independently prove a particular WOWEXEC guest image executed that handler or complete fax operations. No new runtime or fault test was performed.

`GetSupportedFaxDrivers` has several source-established failure concerns worth testing as one ownership transaction. Its local `alpSupFaxDrvList` is not initialized before registry-open/query error, zero-list or allocation failure exits, yet is returned and assigned to the global; `uNumSupFaxDrv` is initialized to zero, and the inspected name-check loop is count-bounded, so the mere invalid returned pointer is **not** evidence that ordinary startup crashes. If the pointer-array allocation returns NULL with nonzero count, `RtlZeroMemory` is called before the NULL test. After the string buffer allocation, a failed second registry query exits without an apparent free; successful list pointers reference that buffer, so its retained lifetime and repeated-init/worker-exit cleanup must be traced before calling it a leak. `BuildStrList` scans for a double NUL without receiving `cbBufSize`; verify actual registry result type/termination and value-change cases with bounded test data before judging reachability. The original `WM_DDRV_PRINTPAGE` retains a global pointer into a mapped view with a comment relying on no nested printpage; check reentry and post-unmap lifetime, but no race is claimed here.

S16/S17 regression obligations: shell registration with absent/empty/valid/malformed registry value, explicit allocation and second-query failures and repeated cleanup; no accidental fax installation on ordinary startup; real provider/guest message conversion with successful and failing view/callback/driver operations; nested printpage and task exit; and resource ownership after each branch. Use controlled host doubles for faults plus a separately identified unmodified guest/provider where available. Preserve the already approved registry authority, original guest and public spooler boundaries, and register any actual mirror correction. This review adds no new provider and does not claim reproduced customer failure.
