# CCPU CMPXCHG / XADD: selected source, inactive bodies in captured release

Scope: `softpc.new/base/ccpu386/cmpxchg.c` and `xadd.c`, shard 2 pending when inspected. The companion observer reproduces exact hashes, Ninja edges, COFF section inspection, map ownership and relocation-masked published-image binding. Run from repository root with `PYTHONDONTWRITEBYTECODE=1 python artifacts/mvdm-audit/shard-2/ccpu-486-instructions-observer.py` and compare with the observations JSON.

Both current files match both OpenNT and OpenNT 4.5 originals by SHA-256. They implement respectively CMPXCHG for 8/16/32 bit (comparison and flags, conditional destination or accumulator update) and XADD (save destination, add with flags, exchange source), with each entire implementation guarded by `SPC486`. Captured x86 release Ninja compiles each and archives both in original-ccpu386.lib. Each actual obj contains only .drectve, .debug$S and .chks64: no code section; map has no owner for either object. Thus selected source is **not** evidence that either instruction implementation is present in that CCPU build.

In `c_main.c` cases 0F B0/B1 and 0F C0/C1 are conditional: SPC486 invokes these functions, whereas the alternative calls Int6. This establishes a concrete source-level CCPU configuration boundary and should be preserved as such in the ledger, not characterized as unused CPU functionality or removed on the strength of release-only evidence. The 386 interpreter entry `_c_cpu_simulate` in c_main.obj is bound to the released ntvdm.exe by 200 object bytes after masking 14 relocation words. This binds only the entry function, not the actual opcode switch or execution of Int6. Executable sections of cached and released images match, though full-file SHA-256 differs; no claim about the cause of this difference.

No runtime instruction probes or guest code were executed. Whether other active CPU backends implement these opcodes, the current runtime chooses this interpreter for a particular guest, the Int6 behavior end-to-end, and the behavior of SPC486-enabled builds remain unverified. No product, guest, build tree, or shared ledger was modified.
