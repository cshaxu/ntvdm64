# CCPU STD opcode: finite contract and witness

Shard-2 `softpc.new/base/ccpu386/std.c` is identical to OpenNT/OpenNT45, SHA-256 0FC14A782E8ECD49BCAFB0B8C546AE036ED2FC22BFA58D9D557B42B5C1441D5A, frozen ledger F73FFD45DFF44FCA4ECEFC49EF769BEAB5C085542CD04FFE4D6A7B5F942E3196. Original `sources:161` names it, selected Ninja emits `obj/ccpu/std.obj`, and the selected worker map records `_STD` from original-ccpu386:std.obj at 00427270. The map is link evidence, not execution.

`c_main.c:4295-4297` selects opcode `0xfd`, calls original `STD()` and continues normal decode. The complete function body is `SET_DF(1)`; `c_reg.h:374,406` maps GET_DF/SET_DF to `CCPU_FLAGS[10]`. `c_bsic.c` packs the direction flag into bit 10 of flags, while original `c_oprnd.h` string-operation macros consult DF. STD does not itself modify arithmetic flags, registers or memory, and a second STD remains set. Contract refers to this source-defined unprefixed instruction; decoder prefix handling, interrupts and general string operation correctness remain separately owned. In particular `c_main.c` marks its LOCK-prefix handling as incorrect; no attempt to classify that independent decoder boundary here.

No exact per-STD runtime receipt was found in current tests by source search. Existing CLD/REP MOVS probes alone cannot establish setting DF. A finite independent DOS guest witness on a hash-identified current worker should clear DF, establish and capture known controllable arithmetic flags, run STD and capture flags with PUSHF/POP, check bit 10 set and those other flags unchanged, run STD again and recheck, then copy known bytes using backward REP MOVSB and verify destination and decremented source/destination indices. Clear DF before DOS I/O/exit. Guest result and worker/package identities must be retained; optional protected-mode/prefix cases are not implied by a real-mode pass. This is sufficient targeted evidence to assess the source file's simple unprefixed semantic contract, not blanket proof of the CCPU decoder or every string operation. No guest or product code changed and no runtime test was executed in this shard.
