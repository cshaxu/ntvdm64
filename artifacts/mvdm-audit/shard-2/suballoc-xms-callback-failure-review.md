## Actual selected route

`xms.486/xms.c::XMSInit` selects the non-`i386` path of the CPU40 build: `VdmAllocateVirtualMemory(..., FALSE)` reserves XMS and, on success with expected address, `SAInitialize` registers `VdmCommitVirtualMemory` and `VdmDeCommitVirtualMemory` from `softpc.new/host/src/nt_mem.c`. The actual worker graph selects `xms.obj` and `xmsmemr.obj` and its map contains the VDM memory functions. `xmsblock.c` uses `SAAllocate`, `SAFree`, `SAReallocate` against `ExtMemSA`. The alternate `STATUS_NOT_IMPLEMENTED` fallback registers `xmsCommitBlock`/`xmsDecommitBlock`; selected `xmsmemr.c` routes those to `sas_manage_xms`, whose CPU40 `stubs.c` body returns TRUE. Do not conflate this fallback with the normal reservation-success branch.

The selected `VdmAllocateVirtualMemory` implementation examined returns success, no-memory, or not-committed; no `STATUS_NOT_IMPLEMENTED` return is visible in that body. The normal commit callback invokes `VirtualAlloc` and returns `STATUS_NOT_COMMITTED` when the requested address is not obtained. The normal decommit callback calls `sas_overwrite_memory`, then `VirtualFree` and can return `STATUS_UNSUCCESSFUL`. Thus failure is supported by the actual callback contracts, unlike the always-TRUE fallback. Whether valid guest operations can induce a failure at the exact fixture stage, with a particular host condition, remains unproven.

## Controlled observations and limits

Original `CommitChunk` invokes callbacks by page and exits on the first nonzero status without undoing earlier successful commits. `FreeChunk` snapshots the struct, clears allocation bits, invokes decommit, then restores the struct on failure. The bitmap is outside the copied fixed struct, so the fixture reports a failed free as available despite failed decommit. Parent-reported controlled fixture observes second commit failure with first page committed and bitmap free; and first decommit failure with 4096 bytes exposed free. These demonstrate the source's reaction to callbacks selected by the fixture, not that `VirtualAlloc`/`VirtualFree` fail in a real XMS session or that a guest has corrupted data.

For actionable verification, instrument an isolated host boundary around the real selected `VdmCommitVirtualMemory`/`VdmDeCommitVirtualMemory` and drive original XMS allocation/free through the guest with a controlled single underlying API failure at the second commit or first decommit; verify callback arguments, retained host pages, bitmap/guest-visible return and subsequent allocations before classifying impact. Distinguish genuine API errors from invalid harness state, preserve original guest, and keep existing no-injection XMS lifecycle as control. Test the semantics before proposing rollback: decommit has `sas_overwrite_memory` side effects before native failure. No autonomous fix or completeness claim is made.
