# WOW per-drive directory synchronization: source review

Scope: shard 2 `wow32/wdos.c`; frozen reconciliation SHA-256 F73FFD45DFF44FCA4ECEFC49EF769BEAB5C085542CD04FFE4D6A7B5F942E3196. No guest or product changes; no new runtime execution. The selected product object/map evidence is in `wow32-selected-link-inventory.json`. This modified original remains **partial**, not proven full restoration.

`wktbl2.h:322,325-326` dispatches the original KERNEL thunks to `WK32SetDefaultDrive`, `WK32GetCurrentDirectory`, `WK32SetCurrentDirectory`. Those enter `DosWow*` and use guest CDS/current drive, the long-path `CurDirs` array, TDB directory validity/owner, and native per-drive `=X:` environment. `UpdateDosCurrentDirectory` explicitly synchronizes host cwd and guest state; native `WU32DlgDirList` and common dialogs synchronize in both directions (`wudlg.c:459,478`, `wcommdlg.c:1645,1692`), while `wkgthunk.c:44,171` imports DOS-to-host only. These call sites are outside this shard and were read only.

The actual per-file source difference is DIV-294: shared `demexp.h` supplies the worker's existing cdecl `demClientErrorEx` declaration instead of a duplicated prototype. `src/mvdm/README.md` and `docs/etc/evidence/m0-t422-s1-normalized-wow32-mirror-delta.md` explain why an inherited stdcall declaration would mismatch the real worker ABI. This is a boundary correction, not a replacement directory algorithm. Source identity/hash and exact diff accounting remain in `file-audit.csv`.

Original `SetCurrentDir` changes native cwd before setting `=X:`; `DosWowSetCurrentDirectory` then may allocate/update `CurDirs`, update CDS and TDB. Failure can therefore leave partial publication. `docs/etc/evidence/m0-t453-s1-files-environment-oem-owner-matrix.md` explicitly records this original ordering; the source review does not establish a bug or justify transactional rewriting. Long paths, drive changes, invalid media and TDB switching need exercise against the original semantics, including failure side effects.

Historical evidence is bounded: `m0-t453-s2-oem-runtime-witness.md` reports real DOS direct/nested OEM operations, not Win16 directory thunk execution. Two production-object caller fixtures establish dialog/import sequence but substitute the `UpdateDosCurrentDirectory` boundary; they cannot demonstrate its implementation. The separate Win16 probe did not reach guest calls and is not a product failure. Tests should complete an isolated real Win16 short/long per-drive/TDB-switch comparison, plus native dialog cwd propagation and failed-path effects; check existing fixture harness failures before attributing failure to product. No claim is made that missing evidence establishes a missing feature.
