# WOW16 reconciliation merge recommendations

[Merge table](s10-followup-wow16-merge-recommendations.csv) joins the latest `role-pending` inventory to the original recipe/consumer observations, current source hashes, functional owners and limitations. It covers all 240 C/H rows, with no hash mismatches in that join. The table is an audit recommendation; no shared ledger, guest or runtime has been changed.

* 66 header files have a bounded observed guest source role: each has an unchanged guest-C quoted-include witness, no same-basename non-guest C/H include found by the captured scan, no exact dependency or graph mention in four selected trees, and source matches the original. The [refreshed Ninja 1.13.2 evidence](host-ch-scope/guest-header-round4-refresh-evidence.json) reports zero stale blocks in each tree. [Recipe verification](host-ch-scope/guest-header-round4-refresh-recipe-check.json) checked 899 witness recipe references, with no hash mismatch. This supports only a captured-profile physical-source exclusion. It does not exclude functionality, guarantee all configurations, or prove a particular guest image/runtime.
* 174 have sufficient source-level purpose and stage ownership for a **conservative partial/source-role record**, but the actual host/guest/shared build identity or behavior remains bounded in each row. This label is not a claim of host runtime execution, complete behavior, or a reason to remove code. The 19 historical dual Win16/Win32 DDEML test C files and 11 local test headers illustrate why directory-only guest classification is wrong; GDI metafile code explicitly documents a dual 16/32 design.

The genuinely unresolved question is not whether each filename has a source description: it is the actual selected consumer, preprocessing, indirect inclusion, or host include-path resolution where noted in the table. Names alone and zero matches in selected graphs cannot prove global absence. Future S14-S17 retain the relevant WOW, USER, GDI, tool and service behavior; DOS DBCS and device contracts additionally remain S12/S13 where applicable. None of these observations modifies/rebuilds guest, restores a capability, or grants a compatibility exception.
