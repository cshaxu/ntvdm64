# Shard 0 Win16 core guest source roles

The [28 exact-path candidates](wow16-core-guest-owner-review.csv) retain
original and frozen source identity. The
[input record](wow16-core-guest-owner-inputs.json) identifies each inspected
original makefile, response and traversed local include. This is a
source-role review, not a guest rebuild or runtime acceptance.

The main session inspected actual USER DAYTONA, GDI, SYSTEM and driver
responses, matching selected object names to explicit make targets and
unambiguous local C/ASM source. Missing/generated or ambiguous source names
were not inferred. MMSYSTEM uses its actual OBJFIRST/OBJ1-OBJ5 list and
CL16/MASM suffix rules plus the inline link16 response. Local quoted C
includes and literal assembler includes supply the recorded header edges;
unresolved include paths are not guessed. CONFIG.ASM has the explicit
link16 CONFIG.EXE -> exe2bin CONFIG.BIN -> DISPLAY.RES -> RC16 driver chain.

The DAYTONA response is an admitted byte-exact supplemental historical
artifact; its independent identity was checked against the supplemental
provenance record. This does not select supplemental native runtime code or
prove this response produced any current distributed guest binary. The 28
accepted files themselves match primary selected originals. Debug/retail,
locale, architecture and original conditional branches remain limits.

Only shard-0 pending paths within the core/driver families were proposed;
shared `wow16/inc` and the agents' extension paths were not claimed. EDIT
implementation bodies, dual-purpose GDI16 metafile code, prebuilt resources
and binaries without the selected input proof remain pending. Host-input
absence is checked separately in the combined checkpoint. No file or
capability receives full-restoration status from this evidence.
