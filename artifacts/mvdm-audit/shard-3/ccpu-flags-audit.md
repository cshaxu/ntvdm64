## CBW/CWD exhaustive and BSWAP selection boundary

The selected cbw.obj and cwd.obj come from byte-identical original source and both appear in `ntvdm.exe.map` as original-ccpu386 symbols. `ccpu-sign-probe.c` SHA-256 `88308D85C0BD5F7061CB439AF40B6CD4E7EE013A5DDA85D42A816E3743B2E450` links the actual selected x86 cbw.obj `DCC35EFADD8110F38F8DDE21ACDD8A4830E5F147332A618D92DEB687ACF0C494` and cwd.obj `0F1B3ABE9929C3C3158DD09252BE2688046E620EF8251D9C7CA44CF173036D72`. A fixture-owned byte/word register-pointer projection supplies EAX/EDX; all 65,536 low-AX inputs per instruction matched actual native x86 CBW/CWD and preserved the other register and upper halves. `/W4 /WX` build, process exit 0, `CBW CWD native-reference inputs=65536 each failures=0`. This does not prove decoder/guest dispatch, register pointer initialization in the full CPU or asynchronous behavior.

For bswap.c, the build graph selects an object, but actual command defines `SPC386` rather than `SPC486`; the original function body is under `#ifdef SPC486`. `dumpbin` of selected bswap.obj has no BSWAP external and ntvdm.exe.map has no BSWAP symbol. Original `c_main.c:1832–1860` maps 0F C8–CF to Int6 under the same non-SPC486 branch, rather than silently providing 486 BSWAP. This is the selected 386-mode semantic boundary, not evidence that BSWAP executes nor sufficient authority to discard 486 support as an overall product capability. No guest test was run. All three ledger entries remain pending for system-level configuration/guest verification.

Undefined flags are intentionally excluded from semantic comparison.

The focused test uses fixture-owned state, not the product CPU state initializer, and does not cover AAD other immediates, guest decode, instruction-level exceptions or protected-mode integration. Keep `aad.c` and `daa.c` pending until their full system behavior and evidence policy are reconciled; do not convert selected symbols or native differential success into proof of every encoding.
