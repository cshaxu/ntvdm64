# Immutable guest historical build carriers — shard 3

`guest-build-carriers.csv` records 239 frozen guest-build-input rows classified by exact path, family, file role, current/frozen SHA256, current three x86 Ninja target exact input path and exact whole-file hash match among the 54 staged `package-c/system32` files. All 239 match the frozen hash and none is a direct inspected host graph input or identical standalone staged system32 file. The roles are 16-bit guest object files, historical build/link recipes/response files, and linker symbol/map/PDB evidence—not executable guest runtime images. All 239 are `excluded` **for those carrier files only**; it is not an exclusion of a corresponding guest application, device, guest source, or behavior.

Original target/role examples constrain the grouping: DOS `cmd/debug/makefile` declares `dest=debug.exe`, assembles named modules and invokes the guest linker; `debug.lnk` enumerates `DEBUG`, `DEBCOM*` and `DEBASM` etc. before `DEBUG.EXE`. `wow16/kernel31/makefile` separately distinguishes `debug3` and `retail3` build destinations, so their `.OBJ` entries are historical build intermediates, not two independently proven installed kernels. `wow16/winsock/winsock.lrf` names `winsock.obj`, `winsock.dll`, link options and `libw.lib`. Similar retained response/map/object families are grouped by path in the CSV; names identify intended historical family, not proof of source-to-product provenance. File extensions and these named target examples do not prove the archive's binary was built from any individual object.

The prior `guest-input-review.md` records archive-manifest identity evidence and observed guest capabilities, including exact identity of some shipped files. This batch does not repeat or upgrade those findings: no source→binary reproduction is established, installed package file identity alone does not prove a function, and unchanged guest source/headers, resources, executables and archive members remain pending or separately reviewed. Product graph inputs do not enumerate all historical/auxiliary build workflows, and a complete file hash search cannot detect matching bytes embedded inside an image. The three Ninja closures concern only current host product builds, not guest rebuilds. Any mirror-diff source stays partial. No original or existing guest was modified, built or executed; no product or combined ledger was changed.

## Format-validation correction

The initial 239 file-role dispositions were not sufficiently supported by extensions alone. The companion CSV now records content evidence for every file. All 163 OBJ files parse as complete OMF record framing: THEADR/LHEADR first, MODEND/MODEND32 last and no trailing/truncated bytes. Five contain one or more record checksum sums that are nonzero; this is recorded per file as an observation, not a corruption claim or source-to-image proof. All 24 MAP files are text with linker `Start`, `Length`, `Class` segment headings. The PDB begins with the explicit Microsoft C/C++ program database 1.00 signature. The 43 recipe/link-response files contain actual build/link directives or named inputs; the DOS command aggregate makefile is separately verified to recursively invoke `$(MAKE)` for DOS utility directories.

The eight binary `.sym` files contain symbol-looking strings but no independently verified format parser or definitive host/guest consumer evidence; they have been **restored to pending**. Therefore this batch now excludes 231 file-role carriers and retains eight pending, not the previous 239 exclusions. Existing guest/source behavior, archive correspondence and the no-rebuild boundary remain unchanged. A record-format check is not proof that an object was linked into the distributed executable.
