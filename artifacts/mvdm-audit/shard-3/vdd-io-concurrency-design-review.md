# VDD I/O hooks: synchronization and retirement design

## Current source and evidence

`nt_vdd.c` exports install/deinstall and manages `VddAdapter` without local synchronization. Its `host_ica_lock` calls belong to IRQ reservation/release, not hook registration. The public `nt_vdd.h` declares the APIs without a thread restriction. AdLib sample invokes install/deinstall from DLL process attach/detach; VSBD also uses these APIs and creates an independent worker thread, although that fact alone does **not** prove the worker calls install/uninstall. Thus neither observed serial nor observed concurrent production calls are proven.

`ios.c` has separate input/output port-to-adapter tables and per-adapter handler tables. `io_connect_port` writes table bytes; `io_disconnect_port` compares an adapter then clears both directions. There is no lock visible in those bodies. Direct CCPU `IN8`/`IN16` in `base/ccpu386/in.c` indexes these tables and calls the selected function directly; generic string-I/O helpers can cache a handler for a loop. Consequently an installer-only mutex does not synchronize dispatch or pin a callback. The test in `vdd-slot-reuse-interleave-review.md` proves an old mapped port can call a replacement handler after slot release/reuse, using a controlled split of the uninstall; it does not prove a real VDD invokes APIs concurrently.

## Design choices

**A. Metadata lock around full install/deinstall, with corrected slot identity and release only after disconnection.** This serializes concurrent registration mutations and closes the demonstrated slot-reuse interval with small code change. It does **not** protect a CCPU thread that already loaded a callback pointer when a DLL is unloaded, nor generic string I/O caching a pointer. Holding the same lock while calling arbitrary VDD handlers would risk reentry/deadlock, especially because the sample performs uninstall inside DLL detach. Thus this is sufficient only if a separately proven and tested lifecycle rule already guarantees callbacks are quiescent before detach; that guarantee has not been established.

**B. Two-phase retirement with the same single adapter owner.** Under a bounded metadata lock, mark the existing slot retiring, prevent admission/reuse, and disconnect its port associations; dispatch must use the same synchronization to acquire a live callback/use reference before releasing the lock and must release that reference after the callback. Retire/reuse only when outstanding references are zero; preserve correct registration and rollback. This avoids calling VDD code while holding the metadata lock and covers dispatch/retirement races, but requires adapting all actual IOS and CCPU direct-dispatch paths, including generic string I/O and module lifetime. A new per-adapter lifecycle counter is coordination state, not an alternate owner of port mappings; it still must have one authoritative owner. It must not add a separate competing routing table.

**Critical unresolved contract:** synchronous waiting during `DLL_PROCESS_DETACH` can deadlock with loader lock, another callback trying to enter the loader, or a callback uninstalling itself. Conversely returning while code can still be called risks executing an unloaded module. The source reviewed does not establish a safe module pin, an existing pre-unload quiescence protocol, or self-uninstall semantics. Therefore B's module ownership/retirement must be designed and proven using the actual loader and VDD entry paths before implementation; no claim that a bare condition variable or reference count solves unload. If pre-unload quiescence is already owned elsewhere, reuse it and test it; do not invent a second lifecycle authority or make the guest wait indefinitely.

## Finite tests before choosing

1. Trace selected module-load/unload and callbacks with real object identities: determine whether unload necessarily follows a CPU quiescence boundary, whether VDD-owned native threads may issue public hook APIs, and whether callbacks can uninstall themselves or reenter registration. Sample `DllMain` use must be included in loader-lock analysis.
2. Keep the existing seven-slot strict test and deterministic slot-reuse witness. Add event-gated concurrent install/uninstall, same/different-port overlap and failed-install rollback. Assert unrelated owners and counts; no sleep-based synchronization.
3. Gate direct CCPU IN/OUT and generic string callback after handler acquisition, begin retirement, and verify no callback is invoked after its owning module is retired or reinterpreted as a new slot; include reentry and callback-in-flight. Exercise both successful and failed acquisition and exact once retirement.
4. Exercise actual original-compatible module loading and unloading in an isolated fixture, including detach/loader lock and owner session exit; if not exercised, explicitly preserve this as unverified. No real guest, device or global driver is needed for controlled negative cases.

Do not silently assume serialized callers or declare the two-phase design proven by the existing split-stage fixture. The separately proven raw adapter-number defect and DMA bounds are still independently fixable. No product, guest or shared ledger changed in this analysis.
