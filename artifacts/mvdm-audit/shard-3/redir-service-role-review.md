# DOS redirector BOP services and lifecycle — shard 3

Scope is pending `inc/rdrsvc.h`. `redir-service-observer.py` and captured JSON compare source identity with both original trees and independently compare the numeric ASM and C SVC constants: all 50 parsed names are shared and equal. Capture includes the existing worker map and previous `redir-private-map.txt` symbol excerpts. This is static evidence; no product, guest or network test was run and no shared ledger changed.

The guest redirector emits SVC bytes from RDRSVC.INC: INT 5C dispatch is in `dos/v86/redir/int5c.asm:141,296` and DOS process termination invokes SVC_RDRTERMINATE in `resident.asm:384`. `nt_bop.c::MS_bop_7` lazily calls `LoadVdmRedir`, then dispatches through VrDispatch and advances guest IP. The loader uses `SafeLoadLibrary` and resolves required exports; selected host adapter `src/ntvdm-exe/softpc/mvdm_softpc_firmware.c:35-48` roots VDMREDIR to the product path and uses `LoadLibraryW` (DIV-323). Current BOP chooses the actual real/protected mode when reading the guest service byte (DIV-466). `vdmredir/vrdisp.c:58-110,114-155` uses a bounded 50-entry table and rejects unsupported values. Prior private map records VrDispatch/VrInitialize/VrUninitialize/VrTerminateDosProcess; the worker map records loader and MS_bop_7. The earlier redir review captured exact private-link text match to its then-published DLL; neither map is bound here to the latest release.

Lifecycle has two distinct scopes: `vrdll.c:157-170` calls VrInitialize on DLL process attach and VrUninitialize plus TerminateDlcEmulation on process detach; `vrmisc.c:45-80` uses the terminating DOS PDB to release its mailslots and named pipes. Dynamic behavior, pending I/O and race safety require separate evidence. Existing `docs/etc/evidence/m0-t430-s1-inherited-contract-audit.md:134-155` already records redirector source risks as hypotheses rather than reproduced faults.

A narrow loader failure issue warrants verification: after loading the DLL and resolving some exports, `nt_bop.c:642-644` calls `CloseHandle(hVdmRedir)` rather than `FreeLibrary` on the module returned by the LoadLibraryW-based provider. Source shows the loader only sets `VdmRedirLoaded` on full resolution and `demhndl.c` checks that flag before named-pipe calls, but a complete audit of all partially assigned callbacks, actual missing-export behavior and process-detach cleanup was not performed. This is a source-level module-reference cleanup concern, not a claim of reproduced failure or active use-after-free; compare original handling and project failure contract before repair.
