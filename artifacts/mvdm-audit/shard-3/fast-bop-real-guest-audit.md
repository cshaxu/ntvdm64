# FastBOP selector — independent Win16 guest allocation witness

Two independently authored Win16 NE probes run against the published `build/package-uuid/package-c` inputs in separately staged, `-FreshPackageIdentity` physical runtimes; no existing guest or product image was modified. Both call original `DPMIBOP 53:03`, then repeatedly call original KERNEL `AllocSelector(0)`, retain each returned selector, and later invoke `FreeSelector` for each retained value. `KERNEL` import ordinal 175/176 and BOP bytes follow selected guest source; neither probe performs CALLF to a reused endpoint.

- r1 source SHA-256 `85BB8CDD228ADEC160679DEB3C3972880DB4903F61506B418E4941F304D8B7B8`: compares all 16 selector bits with returned endpoint. Its 18-byte `FB01` report is in `build/t473-s10/shard-3-fast-bop-guest-r1/guest-report.bin`.
- r2 source SHA-256 `D0F79B32BDBD9B7D13D1FF6B7BD41226939DFD7A0EAA2C46141F61BD00EB6CBA`: compares selector index after masking TI/RPL low three bits; all allocations come from this same original LDT selector allocator, but index-only comparison intentionally treats differing low bits as a conservative hit. Runner SHA-256 `973AB77C793AC4870D891E21020EF7175F6AAF06DCE6DCCD5A7553FF0D752A21` is an isolated adaptation of the existing DC guest runner; its `stage-identity.json` records unique staged identity and source/staged hashes.

Both observer runs completed with guest exit 0. Endpoint was `ES=0xfff7`, `DX:BX=0000:0010`; 8035 successful allocations were observed without an endpoint hit. Since 8035 is below the 8190 loop cap, the next AllocSelector call returned zero (rather than stopping at the cap). Both exact-value and masked-index checks found no match in their respective independent runs. This is a bounded observed allocator exhaustion, not proof about other selector allocators, direct `INT 2Ah` publication, other guest builds or task/worker restart.

The probes decrement their retained-count after each `FreeSelector` call but do not assert its return, reallocate to confirm reuse, or inspect live LDT descriptors after release: `remaining=0` means all 8035 release calls were attempted, not independently verified successful. The report's previous `released=0` label means remaining count and must not be read as proof of release. The stage's KRNL386.EXE SHA-256 was `D404576899CC11D23F368F2B30554E6108657CD37809837B341FD37E6B1A7AF4`, equal to source package and `O:/winnt/system32/KRNL386.EXE`. Observer output reports `image-identity=unavailable`, so actual loaded kernel image identity is not independently pinned by these artifacts. Source package ID `ad4ac7ac-cffa-4892-8770-e41a5b765e94`, r2 staged ID `7ad47381-05de-4ff6-9f10-8f2e0613396f`; fresh resource stamping changes staged host hashes (WOW32 source C318... and staged D6AC...), while the guest KRNL hash remains unchanged. r1 stage identity value was not retained.

This witness contradicts an unqualified claim that this particular ordinary allocator traversal necessarily reuses the FastBOP endpoint. It does not disprove the separate host fixture's deliberately cleared-descriptor stale redirect, or establish that the immutable runtime implements every source free-list detail. The causes of the non-hit and lifetime after external descriptor overwrite remain open. Owned isolated stages were cleaned by the tracked helper; no unrelated task processes were terminated.
