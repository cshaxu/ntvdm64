# Serial NT IOCTL helpers and failure paths

Scope: shard-3 `softpc.new/host/src/nt_ntfun.c`, frozen byte-identical OpenNT. Source and historical evidence only; no new runtime/fault-injection test, product or guest edit.

Original `nt_com.c::host_com_write` routes XOFF characters to `SendXOFFIoctlToDriver`, which allocates an `IOSTATUSLIST`, calls this file's `SendXOFFIoctl` (`NtDeviceIoControlFile` with `IOCTL_SERIAL_XOFF_COUNTER`), then appends successful/pending state under `current->CSEvent`; completed list elements are removed in FIFO order by `RemoveCompletedIOCTLs`. Other helpers translate host serial baud/line control, streaming modem/line status, and `FastWaitCommsOrCpuEvent` issues the serial wait IOCTL then waits on communication or CPU events. Its local static outstanding IO status assumes its documented single calling thread; the selected provider's thread/handle lifecycle is not proven by that source statement. The current product map attributes selected `_SendXOFFIoctl`, `_AllocStatusElement`, `_FastWaitCommsOrCpuEvent`, `_EnableMSRLSRRXmode` to `original-softpc-host-roots:nt_ntfun.obj`.

Two original low-resource/driver-failure conditions need targeted evidence: (1) `AllocStatusElement` can return NULL, and `SendXOFFIoctlToDriver` does not check before forming the `ioStatusBlock` member address in `SendXOFFIoctl`; (2) failed `NtDeviceIoControlFile` in `SendXOFFIoctl` calls `fprintf(trace_file,...)` without the `#ifndef PROD` found in neighboring functions. The NTVDM map lists `_trace_file` as `<common>`, which does not alone prove its initialized value at this point. These are concrete source-level conditions, not a demonstrated guest crash: whether serial XOFF reaches them, whether allocator exhaustion occurs, and trace lifetime in the production image need actual source-linked failure injection. Do not infer a NULL dereference solely from taking a member address; observe the actual call and handler behavior.

Historical T420 S30 used real COM3 and controller loopback but could not send externally with CTS low; its `tests/mvdm-host/nt_com_mock_fixture.c` explicitly replaces these nt_ntfun functions (including status allocator, XOFF send and wait). Therefore its mock open/write/read/close does not cover either condition. A minimal fixture should compile/link the real selected two source bodies or actual objects with only allocator/NT IOCTL and host event boundaries controlled, force allocation and immediate IOCTL failures separately, record output/status and resource ownership, and include success/pending controls. Do not install a serial driver, modify guest, or bypass production error reporting to manufacture success. This row remains pending.
