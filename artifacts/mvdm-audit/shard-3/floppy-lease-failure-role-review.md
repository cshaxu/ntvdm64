# Floppy close/lease failure: source proof and deterministic test design

This follow-up assesses `nt_rflop.c` and `nt_fdisk.c` without editing or running product/guest/device code. `floppy-lease-failure-observer.py` and its JSON hash the current sources, original editions, existing failure fixture, compatibility wrapper, build generator and nt_rflop.obj; they retain relevant relocations and the actual retained compilation command. Earlier `disk-close-failure-audit.md` records an actual-object fixture with a deliberately failed counter update, not a real session-bound lease failure. Its observed result is native handle closed/invalidated while floppy open count, owner and lock remain set; this is an actual provider state inconsistency under the injected failure, regardless of whether real media triggered it.

## Actual worker-thread boundary

`nt_rflop.c:1082-1087` starts `fdc_thread` with CreateThread; `fdc_thread:1479-1505` calls get_drive_handle and later nt_floppy_close. This source path contains no explicit session bind. Unlike several other host source files, `tools/build/New-T310OriginalSoftpcNinja.ps1:1085-1100` does not select thread_start_compat.h for nt_rflop.c. The retained command snapshot likewise has no forced thread compat include. More decisively, the present nt_rflop.obj relocation block for nt_rflop_command references `_fdc_thread` followed by `__imp__CreateThread@24`, not the project session-aware thread thunk. The object/map/command snapshots are separately hashed; identity with the newest deployed EXE has not been independently verified.

`session.c:7,382-385` uses TLS for `session_thread_current`; `mvdm_command_guest_state.c:75-83,174-200` requires that thread binding plus the matching active session and guest-memory epochs for the FD-access update. Therefore, **if that directly created FDC thread reaches a new successful CreateFile open**, the subsequent `add_fd_access(1)` fails with no thread-local owner, closes the new handle and rolls its local open state back. Likewise, **if the thread reaches nt_floppy_close with an existing valid handle**, `add_fd_access(UINT16_MAX)` fails for that reason after the native close, leaving the known stale local close state. These are conditional consequences of the source and observed object, not an assertion that a real floppy/no-media path has been observed or is frequent. A creator with no valid session can add further failure modes; do not generalize beyond this path.

`thread_start_compat.c` already provides session inheritance and owned binding for admitted original threads, but it is not wired to this object. `fdc_thread` has a historical `void fdc_thread(PFDC_PARMS)` signature cast to LPTHREAD_START_ROUTINE, so the x86 calling convention must be matched by the appropriate void-cdecl-parameter adapter rather than a blind WINAPI cast. Merely binding the thread does not resolve its process-global fdc_parms / handle reuse, termination/join, callback ownership, or possible concurrent scalar update: use the existing session ownership/binding contract and reconcile those lifetimes as one design.

## Can this be fixed on host?

Yes: both failures originate in project-owned worker/session integration and can be repaired without touching the guest or inventing a different disk protocol. The close-side native handle and local owner/count/lock must be retired once even if guest FD counter update fails; a failed authoritative guest update still must be reported and reconciled/terminated under the project's existing lifecycle contract, not reported as successful close or followed by uncontrolled reuse. Determine and enforce a single synchronization/ordering rule for scalar read-modify-write and active worker lifetime before admitting a thread binding. Avoid suggesting a scalar retry after guest/session expiration or decrementing it twice. Original disk semantics and 16-bit guest bytes remain untouched.

## Deterministic verification to add with any repair

1. In an isolated fixture, create an actual active session and real guest-memory lease/scalar; enter from a separately created original-compatible FDC thread. Interpose only device open/media/close with deterministic fake handle operations and gate the thread with events. Verify actual `session_thread_current`, owner/epoch and FD-access `+1/-1` behavior, original provider state and exact cleanup; include the pre-repair negative.
2. Exercise successful new open and already-open-close paths; inject counter read, write and release failures separately. Assert handle, owner, lock, open count, guest scalar and returned failure independently; double close must not decrement again. The existing close fixture is a control, not proof of real lease failure.
3. Gate a no-media thread, reset it and immediately request another operation; prove old thread is stopped/joined before parameter reuse or demonstrate an equivalent established ownership mechanism. Test CreateThread failure and session shutdown while pending, with no arbitrary sleeps and no real device.
4. Verify concurrent/main-thread FD updates cannot lose or duplicate a count, and once the session has become invalid no stale guest write occurs. Observe error notification and worker exit under NTSRV's approved ownership contract. Exercise both floppy and fixed-disk close failure even though only floppy owns this FDC thread.
5. Re-run actual applicable DOS/WOW/Win3.x regression after a repair; any physical-media and hardware timing cases not exercised stay explicit. Tests of fake handles cannot claim real floppy compatibility.

`nt_rflop.c` remains partial; this document records a concrete, host-fixable integration gap and unverified external triggering, not a completed implementation or acceptance.
