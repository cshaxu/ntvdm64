# DPMI i386 vs selected CPU40 allocator — shard 3

This read-only review covers pending `dpmi32/i386/dpmimem.c`; `dpmi-allocator-observer.py` and its captured JSON verify source hashes against both original trees and preserve observed map lines. The i386 file is byte-identical to both references. Current `dpmimemr.c`, `xmem.c`, and `dpmi32.c` differ; no blanket original-identity claim applies to the selected chain.

The historical i386-specific source is selected by original `dpmi32/sources:56`. It supplies allocation/free with `NtAllocateVirtualMemory`/`NtFreeVirtualMemory`, reallocation by page-count comparison or allocate/copy/free, and memory info derived from host GlobalMemoryStatus with a 15 MiB largest-free cap (`i386/dpmimem.c:38-260`). These are native-VDM monitor assumptions, not proof they should be swapped into CPU40.

Current observed worker map SHA and lines in JSON show those four provider symbols under `dpmimemr.obj`, alongside xmem allocation and task cleanup from `xmem.obj`, rather than the i386 source. `dpmi32.c:57-69` publishes the allocation/free and cleanup DPMI entries. `xmem.c:55-119` allocates the provider range, allocates a tracking block, records address/length and owner, and rolls the range back if tracking allocation fails; `:125-170` frees the range before unlinking/freeing tracking state. `DpmiFreeAppXmem` implements owner-based cleanup. These observations are static, not proof of live dispatch or complete failure recovery.

Selected `dpmimemr.c` uses the original shared XMS suballocator directly for CPU40 allocation, free, reallocation and free-space reporting under MVDM-HOST-DIV-224 (`:65,124,182,263`); `xmem.c:210` records MVDM-HOST-DIV-272 for BOOL reallocation result handling. The former reports actual shared-pool free space instead of the historical i386 host commit estimate; the latter removes an NTSTATUS/BOOL ambiguity at the current caller. These registered local differences are material, not source identity. See existing shard 0 exception registry candidates for the original authority links and justification; exact source and map hashes are independently captured here.

Proposed status for `dpmi32/i386/dpmimem.c`: **pending**, as an alternative historical allocator with a real current provider, not a missing function merely because the file is unselected. Comparing its native reservation/memory-info model with the selected shared-pool model identifies an observable reporting and allocation-policy difference; neither identical guest semantics nor a regression is established by source reading. Explicit witnesses are still needed for guest-visible alloc/free/realloc including grow, shrink, move, low-memory and tracker allocation failure; owner teardown, concurrent/reentrant operations, invalid/stale handles; and memory-info behavior under fragmentation and exhaustion. The existing map is not bound here to the latest published image; no guest image was modified and no runtime test run. No percentage of restored behavior is inferred.
