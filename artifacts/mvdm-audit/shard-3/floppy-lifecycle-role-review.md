# Selected floppy I/O, worker and close lifecycle — shard 3

This follow-on is a read-only cross-file chain review of selected `nt_rflop.c` (current shard 3 partial) and original GFI/floppy sources. `floppy-lifecycle-observer.py` and captured JSON record source hashes against both original editions, observed worker map providers and normalized retained C-dependency blocks for gfi.obj and nt_rflop.obj. Original gfi/fla/floppy_i match both editions; nt_rflop.c differs, with DIV-006/111 documented in source. No physical or virtual device was opened; no build, product or guest file was modified.

Original `gfi.c:136-180` dispatches through per-drive gfi_function_table. `nt_rflop.c:550-650` opens the host floppy device, queries alignment and supported media, closes the temporary initialization handle and registers the original command, motor, reset, type and change function pointers only after success. Alignment/media query failures call termination; no supported media also fails init. `nt_rflop_command:1030-1090` checks media, may close/reopen and delegates a pending-media operation to fdc_thread; `fdc_read_write` and nt_floppy_read/close are selected map providers. DOS process termination uses owner PDB to close matching handles (`floppy_close_down:895-909`); `nt_floppy_close:911-934` closes/invalidate native handle before updating the project-owned guest counter lease.

Prior `disk-close-failure-audit.md` records a focused actual selected object test with the guest counter function deliberately failed: native handle was closed but original open count and floppy owner/lock remained stale. That is a fault-injection witness for the close transition, not proof a real lease failure happened. Preserve its remediation/lifecycle obligation and DIV-006/111 rather than treating the source hash as an original-only behavior.

Additional static edges, unverified in this review:

* `nt_rflop_command:1057-1089` closes an existing thread handle without waiting, and supplies a process-global fdc_parms to a new thread after failed media checks. `nt_rflop_reset:1466-1471` sets fdc_reset, closes the thread handle and clears the shared handle; `fdc_thread:1479-1506` loops until media appears or that shared handle is NULL. Closing a Windows thread handle is not thread completion; whether reset/new request overlaps an old thread, affects shared parameters, or races module/session teardown needs an isolated deterministic witness and ownership trace. This is not a reproduced race.
* The source loop contains repeated get_drive_handle/media checks and no explicit wait in its own body. Determine whether lower calls block and what the actual behavior is before characterizing it as sustained busy spinning. CreateThread failure/result handling and restoring controller completion also need verification.
* `nt_gfi_rdiskette_term` closes a non-NULL handle; validate invalid-sentinel and partial-init paths with the actual native/open contract, not source inspection alone.

`nt_rflop.c` remains **partial**; GFI source status belongs to shard 0. Existing T420 S28 proves a guest INT13 reset in its stated conditions, not no-media retries, real media I/O, thread races or task/worker teardown. Hashes, map and deps snapshots do not establish identity with the latest deployed EXE. No overall floppy compatibility or restoration percentage is claimed.
