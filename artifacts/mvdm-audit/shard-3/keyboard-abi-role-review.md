# Win16 keyboard ABI and host mapping — shard 3

Scope is pending `inc/WOWKBD.INC`. `keyboard-abi-observer.py` and captured JSON compare this header and related source against both reference editions, and record observed WOW32 linker-map entries. All seven checked originals match both references byte-for-byte. This audit performs no guest build, runtime execution, desktop input or keyboard tests.

## Source chain and ownership

`wow16/drivers/keyboard/keyboard.asm:22,130-149` includes the ABI file and emits thunks including TOASCII, OEM/ANSI, key scan and key mapping, while marking INQUIRE, ENABLE, DISABLE and other local operations separately. `keyboard.def:14` exports TOASCII ordinal 4; `WOWKBD.INC` defines `FUN_TOASCII=4` and the corresponding 16-bit argument layout. `wow32/wowtbl.c` includes `wkbdtbl2.h`, whose ordinal 4 routes to `WKB32ToAscii`; the handler `wkbman.c:21-43` maps the frame, input and output pointers, calls the host `ToAscii`, flushes four output bytes, then releases mappings. Other entries route to host key mapping and codepage functions. This is the keyboard API translation path; it is not the DOS hardware keyboard controller or its IRQ/EOI state machine.

The map snapshot, hash and lines in JSON associate `WKB32ToAscii`, `WKB32GetKeyNameText`, `WKB32MapVirtualKey` and `WKB32VkKeyScan` with wkbman.obj; `wkbdtbl2.h` belongs to shard 1. The map is not independently bound here to the current released DLL. Guest local Enable/Disable and BIOS procedure implementations in `kbdlocal.asm` have separate behavior and must not be assumed to follow the host thunk route. The selected thunk delegates keyboard layout and state interpretation to host USER; guest input frame mappings remain valid only within their mapping/flush/free operations, while application/task teardown and event-queue behavior require independent evidence.

Proposed disposition: **pending** for WOWKBD.INC. Source and ordinal correspondence plus observed provider map do not establish that the installed guest keyboard driver was generated from this source, prove all compiled layouts or dynamically verify per-task keyboard state. Remaining behavior evidence includes host layout and dead-key interactions, locale/codepage conversion, invalid or moved guest buffers across host calls, focus and task teardown. No claim of actual defects or complete keyboard compatibility follows, and IRQ1 EOI fixes must be evaluated independently of this API path.
