# VDD loader ownership and hook retirement

## Verified selected source paths

- Guest third-party BOP `MS_bop_8` (`nt_bop.c:664–686`) dispatches register, deregister and call. `ISV_RegisterModule` (`:899–1007`) calls `SafeLoadLibrary`, resolves init/dispatch exports, calls init and publishes an `isvbop_table` entry. Missing exports and invalid export-name cases call `FreeLibrary` **after load**, potentially after DLL process attach installed hooks. `ISV_DeRegisterModule` (`:1010–1027`) calls `FreeLibrary` first and only then clears the table entry. No explicit hook/dispatch quiescence is present in these bodies. `ISV_DispatchCall` reads the table's callback and calls it directly.
- The separate `nt_msscs.c:167,666–740` setup path calls `SetupInstallableVDD` after reset, enumerates the layered registry's VDD multi-string, and calls `SafeLoadLibrary`; its local `hVDD` is not stored by that function and there is no paired `FreeLibrary` in this path. It is not the guest BOP table owner. What eventually unloads such a module and whether a repeated reset adds references are separate lifecycle questions; do not assert an answer from the missing local pair.
- Original `vdd/samples/adlibvdd/vdd.c:426–437`, `sample2/vdd/vdd.c:113–119`, and `vsbd/vdd.c:592–595` call `VDDDeInstallIOHook` directly or through their helper from `DLL_PROCESS_DETACH`. These are source examples, not evidence that the present installed product loaded them. Importantly, attach can install hooks before subsequent BOP export resolution fails.
- Current install/deinstall mutate the IOS adapter and callback tables without local registration locking. CCPU `IN8`/`IN16` and IOS helpers call entries directly. Existing controlled actual-object split-stage test in `vdd-slot-reuse-interleave-review.md` shows the stale mapping can call a new owner's handler. It does not prove a live unload race.

No pre-`FreeLibrary` VDD hook quiescence was found in the **examined** BOP or installable-VDD paths. This is bounded source evidence, not proof that every possible third-party native thread or external loader entry is controlled by the project.

The isolated [test-owned DLL control](vdd-loader-lock-probe-review.md) demonstrates a loader-dependent wait cycle during detach on the observed host, and a separate deliberately deferred self-request control. Neither exercises the real VDD/IOS/BOP implementation or proves a compatible self-uninstall contract; the diagnostic test timeout is not a proposed runtime timeout.

## Proposed consistent owner sequence

For each **project-owned ISV load reference**, use the existing loader/table lifecycle as authority, not a second independent module owner. Before every project-owned `FreeLibrary` path, including registration failure after successful load, retire that module's registered callbacks: stop new dispatch and hook admission under the same owner, disconnect that module's mappings, then wait **outside any VDD callback and before entering `FreeLibrary`** for already-acquired callbacks to finish. Only after quiescence call `FreeLibrary`; the later original DLL detach `VDDDeInstallIOHook` must be an idempotent no-op for already-retired hooks. Clear/publish the BOP table and handle exactly once according to register success or failure. Do not hold the metadata lock while running init, dispatch, DLL entry or callbacks.

The dispatch side must acquire a reference to the *existing* module/adapter owner while under the same synchronization used for retirement, use the handler outside the lock, then release; it must cover CCPU direct IN/OUT, IOS generic byte/word/string loops and other registered callback families that can point into that module. Reuse the existing loader's valid OS module reference; do not invent a separate competing module or port table. The implementation must handle callback-initiated removal without waiting on its own reference. The path for that case must be derived from actual API and caller behavior and tested before adopting any observable deferral; do not claim synchronous semantics or automatic safe deferral without evidence.

The setup-loaded path needs a concrete authoritative owner for its acquired references and reset/worker-exit retirement. Any code that calls `FreeLibrary` directly outside project-controlled paths cannot be assumed to pass through this protocol; determine the admitted VDD contract and actual modules. During process termination, prove that no other thread is executing callbacks before allowing detach or describe the explicit limit. The exact synchronization primitive, CPU direct-dispatch integration, and scope for memory/user hooks are not established by the source review; they must be designed together, not hidden inside a single slot lock. The four-line adapter/DMA fixes remain separate and do not prove unload safety.

## Executable verification required

1. A test-owned DLL with real DLL attach/detach hooks and a controlled callback gate: register through actual BOP loader, pause callback after acquisition, request deregistration, prove callback completes before `FreeLibrary`/detach and no new callbacks or slot reuse enter. Use event coordination and no arbitrary sleeps.
2. Repeat for each post-load failure branch, same module multiple references, invalid/double BOP handle, registration rollback and setup-loaded path; assert exactly-once reference and hook cleanup. Verify actual image/object identity and no access to user media.
3. Exercise direct IN/OUT and cached string-I/O callbacks, reentry/self-uninstall, a native VDD-owned thread, and module detach under the loader lock. A test must not wait under that lock on a callback which can need it. Verify the accepted behavior against original contracts before any semantic concession.
4. Extend the ownership sweep to memory hooks, user hooks, BOP dispatch and process/session shutdown, ensuring no registered function pointer survives the module. Keep untested categories explicitly open; a port-only test cannot prove complete DLL lifecycle.

These are source-derived proposed implementation and a finite verification matrix, not a runtime fix or proof that live VDD calls are concurrent. No product, guest or shared ledger was modified.
