# Guest source/resource ownership candidates — shard 3

`guest-source-owner-review.csv` inventories all 424 still-pending frozen `immutable-guest-or-guest-build-input` paths at review time. Each live file matches its recorded frozen SHA-256; it records up to five exact filename occurrences with path, line and text in original nearby makefile/sources/link recipes, plus exact hash matches in `assets/winnt-guest-manifest.json`. Searches cover each file's directory and two parent directories, so no hit means **not located in that bounded search**, not no original build use. A textual occurrence can be a comment, dependency or inactive branch; the 223 guest-build-input candidates require role/target review before changing classification. They are candidate host-build-input exclusions only, never guest-function exclusions. The other 189 remain owner-chain pending, including runtime-named binaries that did not exactly match the archive manifest. This candidate CSV does not change `file-review.csv` or combined accounting.

Twelve rows have immutable runtime-image identity candidates: COMMAND.COM, KB16.COM, HIMEM.SYS, KEYBOARD.SYS, KEYBOARD.DRV, two mouse source-path images matching MOUSE.DRV, GDI.EXE, SHELL.DLL, SYSTEM.DRV, USER.EXE and WFWNET.DRV. Their exact manifest destinations are in the CSV. They match by complete SHA, not name; one file named MOUSE.EXE matches the archived MOUSE.DRV bytes, illustrating why names cannot decide identity. This establishes archived asset identity only: it does not establish loading in every worker or functional completeness. Current `assets/winnt.zip` hash `7A0534DEC9940B2D8366C8EF71DD536ED94BE7817D7C4E1E19BED05F6E60B8F7` equals the manifest archive hash; manifest SHA is `13C7CD6957E88BC4F035E7E727B6AF44313B14894AA4CA1B120DBED555C0EEA0`. Previously documented installed-image and execution observations remain in `guest-input-review.md` with their own time/package scope.

Representative direct chains include DOS `append/makefile` naming `append.obj: append.asm`, DEBUG makefile/link response enumerating object inputs for DEBUG.EXE, and historical Windows kernel makefile separating debug3/retail3 compilation. Exact recipe references are supplied per row; they do not prove a retained source generated the exact distributed guest binary. Candidate grouping is evidence for subsequent verification, not an automatic bulk decision: inspect actual active target/conditional and distinguish guest build inputs, shared headers/resources, historical test inputs and loaded runtime images. Mirror divergences remain partial, regardless of apparent guest role. The earlier `guest-build-carriers.md` separately covers OMF intermediate formats and its eight unresolved symbol files; this batch does not reclassify or duplicate those already-reviewed rows. No guest or product was modified, rebuilt or executed.
