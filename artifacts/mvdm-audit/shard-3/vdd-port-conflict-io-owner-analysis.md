# VDD conflict checking and IOS ownership

Read-only source analysis against current and byte-identical OpenNT `nt_vdd.c`/`ios.c`; the existing controlled fixture evidence is `vdd-port-conflict-static-review.md`. No new device operation or product/guest edit was made.

## Source facts

`ios.c:59–66` explicitly maintains separate input and output adapter maps, allowing two devices to share an address in different directions. `io_connect_port` writes only the requested `IO_READ` and/or `IO_WRITE` table but unconditionally returns TRUE in NTVDM. Callers such as `vga_prts.c` deliberately use direction-specific assignments and reconfigure ports; changing this shared primitive into a global first-owner check would change those other callers, many of which do not handle failure. VDD installs specifically pass `IO_READ_WRITE`, so a conflict in either relevant direction must be considered without treating an unrelated native device as automatically a conflicting VDD.

The mapping index is `io_address & (PC_IO_MEM_SIZE-1)`. In the selected NTVDM profile `ios.h:23–26` sets size to 0x10000, so 16-bit VDD ports do not alias one another. Non-NT profiles with size 0x400 do alias; do not generalize the NTVDM conclusion to them. `io_disconnect_port` compares both directional maps, but if either equals its adapter it clears **both** directions. A concurrent/different-direction owner can therefore be erased; this cannot be fixed by assuming one table represents both owners. The original uninstall comment says its default hook reads `0xff` and ignores writes, not that the prior native device mapping is automatically restored.

`nt_vdd.c:233–266` states first hook wins and returns `ERROR_ACCESS_DENIED` on a hooked port, while also stating a video-port hook may succeed without a guarantee its handler runs. It forbids VDD hooking DMA ports as usage guidance; it does not document a simple global `EMPTY_ADAPTOR` policy. Actual VDD slot ownership is tracked separately by `VddAdapter[0..6]`, whose selected adapter values are 36–42. The eighth named constant and precise scope of the first-owner claim vis-à-vis built-in device owners remain separate contract questions. Duplicate ranges in a single request currently succeed; no explicit original rule requires rejection.

## Bounded repair direction

Implement conflict control at the **VDD registration boundary**, not as a blanket change to `io_connect_port`: before publication, examine both actual IOS direction maps under the same serialization used by VDD registration/retirement, and reject a port owned by a different live VDD with `ERROR_ACCESS_DENIED`. Use the existing port maps and VDD adapter owner as authority, not a parallel independent ownership table. Treat repeated/overlapping portions of the same request consistently rather than causing self-conflict. Keep the documented video behavior and original native-device interactions until their exact expected semantics are traced; do not silently reject every nonempty IOS slot. If a conflict is found before modifying maps, the old mapping and allocated adapter state must remain unchanged; if publication can fail later, explicitly roll back only this request's changes.

Uninstall must clear each direction only if that direction still belongs to the uninstalling adapter, and must not release/reuse the adapter before its mappings are retired. This can be a VDD-specific operation; changing shared IOS disconnect behavior globally requires its own caller audit. A registration metadata lock alone is not a proof of safe callback/module retirement because CPU IN/OUT dispatch reads the tables directly; retain `vdd-io-concurrency-design-review.md` and `vdd-loader-quiescence-review.md` for the separate callback-lifetime requirement. Ensure the widened inclusive-loop fix covers install, rollback and deinstall through `0xffff` without introducing runtime timeouts.

Before product change, use the existing actual-object fixture to verify original owner A remains active and B gets `ERROR_ACCESS_DENIED` on first and later-range overlap, one-direction occupancy, duplicate/overlapping own ranges, 0xffff, video exception and native port interactions; check port tables, callbacks, slot counts, LastError and rollback. A deterministic concurrent registration and callback-in-flight test is separate. The correct policy for collisions with native devices, duplicate inputs and video reconfiguration is not fully established by the observed test and must not be guessed. No actual guest/VDD conflict or completed fix is claimed.
