# CPU 486 compile gates and selected CPU40 profile

The current T310 x86 product flags in `New-T310OriginalSoftpcNinja.ps1:743` and generated worker Ninja use `CPU_40_STYLE`, `CCPU`, `SPC386`, not `CPU_486` or `SPC486`. Original `base/ccpu386/sources` lists `bswap.c`, `cmpxchg.c`, `invd.c`, `invlpg.c`, `wbinvd.c`, `xadd.c`; graph selection thus compiles the files, not necessarily their guarded functions. Actual x86 `dumpbin /symbols` on all six selected objects shows no corresponding external definitions, and cached NTVDM map contains none. This is a static compiled-profile result, not real guest execution.

`c_main.c:166-173` includes those six headers only under `CPU_486`, while the implementation bodies and actual decoder `#ifdef`s use `SPC486`. In currently selected neither-defined configuration there is no inconsistency: 0F 01 /7 INVLPG, 0F 08 INVD, 0F 09 WBINVD, 0F B0/B1 CMPXCHG, 0F C0/C1 XADD and 0F C8–CF BSWAP take original `Int6()` #UD branches. If only `CPU_486` is enabled, declarations appear but bodies/decoder remain disabled. If only `SPC486` is enabled, calls and implementations are enabled but the corresponding guarded declarations are absent; whether a particular historical compiler accepts implicit declarations cannot establish a safe typed ABI. A future 486 build must select coherent declarations and bodies, not flip just one macro. Exact behavior for bad modRM, privilege/fault priority or live guest #UD has not been demonstrated by this static survey.

Original `obj.vdm/CDEFINE.INC` chooses `SPC386` for its non-386 CCPU setup and lists MONITOR/C_VID/X86GFX for 386; the retained `base/ccpu386/sources` includes both 386 and guarded 486 source files. Repository search for `#define CPU_486`, `#define SPC486`, `/D` or `-D` versions under src/tools/docs yielded no actual retained defining recipe. Consequently the original two-macro activation mechanism **is not established**; do not claim original NT4 config used either a proven paired switch or that CPU_40_STYLE itself means 486. `c_main.c` source SHA256 `A02368618BA57A1313E25F5C20B3B22D1C8D78A0E2CF215AC3E9036204D0FABC`; `cdefine.inc` `A5CC355BFAB633968217C85A4BB210F684039E08E7784578800C672F65772F14`; cached `c_main.obj` `6FF59175D530E65B489B2C1BACB93B7C5AC459E049FE75B28EC0372AFA1C5986`.

Finite recovery group, if 486 is admitted: (1) establish original macro provenance and typed compilation of both gates; (2) enable/test the six leaves and opcode dispatch together, including 16/32 variants and #UD/privilege negatives; (3) integrate SPC486-wide state dependencies (`c_reg` AC/CD/NW and control masks, `c_tlb` invalidation/paging, `c_seg`, `c_stack`, `c_bsic`, MOV and reset EDX component ID) and verify cache/TLB and CPU identification consistency; (4) test protected-mode/guest profiles and rollback without changing existing guest images. Original INVD/WBINVD bodies are intentionally empty with comments conditional on a cache implementation; this is not evidence that an arbitrary modern host cache can be ignored. No current modification or unconditional 486 capability claim follows from merely compiling empty objects. Current 386 profile and missing higher-CPU behavior are separate: retain the 486 source rows pending, not excluded.

This investigation used source, original recipes, current graph and object/map inspection; no product or guest changes and no guest test. Other external/generator repositories and original non-MVDM build environments were not searched, so no global nonexistence claim is made.
