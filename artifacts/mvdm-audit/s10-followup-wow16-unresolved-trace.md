# S10 WOW16 unresolved-row source/consumer trace

[CSV](s10-followup-wow16-unresolved-trace.csv) and its [reproducible observer](s10-followup-wow16-unresolved-trace.py) cover the 119 rows which lacked a direct recipe classification in [the prior follow-up](s10-followup-wow16-recipe-roles.md). Each row binds the present file SHA-256 to a source-description excerpt where available, local quoted include sites, possible host same-basename includes, a bounded role statement, and the owning functional stage. Each path, line and excerpt is an observed source fact; the S ownership is a handoff for the related behavior, not proof of execution or recovery.

The scan found all 119 rows with a source-role excerpt or declaration (113 from descriptions/markers and six from fallback declarations), 31 with at least one resolvable same-directory quoted include, and 35 with at least one host-side same-basename include. Host include names cannot prove the build resolved to this physical header; include-path order and profile must be established separately. The observer scans C/H files under `src` and resolves quoted includes relative to the including source; macro includes, configured include paths, indirect/generated consumers, other source languages, all historical build profiles, and actual runtime usage are outside its result. Lists in the CSV are capped, with total counts retained. Scope is per-file identity and behavior ownership, not exclusion from the product or a count of capabilities.

The 16/32 metafile quartet is especially important: `wow16/gdi/gdi16.h:12-27` explicitly states that its code is used by Win16 WOW and Win32 GDI and selects `WIN16`/`WIN32`; `meta.c`, `metarec.c`, and `metasup.c` include it locally. That establishes an original shared-design intention, not that either corresponding build is currently selected. GDI/metafile recovery remains S16, with WOW boundary work in S14 as appropriate. `wow16/inc/cmstrip.c` describes an assembler comment/text-stripper; its current tool ownership is not proven. `wow16/inc/dbcs.c` and its header describe DOS-app DBCS, without proof of the active consumer. DDEML dual-target tests and their headers are covered separately in the previous recipe CSV and do not become guest-only by location.

The remaining source-level classifications are deliberately bounded: a comment describes intended roles such as USER EDIT, communication, multimedia, OLE, RAS, printing and common-dialog declarations, but does not establish whether a guest, host, or alternate-build target actually uses that precise file. The CSV records these facts and the handoff, including rows with no usable description. S11-S17 must trace the selected owner for the corresponding functionality. Guest source remains unchanged; none of these observations authorizes guest rebuild, deletion, or treating a feature as out of scope. No shared ledger, product code, binary, or test was modified.
