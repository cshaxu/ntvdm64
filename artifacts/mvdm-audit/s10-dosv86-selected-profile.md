# S10 DOS/v86: per-file selected-host boundary

This refines [the previous owner review](s10-followup-dos-v86-ownership.md) with [38 per-file records](s10-dosv86-selected-profile.csv). It does not change source, guest, or shared ledgers. Each record is bound to its current source SHA-256 and checked against the earlier [guest-tree dependency observation](host-ch-scope/guest-tree-name-collision-evidence.json). All 38 source hashes match that observation; none occurs by exact physical path among its captured worker x86/x64, WOW32 x86 and isolated-package worker x86 Ninja dependencies. Their four `build.ninja` hashes still match the capture. Dependency output is a historical snapshot, not evidence that every current or alternate graph was compiled or that all external tools have been checked. In particular the worker Ninja log has since been rebuilt, so this report does not purport to regenerate that snapshot.

The same-name distinction matters: 48 lexical host `bios.h` inclusions do not establish use of the v86 header; the observed exact build dependency resolves to `softpc.new/base/inc/bios.h`. Recorded same-basename `version.h` dependencies resolve to `src/common/protocol/version.h`, not the DOS v86 path. The CSV retains counts and observed dependency paths for every row. Standard include files may come from compiler-installed paths not captured in Ninja dependency data; zero recorded matches is not proof of global non-use.

- Six `.c` files are original build helpers, not current NTVDM worker execution: COMMAND `buildmsg` and `buildidx`, `getsize`, `h2inc`, `stripdd`, `stripz`; original recipes and their callers are cited in the earlier owner review. Guest-build tooling and selected-profile physical exclusion are distinct from deleting original sources or any runtime behavior.
- Nine common headers and `cmd/mem/parse.h` have a concrete historical 16-bit MEM build relationship through `cmd/mem/makefile` and `make.inc`; physical-path resolution is supported by the original include paths. No claim is made that current installed MEM.EXE was built from them.
- The `usa-ms/bldmsg.h` locale header is not proven as the resolved header for compiling `buildmsg`: the source says `#include \"bldmsg.h\"` but no checked recipe compiles that source. It stays unresolved.
- The other 21 CRT/BIOS headers retain unresolved original consumer ownership; their missing captured host dependencies supports only a bounded physical nonselection observation. Do not classify guest-only or globally exclude them from the source tree on this evidence.

The distinction in the CSV between observed historical build role and captured current-host dependency is deliberate. DOS runtime behavior and guest-facing functionality remain assigned to S12; tool/debug scope remains with its planned stage. No guest was built or modified, no execution test performed, and no claim of behavior recovery follows from file hashes.
