# Original DOS absolute I/O and fdisk failure boundary

`dos/v86/doskrnl/dos/mscode.asm` routes INT 25h/26h through SVC_DEMABSDRD/SVC_DEMABSDWRT. Original DEM dispatch selects `demAbsRead`/`demAbsWrite`, which call `demAbsReadWrite` with direction; this obtains 16-bit register or extended DISKIO request fields and a BDS. The original `demDasdRead`/`demDasdWrite` performs volume/sector range checks, maps the guest buffer, and chooses `nt_fdisk_read/write` for non-removable media, or `nt_floppy_read/write` when original INT13 is installed, otherwise routes through guest BIOS disk I/O. Success compares sectors actually returned with requested; error translates the host last error. Guest DOS owns request ABI and DOS result, DEM owns BDS and conversion, backend owns the host device handle and physical I/O. Source presence, BDS registration and release image identity are independent evidence questions.

A specific source-level failure candidate exists in current `softpc.new/host/src/nt_fdisk.c::nt_fdisk_read`: after valid `fdisk_data` and current PDB, if `get_fdisk_handle(..., FALSE)` returns FALSE, control falls off a non-void function with no return. Both pinned originals have the same fallthrough. The helper can return FALSE when `CreateFile` fails or when the project-owned SCS counter update fails after closing the newly opened handle. The caller `demDasdRead` interprets the resulting unspecified ULONG as bytes read. This is a proven source control-flow gap, not a demonstrated guest failure, and is not evidence that direct user media should be opened. Also the original `StartSector + Sectors` range expression could wrap a DWORD if extreme inputs reach it; whether the selected guest, geometry and lower backend admit such values is unverified. Do not mark either item as a reproducing bug or silently alter original semantics.

The historical `t230_s7_demdasd_ioctl_direct_import_fixture.c` uses an archived copied boundary and verifies no-registered-BDS failure, not a current linked product open-failure branch. The separate `contained_media_fdisk_test.c` configures a disposable image through a runner-only media boundary, checks successful write/read, out-of-range read, and cleanup; it does not exercise `get_fdisk_handle` failure in the actual worker. Neither fixture establishes failure return or last-error preservation in the current production chain. Product-map evidence for entry functions is recorded in `shard-2/parallel-review-current.md` and is image-version-specific.

A finite follow-up can use only a disposable test image and a seam targeting handle-open or SCS publication failure, record returned byte count plus GetLastError, DEM sectors/CF/AX, cleanup and a subsequent successful I/O; then verify actual reached guest entry and package hashes. Keep this candidate separate from independent partial-feature evidence and obtain appropriate review before changing a mirrored original file. `dem-absolute-io-observer.py` records current/original source and both fixture hashes; no test, product, guest, disk or ledger changed.
