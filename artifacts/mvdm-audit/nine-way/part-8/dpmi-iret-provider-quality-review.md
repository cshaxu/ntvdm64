# DPMI IRET hook provider classification

Physical shard 2 records `dpmi32/i386/dpmimisc.c` excluded. Its current bytes match both original editions (SHA256 `C4B46844E5D5CD8A0D26A20F8635E46F58A53CCE768AEAD3A472300D773FB8F5`): this is not an original mirror diff. The original i386 manifest `dpmi32/sources:56` selects it, and its two exported handlers `DpmiDpmiInUse` and `DpmiDpmiNoLongerInUse` are empty. This is the original x86 native-VDM profile, not proof that all guest IRET behavior is unneeded.

The current CPU40 build graph compiles `dpmi32/dpmimscr.c` and includes its object in `original-mvdm-dpmi32.lib`; the generator explicitly adds this RISC-derived provider. The actual dispatch table slots 0Ch and 0Dh refer to the same handler names, and the selected implementation respectively enables and disables emulator IRET and interrupt hooks. Therefore the two providers are intentionally not source- or operation-equivalent: CPU40 needs emulation state that the original hardware-oriented x86 empty handlers did not. `dpmi32/dpmimscr.c` has registered project adaptation and is separately partial; excluding an individual historical provider as an unselected file role cannot mean the guest DPMI operation is excluded, or that lifecycle equivalence is proven.

Recommended coordinator disposition: keep `dpmimisc.c` at most as an *unselected historical provider role* if the ledger explicitly preserves its original profile and the chosen emulator provider; otherwise pending until that distinction is represented. This review does not assert that original NT kernel behavior and CCPU are equivalent. In particular verify nested clients, hook activation/deactivation balance, protected-to-real transitions, task exit and failures against the selected provider; build graph and dispatch source do not establish current-image linkage or execution. Existing `shard-0/fast-bop-selector-lifetime-audit.md` and `shard-3/fastwow-comparative-audit.md` discuss related fast-BOP boundaries but are not proof of all hook lifecycle.

`dpmi-iret-provider-quality-observer.py` records hashes of both original and current provider, dispatcher, manifests and observed build graph in `dpmi-iret-provider-quality-evidence.json`. Static only; no product, guest, build or shared ledger change.
