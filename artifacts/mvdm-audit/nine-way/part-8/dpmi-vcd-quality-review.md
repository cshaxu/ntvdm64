# DPMI virtual COM service classification quality review

`dpmi32/vxd.c` is currently partial (physical shard 2), correctly so under the mirror-byte rule: current SHA-256 is `240AF56E0A6644E1E4465BE781858FB7BBBE581AD062B7B62ED0BCA7F3436C22`, while both original editions hash to `C42DB46A3E7F985B83988668778613BA497B0A940F2AEF4E0A2E082E54D8DD3A`. Splitting source bytes on line boundaries yields identical lines; the byte difference is line ending representation, not a demonstrated algorithm change. Canonical code-line retention is 68/68, 100%; this does not establish full function correctness or execution.

The historical guest route `dpmi/486/dxfunc.asm::VCD_PM_Svc_Call` issues BOP 53:12; `dpmi32/dpmi32.c` dispatch entry 12 calls original `DpmiVcdPmSvcCall32`. The function returns version 030Ah or calls `VcdPmGetPortArray`, which enumerates host `HKLM/HARDWARE/DEVICEMAP/SERIALCOMM`, converts numeric suffixes and masks to nine ports; unsupported calls set carry (and hit an ASSERT in builds where enabled). Registry data and port presence are host-owned; guest ABI and service selection are original behavior. The current formal x86 Ninja graph compiles `vxd.c` to `obj/dpmi/vxd.obj` and includes that object in `original-mvdm-dpmi32.lib`. This graph does not independently prove exact extraction into the currently published image or the identity of historical test binaries.

Existing T420 S38 evidence `docs/etc/evidence/m0-t420-s38-dpmi32-capability-review.md` records an actual DPMI guest probe on direct and twice-nested routes, with version, bounded nine-bit port result and unsupported-call refusal. The report records a tested worker SHA and the probe source; it does not establish actual physical COM transmission, exact agreement of host serial registry with returned bits, malformed registry values, concurrent registry changes, or current-release package equivalence. The probe can only establish the bounded assertions as documented; host session/retirement and external device failures remain separate acceptance work. The original implementation converts a registry value and shifts by its converted port number; out-of-range or malformed values are a source-level robustness question and not a demonstrated failure. Do not replace the original behavior based on this observation alone.

`dpmi-vcd-quality-observer.py` reproduces SHA-256 for both original sources, current source, dispatcher, DOSX source, probe, historical evidence and captured Ninja graph in `dpmi-vcd-quality-evidence.json`. Static review only: no build, guest/product execution or shared ledger change. Prior DPMI context and other exception-lifecycle gaps remain separately documented in `shard-2/dpmi-exception-mode-xmem-review.md`.
