# DOS delete, chmod and rename: original path ownership

The original NTDOS `file.asm` emits separate `SVC_DEMCHMOD`, `SVC_DEMDELETE` and `SVC_DEMRENAME`; `demdisp.c` routes those services to original bodies in `demfile.c`. For these three bodies the current code still obtains synchronous guest paths through `GetVDMAddr`; attribute operations, deletion and rename pass those paths to the original OEM-to-Unicode wrappers. Rename first checks different drive letters (DOS error 11h) and same source/destination (DOS error 5), and otherwise delegates to `MoveFileOem`. OEM wrappers use RTL OEM conversion before Win32 `GetFileAttributesW`/`SetFileAttributesW`, `DeleteFileW` or `MoveFileExW`, returning errors via the original DEM client error path. NTDOS owns DOS operation ordering and errors; DEM owns conversion of guest registers; OEMUNI owns OEM conversion; Windows owns filesystem resources. File paths are guest pointers, not host-owned persistent state.

By contrast `demOpen`/`demCreateCommon` have separately registered bounded guest path-copy adaptations; do not describe these three unchanged synchronous bodies as using those lease/copy paths. The surviving original pointers, possible reentry, NUL bounds and guest-memory lifetime deserve direct applicable-caller review, but a vulnerability or regression is not established without showing reachability and failure under the actual guest/host memory contract. Do not replace original control flow merely because these calls differ from open/create.

T404 S5 `m0-t404-s5-dem-chmod-ingress-correction-001.md` records a temporary diagnostic worker SHA and a real NTDOS `50:01` chmod ingress during a positional WRITE startup. Its NTDOS map/source address and service identify ingress, but the run timed out before WOW startup and did not establish returned attributes, delete/rename behavior, failure cleanup or current-release identity. Prior code/image binding and partial status are separately documented in `shard-2/dem-initialization-dispatch-file-review.md`; nothing here upgrades the status. Finite evidence gaps are actual guest success/error results for delete, chmod and rename, OEM conversion failure and same/different-drive cases, plus valid/invalid guest path boundaries, potential reentry and task teardown on the current package. Use disposable files and immutable guest input if later admitted.
