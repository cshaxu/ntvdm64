# Part 7 multimedia driver provider selection

Owned `wow16/mmsystem/drvr.c`, `drvrrare.c` and `drvrstr.c` describe the legacy C driver table; do not infer that they back the selected WOW16 multimedia DLL. Original `wow16/mmsystem/makefile:12-18` lists `drvr31.obj` in OBJ3 and does not list the three owned C objects. `drvr31.asm:136-190` implements DrvClose / DrvGetModuleHandle / DrvSendMessage / DrvDefDriverProc as direct jumps to Windows driver APIs. By contrast, `drvr.c:70-137` locks the installed driver table around callback dispatch and `drvrrare.c:237-288` sends DRV_CLOSE and frees only after a successful result; `drvrrare.c:598-646` has its own `fUseWinAPI` branch. The latter semantics belong to this historical C implementation and must not be asserted as the behavior of the listed drvr31 selection.

`assets/winnt-guest-manifest.json:399-402` identifies packaged MMSYSTEM.DLL as a retained NE image. A historical recipe is evidence of intended build, not evidence of matching binary provenance or actual driver callbacks. Existing `tests/adapter-mvdm-host-out/wow/wow_multimedia_inventory_fixture.c` explicitly validates only public host WINMM inventory/capabilities and no-device behavior, not 16-bit driver loading, callback ordering, failure rollback, nested callbacks or unload. Original debug and alternative build configurations remain separate pending cases.

Suggested classification for the three owned C files: historical alternative driver-management implementation present in source; current package applicability and all behavioral conclusions pending image/call proof. Do not remove them or classify an entire multimedia facility as complete based on this recipe. No guest/product modifications or runtime test performed.
