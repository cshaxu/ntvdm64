# MMTASK task-stub and package candidate

Owned `wow16/mmsystem/mmtask.tsk`, `mmtask/mmtask.asm`, `mmtask/MMTASK.TSK`, `mmtask/MMTASK.RES`, and `messages/usa/mmtask.rcv` are related original guest build and binary artifacts. Original `mmsystem/makefile:90-108,125-128` builds and binplaces the stub beside MMSYSTEM; `mmsystem/task.c:73-115` loads IDS_TASKSTUB then passes a callback/instance structure to BWinExec. `mmsystem.rc:190` maps the resource to `mmtask.tsk`. The stub `mmtask.asm:150-233` copies the command payload before InitTask, initializes a queue, consumes the initial event, and invokes the passed callback before exit. Its task/queue ownership and callback execution are guest behavior, not host WINMM enumeration.

`mmtask-observer.py` prints JSON to stdout with exact retained stub and MMSYSTEM NE SHA, and inspected ZIP / install paths. Both owned copies of the retained task have SHA `76d14010567c7b8fdfbbfed716819b32622977768ab4b14b354ce2471172a2db`. The inspected ZIP contains the matching retained MMSYSTEM.DLL but no entry with the MMTASK.TSK basename. The exact `assets/release` and `O:/winnt/system32` candidate paths are absent. A guest might obtain a stub elsewhere in its executable search paths; source and identical retained MMSYSTEM image do not prove that the NE contains or calls the source routine. Thus missing package file is a concrete candidate, not a proven mmTaskCreate runtime failure.

Classification: both TSK files are identical preserved prebuilt guest task images, assembly and resource are original guest build inputs; their actual deployment and mmTaskCreate task lifecycle remain pending. Targeted verification requires finding the effective guest search path and calling mmTaskCreate with an observable callback and clean return/failure (no new guest build). Current multimedia public-host fixture does not exercise that path.
