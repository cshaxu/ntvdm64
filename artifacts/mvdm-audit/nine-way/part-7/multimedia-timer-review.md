# Original MMSYSTEM timer provider: selected recipe versus alternative asm

Owned `wow16/mmsystem/timea.asm` contains a `timeBeginPeriod` wrapper that clamps periods below 6 ms and direct 32-bit thunk code. The original `mmsystem/makefile:12-18,183,253` lists `time.obj` built from `time.c`, not `timea.obj`; do not attribute that asm clamp to the selected recipe merely because the source is retained. For the listed source route `time.c:378-383` implements timeGetTime through `timeMessage(TDD_GETSYSTEMTIME)`; `stack.asm:1051-1094` initializes the bridge if needed and invokes MMCALLPROC32 with `tid32Message`. `init.c:73-80,613-634` selects host `winmm.dll` and looks up the timer and other multimedia message endpoints.

On this machine `objdump -p C:/Windows/SysWOW64/winmm.dll` lists `tid32Message`, the MIDI, waveform, auxiliary, MCI message names and NotifyCallbackData. This is only PE export presence, not a behavioral or image-loading proof. `tests/adapter-mvdm-host-out/wow/wow_multimedia_inventory_fixture.c` checks public timeGetDevCaps and several host enumeration functions; it explicitly does not run guest callbacks, timer create/cancel, timing resolution or teardown. The packaged MMSYSTEM.DLL identity is tracked in `mmtask-evidence.json`, but its source build provenance is not proved.

Suggested classification: `timea.asm` retained alternative original guest implementation, not shown as an input by this specific recipe; selected source-level timer route retains distinct guest, thunk and host ownership. Actual loaded NE and winmm identity, per-task timer cancellation, race during guest destruction and timeBeginPeriod matching remain unvalidated; no guest change or runtime test.
