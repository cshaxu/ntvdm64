# Part 3: CPU/C-VID source identity and selection

`softpc-owned-observations.json` records all 34 owned SoftPC keys with SHA-256 for current and both original trees, per-key textual include candidates, and normalized source-path hits in the on-disk x86 formal Ninja graph. Reproduce with `python artifacts/mvdm-audit/nine-way/part-3/softpc-owned-observer.py`. All 34 files are byte-identical to both originals. This doesn't prove the graph is the deployed binary or that textual includes resolve to these exact copies.

The six instruction pairs have a separate review (`ccpu-instructions-role-review.md`). `ccpu386/c-files` is the original list of instruction/CPU files; `ccpudefs.inc` and the generated-surface headers `evid_c.h`, `evidfunc.h`, `evidgen.h`, `gdpvar.h`, `pigger_c.h`, `univer_c.h` are individually inventoried in the JSON; include hits are candidates, not all active preprocessing branches. `ccpu386/stubs.c` supplies historical production CCPU debug stubs and has an object edge at line 204 of the inspected graph; actual extraction and calls require separate proof. `ntstubs.c` has no edge in that graph, and `vglob.c` is an alternate GDP carrier: prior package audit `docs/etc/evidence/m0-t420-s1-ccpu386-package-audit.md` explains duplicate CPU/FPU/SAS or GDP ownership and retains only the needed separately composed leaf. Neither is a reason to delete supported functionality.

The separate historical `cpu/src/evid/ev_glue.c` explicitly provides C-E-vid/Jcode glue, includes the generated interfaces and declares video-vector state. It must not be confused with the selected `cvidc/ev_glue.c`; this exact path has no source edge in the inspected graph. Its other-build role and any historical release identity remain unverified. The owned `cvidc/acc_efi.h` is a table of access-selector entries, `access_c.h`, `adjust_c.h`, `axphst_c.h`, `bldr_c.h`, `bodge_c.h`, `bpi_c.h`, and `buffer_c.h` are corresponding declaration/generated interface inputs, and `c2cpusad.h` identifies itself as generated. `cvidc/ccpudefs.inc` is a separate path from its same-named CCPU counterpart. No direct include was found for most of these headers using the bounded source scan; generated builds, indirect use and alternate profiles remain unverified, so no absence-based blanket exclusion is justified.

Per-key conservative suggestion: retain the original source role and separately verify active generated/dependency path and final-image binding where required. Existing C-VID selection and vector-composition context is in `docs/etc/evidence/m0-t420-s2-cvidc-package-recovery.md`. No CPU instruction, video operation, failure, concurrent lifecycle or release-binary execution was run here; no restoration percentage is inferred.
