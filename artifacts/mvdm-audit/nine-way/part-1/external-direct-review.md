# Part 1 external: native DirectDraw/blit provider family

Exactly 209 assigned OpenNT-4.5 external keys under `ntgdi/direct/` are recorded per-key in `external-direct-evidence.json` with source path, SHA-256, size, provisional file role, four normalized VALID graph checks and ZIP basename observation. Replay `PYTHONDONTWRITEBYTECODE=1 python -B artifacts/mvdm-audit/nine-way/part-1/external-direct-observer.py`. All sources exist; 48 code, 50 header/include and 111 resource/build/data candidates by extension, with 59 blitlib, 56 ddraw, 29 ddapps, 22 ddhel, 16 inc, 15 ddhelp and remaining misc/dirs records. Their provisional file roles are not proof of semantic irrelevance; every key remains `pending-specific-provider-semantics`.

Original `direct/dirs` selects blitlib, ddhel, ddhelp, misc and ddraw and makes ddapps optional. These are native host graphics components rather than guest VGA hardware implementation. A bounded exact-pattern text search for DirectDraw/IDirectDraw and ddraw.h in current wow32, wow16 and ntcon C/H/ASM sources found no direct API references. That does not rule out dynamically loaded APIs, other code, guest applications, native graphics internals or observable effects. The separate WOW GDI wrappers and SoftPC framebuffer/Video7 owner must be checked for concrete overlapping behavior, not assumed equivalent from common drawing terminology.

No exact files occur in the four current VALID dependency sets and none has a ZIP basename match. Neither proves the actual host desktop provider, COM registration, surface management, clipping, timing, synchronization or Win16 application behavior. Check a specific consumer/provider, version/architecture and lifetime before deciding each key; do not categorically exclude the family or import it wholesale. No product, guest, graphics provider or external source was run or modified; shared ledger and build tree were untouched.
