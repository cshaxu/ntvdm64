# Other physical shards: explicit guest-input-only exclusions

`other-guest-excluded-scope-observer.py` joins the `fb85f484c` snapshot of `combined-initial-status.csv` against the same snapshot of `shard-0/review.csv`, `shard-2/file-audit.csv`, and `shard-3/file-review.csv`. It selects only rows whose initial aggregate says excluded, whose corresponding current shard decision still says excluded, and whose exact basis positively limits the finding to original guest build/input, guest declaration, or exclusion from current host implementation while saying guest functionality and/or image provenance remain open. It emits one row per exact path and preserves the finding, original evidence and remaining-evidence columns; captured stdout is `other-guest-excluded-scope-evidence.json`. Counts: shard 0 = 216, shard 2 = 190, shard 3 = 158 (564 total).

Examples include `dos/v86/cmd/command/command2.asm`, `dos/v86/dev/himem/himem.asm`, and `dos/v86/cmd/debug/debasm.asm`. These are not claims that the current packaged guest is built from those exact sources or that a particular functionality has passed. Their scoped historical build/input classification should remain visible. If the coordinator's aggregate excluded state means an overall adjudication, these exact 564 need pending overall until real owner/guest applicability is settled; if a distinct field faithfully records a host-input-only exclusion while independently retaining capability, preserve that field without reclassifying capability. Do not interpret the simple aggregate count as proof of feature absence.

Shard 0 rows already changed away from `excluded` in the current shard CSV are deliberately omitted, even if the old combined initial snapshot still says excluded. This conservative predicate also omits historical object files, listings, recipes, vague bases and unrelated excluded categories; it does not prove those are all valid. No guest, product, build tree or shared ledger was modified; no execution tests were run.
