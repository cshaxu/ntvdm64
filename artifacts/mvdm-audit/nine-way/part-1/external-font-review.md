# Part 1 external: font driver and font-data family

The 436 assigned OpenNT-4.5 external keys under `ntgdi/fondrv/` and `ntgdi/fonts/` are individually recorded in `external-font-evidence.json`: key, original path and SHA-256, size, provisional role, exact normalized VALID dependencies for four current host graphs, and ZIP basename observations. Replay `PYTHONDONTWRITEBYTECODE=1 python -B artifacts/mvdm-audit/nine-way/part-1/external-font-observer.py`. All source files exist; 45 are source-code candidates, 45 headers/includes and 346 font/resource/build/data candidates. Every key retains `pending-specific-provider-semantics`; identical path-family membership is not evidence fonts, glyph metrics, encodings or drivers are interchangeable.

There is one direct packaged-data match: `SRC:0e87b2e6fc2615658f92`, `nt/private/ntos/w32/ntgdi/fonts/ega.cpi`, original SHA-256 `30f809477737650b3005ea1efd3bbd44de439891036db000372f63a6c0b1fe7a`, equals ZIP `WINNT/SYSTEM32/EGA.CPI` and exact installed `O:/winnt/system32/EGA.CPI`. `softpc.new/host/src/nt_fulsc.c:357-372` describes and implements LoadCPIFont, called at line 320, and the worker graph compiles nt_fulsc.obj. However, a search of the current NTVDM map found no LoadCPIFont or loadNativeBIOSfont symbol; a compiled object and equal resource do not prove the selected release executes that path. Actual codepage-dependent font selection, resource ownership, error and teardown need dedicated evidence. This key must not be blanket classified as external and irrelevant.

WOW32 `wgfont.c` performs original font creation, handle mapping and callbacks around modern Windows font/GDI APIs. The OS owns real font provider/resources; project code owns guest conversion and callback boundaries. Existing `shard-2/wow-gdi-text-font-metafile-review.md` binds selected font thunks to the built map but explicitly leaves enum callbacks and formatting behavior pending. The exact external paths have no hits in the four observed VALID dependency sets; all except EGA.CPI lack ZIP basename matches. These are not proofs about current installed system fonts, alternate guest codepages, localized/bitmap fonts, DPI, rasterization, dynamic font selection or exact original provider equivalence. Original `font` resources and `fondrv` code can be independently relevant to a named guest font or model, so per-key actual use must be resolved before disposition.

No guest, font provider, product or external program was executed or modified; no shared ledger, user fonts, guest media or build tree changed.

## EGA.CPI conditional path

`nt_fulsc.c:318-321` attempts LoadCPIFont only if `sc.Registered` is true and `GetConsoleOutputCP()` is not 437; unregistered, codepage 437 or load failure takes the BIOS-font fallback. `LoadCPIFont` resolves CPI_FILENAME by appending it to `NtvdmGetSystemDirectoryA` and opens it read-only (`nt_fulsc.c:383-401`). Therefore the equal packaged CPI is not necessarily accessed on default codepage 437. The release-image map did not expose the function in the observed build, and actual installed execution remains unproven; the source condition and file hash are not a live-access witness.
