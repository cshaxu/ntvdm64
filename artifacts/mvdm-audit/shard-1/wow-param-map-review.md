# Shard 1: WOW parameter-map identity and lifecycle bindings

`wow32/wparam.c` has a registered project difference from original OpenNT (the current diff against the primary copy is 26 inserted lines and one deleted line); both original editions and current bytes are independently bound to the frozen reconciliation hashes. The original linked-list/refcount/cache architecture remains, with `MVDM-HOST-DIV-347` adding NULL-map rejection, refresh failure handling and rollback of a pinned reference on failure or abnormal termination. This is not an exact-source restoration claim.

The observer binds nine map-visible functions in the selected object to the release WOW32 image and resolves these actual caller edges: `W32Init` → `InitParamMap`; `WowOriginalFreeTask` → `FreeParamMap`; and `WU32SetWindowText` → `AddParamMap` and `DeleteParamMap`. Hashes and call offsets are in the JSON. The source shows an original per-worker cache/list, task ID retained on each node, reference increments for an existing mapping, up to 16 saved native-address aliases, per-borrow deletion and residual task-scoped purge. Heap/cache initialization is not a per-task lifecycle owner. `MAPPARAM_EXTRA` is source-disabled and is not newly claimed as a capability.

T447 S4's `m0-t447-s4-message-source-audit.md:6360–6380` records the rationale for the DIV-347 source changes and distinguishes an acquired per-call borrow from task-exit residual cleanup. It also flags segment refresh as potentially reentrant and preserves the 16-alias original policy. This report's current image checks extend static binding only: the older evidence must be consulted for individual fixture identity and cannot automatically prove the present image's live callback behavior.

No fresh runtime test demonstrates same-pointer overlapping borrows, alias eviction, nesting, rollback after segment fault, task death while another task uses an alias, cache fallback or failure behavior. In particular a source-level task-owner cleanup call is not proof all normally borrowed nodes have been retired or that another task's live state survives a forced termination. Preserve those as explicit execution/lifecycle obligations; do not create a second owner based on this review.
