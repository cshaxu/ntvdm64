# WOW mapped-file cache flush tail witness

`wkfileio.c:714-733` loops only while `pCache->hpfNext != 0`, so it never handles the tail. Original `InitMapFileCache` builds 11 list entries (the static array has 12 slots); `AllocMapFileCache` can populate that last list entry. The same tail condition is present in the OpenNT reference. `WK32FileRead` invokes flush after cache traffic thresholds (`wkfileio.c:532-537`), and `WK32WowFailedExec` also invokes it (`wkman.c:2539`). A skipped entry can retain its state and owned mapping until another cleanup path; this static/fixture evidence does not establish a process-lifetime leak or real user-visible failure.

`wow-file-cache-flush-fixture.py` extracts and hashes the actual current cache init, find, alloc, free, mapping and flush functions, compiles them with mocked Win32 boundaries, fills all 11 slots, calls real FlushMapFileCaches, and confirms one occupied tail remains. The file also repeats the separate MapView failure/handle-reuse and normal controls. It does not use an actual file, mapping or guest. The x86 current object section 15 for FlushMapFileCaches is fully matched after relocation masking in both current built and installed WOW32.DLL at PE file offset 0x181a0; exact identities and relocation evidence are in `wow-file-cache-flush-image-evidence.json`, reproduced by `wow-file-cache-flush-image-observer.py`.

Needed before assigning a fix: verify cache ownership contract and original intent, exercise actual mapped handles and file positions through valid guest operations, and assess correct cleanup and entry order under reentrancy. A change to include the tail should also re-check the list reorder performed by FindMapFileCache during cleanup and original behavior. No production failure, host-handle leak, guest regression, source change or default release is claimed.
