# Shard 1: CCPU stack support and interrupt callers

`softpc.new/base/ccpu386/c_stack.c` matches both frozen original sources. The observer binds all 13 map-visible release functions to their selected `c_stack.obj` bodies. It also binds `do_intrupt` and resolves all 22 interrupt-site machine-code calls to `spush`, `spush16`, `validate_stack_space` or `validate_new_stack_space`. Exact inputs, addresses and call offsets are recorded in the companion JSON. This is stronger than an owner-name match but does not execute a guest or prove that any single branch is taken.

Original stack bookkeeping separates SS stack-address size from instruction operand size: `byte_change_SP` selects SP or ESP from the SS B bit, while `spush` adjusts/writes 2 or 4 bytes according to operand size. `spush16` with a 32-bit operand reserves four bytes but writes only the low word; the other two bytes are not implicitly zeroed. `spop` reads the operand width and then advances SP/ESP. The source explicitly requires callers to complete stack checking before push/pop; the interrupt entry has its own current-stack and changed-stack validation calls. Successful and failing return ownership must therefore be judged across the caller, validation, memory access and exception paths rather than from these helpers alone.

The earlier `ccpu-stack-instruction-audit.md` records a controlled instruction-level fixture with stubs and explicitly says it does not test the actual stack provider. No new runtime or failure test has been made. Remaining boundaries include expand-down limits, 16-bit wrap, page faults after validation, fault ordering, privilege and task transitions, nested exceptions, interrupted memory writes and IRET restoration. Bindings do not prove these behaviors or establish general stack correctness; retain them in S11's runtime obligations.
