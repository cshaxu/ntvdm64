# XCHG selected header and real decoder contract — shard 1

Only `softpc.new/base/ccpu386/xchg.h` belongs to shard 1 among the NOT/LEA/XCHG/JCXZ .c/.h family. Its actual and both frozen original edition SHA-256 values are `B12F6F0AB67CE7A232459BE61A8B379D4387CD144470353685663A1F8BBA6386`. Its entire non-comment content is `IMPORT VOID XCHG IPT2(IU32 *, pop1, IU32 *, pop2);`, no second API. Under selected ANSI profile this is `extern void XCHG(unsigned long *, unsigned long *)`; CCPU Ninja flags have no alternate x86 calling-convention switch, so ordinary C uses __cdecl. Both `obj/ccpu/c_main.obj` and `obj/ccpu/xchg.obj` have VALID dependency edges on this exact header in `carrier-dependency-edges.csv`.

The original selected leaf `xchg.c` exchanges two dereferenced IU32 values and accesses no flags. Its valid C contract requires both pointers to designate accessible IU32 objects for the duration; same-address alias leaves the value unchanged. The actual decoder passes two distinct scratch operand fields (`ops[0].sng`, `ops[1].sng`), not direct guest pointers. This is a full 32-bit swap; width normalization and masked register/memory writeback belong to caller.

`c_main.c` cases 86 and 87 select 8-bit and operand-size-selected 16/32-bit forms. They decode E as RW/PG_W and G as register, fetch both before `XCHG`, then put E and G. Cases 91..97 select AX/EAX versus encoded register with operand-size-selected 16/32 fetch/writeback; 90 is handled as NOP. Address calculation, guest memory faults/access rights, E/G aliases, prefixes, cross-thread atomicity, and exception ordering are decoder/memory subsystem behavior; this leaf alone cannot certify them. Guest-visible register aliases require testing even though the scratch pointers are distinct.

For full classification of this one declaration, the pending leaf evidence must establish the published image body and actual decoder target (including all 86/87 and 91..97 references) against the selected object, plus guest execution of each used width and representative E-register, E-memory and accumulator-register forms. Check both values exchanged, preservation of unaffected upper bits/adjacent bytes, same-register alias, and unchanged flags; cover distinct initial values and boundary/large sampled operands. Negative image/oracle control must demonstrably fail. Full is limited to the header declaration and helper's valid contract; it cannot establish all ISA decode, protected-mode fault, lock/atomicity or lifecycle behavior. Follow-up evidence: `../ccpu-transfer-guest.json` records normal guest pass (3,276,800 group checks) and a deliberately wrong NOT expectation rejected; `../ccpu-transfer-image.json` matches the full 19-byte XCHG leaf and five actual decoder references to its matching body. The guest records this exact xchg.h hash and covers register, aligned/unaligned memory, aliases, flags and width sentinels. This is sufficient for full/100 for the declaration contract alone. NOT-only negative control is a group harness control, not an XCHG-specific corrupted oracle. No new build or guest test is performed during this independent review.
