# Shard 1: WOW virtual-memory thunk and original allocator

## Proven image and ownership

`wow32/wkmem.c` matches both frozen original source copies. The observer binds the object bodies of `WK32VirtualAlloc`, `WK32VirtualFree`, and `WK32GlobalMemoryStatus` to the release WOW32 executable code and resolves their actual image relocations. The alloc/free calls resolve to NTVDM executable imports; the current worker link map names original `nt_mem.obj` as provider. The KERNEL dispatch table declares VirtualAlloc at 233, VirtualFree at 234, and GlobalMemoryStatus at 237. Image binding does not by itself prove actual guest invocation, the current NTVDM release matches this worker map, or behavior.

For the compiled non-`i386` branch, allocate calls `VdmAllocateVirtualMemory` with commit enabled. Only `STATUS_NOT_IMPLEMENTED` uses native `VirtualAlloc`; other failures return NULL. Free applies the analogous fallback policy. Original `nt_mem.c` owns guest-linear chunks, 4K rounding, host commit/decommit and header accounting. The guest retains its arena bookkeeping; host memory status is forwarded to `GlobalMemoryStatus`. Historical evidence `docs/etc/evidence/m0-t452-s1-modules-memory-alias-source-matrix.md` records earlier allocator tests and explicitly limited coverage; it is not fresh failure-path proof.

## Failure-path candidates requiring adjudication

1. `src/mvdm/softpc.new/host/src/nt_mem.c:586` and `:787` contain `headerPtr->flags & HDR_VALID_ALLOC != HDR_VALID_ALLOC`. C parses equality before bitwise AND, so the flag expression is `flags & (HDR_VALID_ALLOC != HDR_VALID_ALLOC)`, i.e. zero. The surrounding page-alignment condition remains active, but the intended valid/allocated flag check cannot reject an aligned invalid or already-freed entry. This is a source-level defect in the original selected provider; actual call reachability, allocator consequences and test identities remain to be established before asserting a runtime regression or choosing a correction.
2. In `VdmAllocateVirtualMemory`, the header is marked allocated and may be split before host page commit; `STATUS_NOT_COMMITTED` returns before visible undo and before `totalFree` changes (`nt_mem.c:417–455`). This is a concrete failure-path consistency concern, contingent on commit failure and surrounding allocator invariants. No injected failure or resulting observable corruption has been demonstrated here. Free likewise calls `sas_overwrite_memory` before attempting host decommit; the effect of decommit failure needs separate assessment, not an assumed defect.

These are not grounds to replace the original allocator or declare all WOW memory paths broken. Suggested finite follow-up: verify actual released NTVDM image binding, review all callers and initialized header bounds, then exercise aligned invalid/repeated free and controlled commit failure with the original selected provider in an isolated fixture. Distinguish an existing original defect from a project integration regression; follow the project's exception policy if modification is warranted.

## Follow-up: caller constraints and existing evidence

`HDR_VALID_FLAG=1`, `HDR_ALLOC_FLAG=2`, and `HDR_VALID_ALLOC=3` (`nt_mem.c:70–77`). `ADDRESS_TO_HEADER` computes a page-indexed header pointer without a local bounds check (`:112–113`). Free checks page alignment, the ineffective flag expression, the first (real-mode) header, and the remap flag; there is no preceding allocation-identity check in `WK32VirtualFree`, which forwards the address from the guest frame (`wkmem.c:92–119`). The original WOW guest arena `kernel31/3gcompac.asm:1252–1275` normally passes the saved `pga_lrunext` for an arena block it has unlinked. Thus the normal documented caller supplies its owned address; source inspection alone does not establish that a correct guest can pass a stale or arbitrary address.

Reallocate first requires `HDR_COMMITTED_FLAG` before its alignment and ineffective allocation-flag test (`nt_mem.c:770–790`), narrowing its candidate path. The source caller in `dpmi32/dpmimemr.c:188` is bypassed in the selected `CPU_40_STYLE` configuration: that branch calls `SAReallocate` and returns before reaching the VDM allocator (`:177–185`, registered `MVDM-HOST-DIV-224`). `VdmReallocateVirtualMemory` is not exported by the current CPU40 host (see `shard-1/export-template-profile-review.md`), but the existing direct host fixture exercises valid grow/shrink. No production direct caller was found in the audited `src` tree beyond the bypassed DPMI caller and internal declaration, so do not assert a reachable product realloc defect.

`tests/mvdm-host/original_external_memory_test.c:174–188` checks a valid direct allocation, resize and free; it does not check invalid or repeated free or a forced host-commit failure. The T452 S1 matrix says invalid/repeated free projects false, while its delivery receipt only identifies the direct valid allocator-pair fixture; this does not establish that the actual `nt_mem` provider was tested for those negative cases. Shard 2's `suballoc-xms-callback-failure-review.md` independently records XMS commit/decommit failure behavior; that is a distinct suballocator route and does not prove this header issue. A search of the current policy/operations and audit exception records found no specific registration for the ineffective flag check; `nt_mem.c` has other registered source divergences, so this observation must not be represented as an undocumented project-authored change.
