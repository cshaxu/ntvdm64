`guest-source-owner-review.csv` accounts for all 408 still-pending source/declaration/resource rows in the shard's prior immutable-guest cohort: 309 source/declaration, 99 resource/support. Each row retains frozen and freshly verified current SHA-256, family, existing original recipe ancestry and exact filename references, four-target host input observations, package identity matches and explicit remaining boundary. Source universe SHA-256: `F73FFD45DFF44FCA4ECEFC49EF769BEAB5C085542CD04FFE4D6A7B5F942E3196`. No row here matches the prior package-c whole-file hash inventory; that does not establish the original guest functionality is absent.

Thirteen candidate classifications have additional original recipe and original bytes independently checked: twelve COMMAND source/message dependencies and APPEND's `append.skl`. Original `command/makefile` builds and links named object dependencies into `command.exc` then relocates to `command.com`; original `append/makefile` has `append.skl -> append.ctl -> append.obj -> append.exe`. Both original recipe paths and line locations are provided per row. Original/current source bytes match the frozen hash. These are candidates for exclusion **only as host build input files**, since the active host targets use other C/ASM roots, not an exclusion of the guest code, resource, program or functionality. In particular recipe evidence establishes historical build dependence, not that the installed immutable image was produced from these exact bytes. COMMAND.COM's independent current immutable-image identity and BOP route are documented in `guest-command-dosx-review.csv`; they do not fill that provenance gap.

The remaining 395 rows retain their prior precise recipe filename references and family ancestors, with linkage marked unknown. References can be comments, incidental uses or only local dependencies; they were not promoted automatically into complete historical guest target ownership. In particular common include trees need actual caller/condition checks; resources require a consuming RC/message/build chain; a same-name target or missing host input alone is not sufficient. Each retained family therefore has a finite next step: resolve original target -> link/resource compiler -> exact row, distinguish host and guest consumption, and only then propose role classification. Exact image provenance and execution behavior remain separate.

No product, guest, merged ledger, or other shard was changed. `file-audit.csv` classifications remain untouched for the main reviewer.
