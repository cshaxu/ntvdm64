# Shard 1: WOW Winsock database requests and task cleanup

`wow32/wsdata.c` differs from the frozen original (189 inserted and 13 deleted lines against the primary reference); the async cancellation and task-lifetime changes are registered as `MVDM-HOST-DIV-463`. The observer checks current and both original hashes, binds 23 map-visible functions to current released WOW32 bytes, and resolves selected actual machine-code edges `WWS32TaskCleanup` → `WWS32CancelAsyncRequestsForTask` and `WWS32PostAsyncGetHost` → `WWS32FindAndRemoveAsyncContext`. These prove link composition, not guest runtime or every asynchronous race.

## Authority and lifetime

Synchronous database lookup uses the existing per-task guest buffers and converts host structures. Original async constructors hold a global context list containing native request identity, a 16-bit request identity, destination and native buffer; the project extension adds task serial. Completion removes its matching context, converts into the guest buffer on success, posts the Win16 message, and frees the context/native buffer. Task cleanup detaches records with its serial under the existing critical section and then asks the provider to cancel outside the lock; only afterward does `wsext.c` free that task's guest database buffers. The cancel API similarly resolves the 16-bit/task identity to the native request and removes/releases a record on provider cancellation success. The source path does not create a second task or request registry.

Historical `m0-t467-s3-winsock-async-lifetime.md` documents actual guest localhost completion, successful cancellation and task-loss witnesses with a different, hash-identified candidate image. It explicitly excludes injected allocation failure, 16-bit handle wrap and async-select window loss. Those results are not fresh validation of the current release image. `shard-3/winsock-abi-role-review.md` independently records that task rundown ignores the provider cancel return before freeing the native buffer: whether an unsuccessful cancellation can still result in a provider write or completion is an unresolved provider/lifetime question, not established corruption or safety.

The original `WWS32GetAsyncTaskHandle16` saves the pre-increment WORD counter into a local, increments and avoids zero, but returns the updated counter rather than the saved local. Constructors store the same returned value both in the guest result and context, so this alone does not establish a mismatch. The 16-bit counter eventually wraps and does not itself check for an outstanding identity collision; actual consequences under same-task concurrent outstanding requests require bounded testing and comparison with original behavior. The task serial counter's cross-thread update and wrap are also not proven by this static observation.

Replay `python artifacts/mvdm-audit/shard-1/wow-winsock-database-observer.py`. This audit ran no provider, guest, network or product, and did not change guest, product, build tree or shared ledger. Completion-versus-cancel races, failure paths, native buffer lifetime and multi-task identity remain explicit limitations.
