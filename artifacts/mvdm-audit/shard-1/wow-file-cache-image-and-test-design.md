# WOW mapped-file cache: relocation-aware image binding and finite test design

This follows `wow-kernel-headers-lifetime-review.md`. No code, guest, product, shared ledger, build tree or production process was changed. The extracted complete bodies of `W32MapViewOfFile`, `FreeMapFileCache`, `WK32FileRead`, and `WK32FileClose` are text-identical between current source and the OpenNT reference, although wkfileio.c as a whole differs. The defect candidate is present in the original bodies, not a demonstrated project-added divergence.

`wow-file-cache-image-observer.py` parses current x86 wkfileio.obj COFF sections 17, 37, 39, 57, masks their four-byte relocation sites, and requires all other bytes in each full function section to match both current built and installed WOW32.DLL. Both match: FreeMapFileCache at PE file offset `0x18250`, W32MapViewOfFile at `0x18900`, WK32FileClose at `0x18990`, WK32FileRead at `0x192d0`. Full image and object hashes and relocation encodings are recorded in `wow-file-cache-image-evidence.json`. In both PEs, W32MapViewOfFile relocation fields bind to IAT entries `CreateFileMappingA` RVA `0x8f578`, `MapViewOfFile` `0x8f588`, and `CloseHandle` `0x8f5d4`; FreeMapFileCache's CloseHandle also binds `0x8f5d4` (`objdump -p` verifies names). Thus both observed images contain the exact non-relocation instruction bodies and resolve those host operations; this is not a runtime witness. Full built/installed DLL hashes differ, and this finding does not replace whole-package identity review.

Finite regression design, using a compiled isolated fixture that extracts the actual current functions and their cache types into a test unit, substitutes deterministic Win32 boundary functions, and never opens user files or touches guest: initialize cache; simulate valid source file handle, CreateFileMapping returning H, MapViewOfFile returning NULL, CloseHandle recording H, and ReadFile succeeding. Verify the original cache stores H after closing it. Emulate H reuse by assigning it to an independent live fake handle, then invoke the real cache free/close sequence; assert the event log demonstrates a second close of H and corruption of the fake handle's ownership. A distinct no-reuse case verifies second close returns invalid handle. Control case: successful map, read, final close gives exactly one unmap and one mapping close; CreateFileMapping failure must not close H; repeated free must not repeat cleanup. Also test mapping failure followed by cache eviction, and source handle reference-counted close behavior, with exact event ordering and fallback bytes. Handle reuse is deliberately simulated, not claimed a reliable real-Windows allocator policy. A minimal candidate would clear hMappedFileObject immediately after the failed-map CloseHandle; then rerun every case and verify untouched normal path and original guest semantics. A source-extracted fixture must verify function-body hashes and boundary ABI, and explicitly use the selected implementation rather than reimplementing its logic in the test.

No failure injection or live product run has yet been performed, so this is an image-bound source defect candidate plus an executable test design, not an observed production crash or completed fix. Replay `PYTHONDONTWRITEBYTECODE=1 python -B artifacts/mvdm-audit/shard-1/wow-file-cache-image-observer.py` and inspect `objdump -p` import entries. No claim that every real host produces or reuses the same handles.
