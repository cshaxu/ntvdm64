# Shard 1: Win.ini embedding and registry translation

## Identity and actual bindings

Original `wow32/mapembed.c` maps Win16 `[embedding]` profile data to and from classes registry keys. It is byte-identical to both frozen OpenNT copies. The observer binds its six function bodies from the selected object to release WOW32 machine code and resolves its actual registry call relocations to `wow_registry_*` project bindings, rather than presuming direct host Registry access. Hashes and provider owners are in the JSON. Linkage alone does not prove guest invocation or registry persistence.

Original profile thunk flow in `wkernel.c:149–194,209–240,247–275,459–468` is bidirectional: successful embedding-key writes call `UpdateClassesRootSubKey`; embedding reads refresh one key or enumerate all keys before querying the profile. The two-second `GetTickCount` guard belongs to the original compatibility behavior and is separate from lifecycle timeout policy. `UpdateEmbeddingKey` queries a class and server, writes the profile projection and releases its temporary buffers and registry key on both ordinary and `NukeClass` exits. Reverse conversion parses the supplied profile value and creates/sets two class keys, closing handles on the visible paths. The source path points to a shared `_LastTimeUpdated`; cross-task/process freshness is not established here.

The project intentionally binds registry calls to the worker-owned shadow registry via the WOW32 binding (`docs/etc/evidence/m0-t461-s2-binding-implementation.md`). That receipt's registry fixture and old package results do not test this OLE/embedding consumer; the T461 S1 matrix explicitly hands it to W18. Profile operations in mapembed still resolve native `GetProfileStringA`/`WriteProfileStringA` imports. No inference that this module writes the real Registry should be drawn from API spelling.

## Bounded failure-path candidates

- `UpdateEmbeddingAllKeys` stops only at `ERROR_NO_MORE_ITEMS` (`mapembed.c:148–157`). Its actual `wow_registry_enum_key` binding returns `ERROR_INVALID_HANDLE` when its parent key/provider cannot be obtained (`wow_registry_binding.c:243–249`). If that error persists on an entered all-key enumeration, the original loop continues incrementing rather than reporting failure. Production reachability and persistence of that state have not been proved; the normal shadow enumerator returns `ERROR_NO_MORE_ITEMS` after enumeration. A controlled provider failure at this exact entry and a no-failure control are needed before classifying a product failure.
- `UpdateClassesRootSubKey` writes two NUL bytes into its supplied `Value` buffer while parsing (`mapembed.c:395–405`). `WK32WriteProfileString` and its private variant pass the string obtained by `GETPSZPTR`; how this maps, flushes or protects guest memory in the actual profile and its observable semantics are not established here. Do not assume mutation is guest-visible or assert a defect without a direct witness and original-behavior comparison.
- `IsWinIniHelper` relies on a debug assertion after `GetFullPathName` to bound a MAX_PATH local buffer before comparing it. Long-path handling and modern host return behavior require an explicit controlled case; no overrun or product exposure is claimed.

Replay `python artifacts/mvdm-audit/shard-1/wow-embedding-observer.py`. This review did not execute the product, touch guest or registry/profile data, or modify build trees or shared ledgers. Original OLE behavior, independent workers, callbacks, host failures and state durability remain unverified.
