# DEM FCB open failure ownership and minimal repair boundary

This source audit uses the original/current chain recorded by [FCB open review](../nine-way/part-8/dem-fcb-open-review.md) and the existing [selected-object high-size witness](../nine-way/part-8/dem-fcb-metadata-selected-object-review.md). No new runtime, product or guest change occurred.

`demdisp.c` dispatches open/create to `demFCBCommon`. After `CreateFileOem` succeeds DEM owns the native handle. Metadata must succeed before its split value is published through AX:BP to the guest; on success the guest/`demCloseFCB` owns eventual close. The separate `demGetFileInfo` caller opens a handle and explicitly closes it on both metadata success and failure. Therefore `demGetMiscInfo` and its two callers must have **one consistent close owner**: a helper-owned close on all failures would double-close the existing `demGetFileInfo` caller. Original/current `demClientError` reads `GetLastError`, may inspect the live handle to map a hard error to a drive, updates guest state, and does not itself close that handle.

Current `demFCBCommon` returns immediately when metadata fails without publishing or closing its acquired handle. `demGetMiscInfo` compares BOOL `GetFileTime` to -1, does not check `FileTimeToLocalFileTime`, and closes internally only in the special `GetFileTime == -1` branch; its DOS-time failure, file-size error and nonzero high-size branches do not close. Thus the source-level ownership counterexample affects open/create and the special helper-close branch is inconsistent with the other caller. The high-size actual-object fixture used a real 4 GiB sparse file and recorded `highsize result=0 handle_live=1`, but calls the helper directly with `demClientError` stubbed; it does not prove a guest-reached leak or error semantics. The selected `demfcb.obj` SHA-256 at that witness and this review is `40550EA098C987667A0114709625B57D814AD25EB14E4286B5D644188ADC872D`. The T420 S33 recorded guest FCB open/read/close exercises the then-identified package's happy path only.

Minimal S12 repair candidate: define the metadata helper as borrowing the handle, keep error translation while the handle is valid, and close the unpublished handle exactly once in each owning caller's failure path. Preserve guest ownership after successful open and `demGetFileInfo`'s normal close. Correct BOOL failure checking, check local-time conversion, and handle `GetFileSize` sentinel using the documented last-error distinction rather than interpreting every `0xFFFFFFFF` low part as failure. Do not casually invent a mapping for out-of-range file size or APIs which do not reliably set last error; determine the original DOS/hard-error contract and ensure error registers/packet and any required last error survive cleanup. This is a design candidate, not a claim of completed implementation or an approval for a new observable semantic concession. Register any original-source difference.

Before changing code, use the real selected DEM object and controlled host/OEM seams to establish: open/create failure and success; `GetFileTime`, local-time, DOS-time conversion and size failures independently; nonzero size high part; valid low `0xFFFFFFFF` with zero last error; error sentinel with a real last error; and both `demFCBCommon` and `demGetFileInfo`. Assert acquisition, live handle during `demClientError`, exactly one close where not published, no close before success publication, CF/AX and hard-error packet behavior, plus cleanup on failure. Follow with version-bound integration on disposable files and unchanged guest; diagnostic seams or historical happy-path evidence are not release acceptance.
