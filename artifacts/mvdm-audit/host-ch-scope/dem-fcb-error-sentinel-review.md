# DEM FCB error translation and real 4 GiB−1 sentinel

This review combines original/current source tracing with a new selected-object host observation. It does not change or execute guest or product code. The saved [test source](dem-fcb-size-sentinel-fixture.c), [runner](dem-fcb-size-sentinel-run.py), and [receipt](dem-fcb-size-sentinel-observation.json) operate only on a temporary, delete-on-close sparse file and call the existing selected x86 `demfcb.obj::demGetMiscInfo`; the fixture's `demClientError` records LastError but does not implement the real original converter. The object SHA-256 is `40550EA098C987667A0114709625B57D814AD25EB14E4286B5D644188ADC872D`; the MinGW linker reported the same `.drectve` warning as the prior high-size probe but succeeded.

For a real sparse file of exact length `0xFFFFFFFF`, the host `GetFileSize` returned low `FFFFFFFF`, high `00000000`, and LastError 0 after the fixture cleared it. The real DEM helper then returned FALSE, invoked the error seam once with LastError 0, and left the native handle alive. The run exited 0 as an observation of this baseline, not as a compatibility pass. Existing [4 GiB high-part selected-object witness](../nine-way/part-8/dem-fcb-metadata-selected-object-review.md) separately observed helper FALSE and live handle for `0x100000000`. Both observations call the helper directly; neither proves a particular guest binary or `demFCBCommon` reached the boundary.

Original `demClientErrorEx` reads thread LastError, maps zero to `ERROR_ACCESS_DENIED` (5), and for non-hard errors writes AX (if requested) and CF. Errors 19–31 or WRONG_DISK are hard: it marks the registered hard-error packet, obtains a drive letter using the still-live handle when provided, maps WRONG_DISK down to GEN_FAILURE, converts the result to the INT 24 code, saves registers/current service for retry, and sets CF. The source route is described in [hard-error audit](../shard-3/dem-hard-error-audit.md). Source tracing therefore predicts zero-seam-error falls back to 5 in the real converter, but the new probe **does not call the original converter** or establish a live packet or retry. A stale nonzero thread LastError after a successful oversized-size query could lead to a different translation; no source contract supports inventing a replacement hard-error code without validation.

`demGetMiscInfo` currently tests low `FFFFFFFF` directly, not `GetLastError`, and rejects any nonzero high part. On the exact 4 GiB−1 file this is an empirically observed false rejection at the helper boundary. High part nonzero cannot be represented by its 32-bit size output; its intended DOS failure code still needs original-contract evidence. For true `GetFileSize` error, clear LastError before the call and distinguish a nonzero error after the sentinel; preserve the resulting error until original error translation has consumed it. Other metadata conversions need separately defined treatment when their failure does not guarantee a meaningful LastError.

The two actual callers have different cleanup: under controlled metadata failure `demOpenFCB` does not publish or close its acquired handle, while `demGetFileInfo` closes it. The selected-object [caller fixture](dem-fcb-callers-reachability-review.md) proves those branches with fake handle/error seams. A coherent candidate makes the helper borrow the handle, translates errors while the handle is alive, then lets each caller retire its own untransferred handle exactly once. Do not close before original hard-error drive lookup, double-close the second caller, or rely on LastError surviving cleanup. Source-level DOS SVC paths and historical guest success are documented there, but actual guest failure and hard-error/retry sequencing remain unverified.
