# SoftPC BOP build ID, generated C-VID bindings and allocation macro

This source/object audit covers three currently pending `softpc.new/base/inc` physical C/H roles. Original source is retained; no runtime test or guest modification was made. It distinguishes identical basenames by their actual paths in compiler dependencies.

| Header | Original contract and selected evidence | Suggested disposition and remaining work |
| --- | --- | --- |
| `build_id.h` | Defines a 16-bit `BUILD_ID_CODE` from date/special fields. `bios/build_id.c:59-76` uses it for BOP 21, copying `Base$` into guest `DS:CX`, returning the code in BX and AX=0 for its known module. Original `bios.c:183` dispatches `Get_build_id` as BOP 21. Cached `obj/bios/build_id.obj` has a VALID dependency on this exact header and the worker map attributes `_Get_build_id` to that object. | **Partial:** the original contract and built dispatch are present, but this inspection does not establish guest invocation, unknown module behavior, boundary/fault handling or current package identity. Keep those proofs in the BOP/BIOS recovery group. |
| `j_c_lang.h` | Original register/prototype definitions for generated C. Multiple `base/cvidc/*.c` include a basename `j_c_lang.h`, but cached `SEVID000.obj` and `ev_glue.obj` VALID dependencies resolve to `base/cvidc/j_c_lang.h`, not this `base/inc/j_c_lang.h`. Their SHA-256 values differ (`55df471afe9f7c0a8cf83aae0476a1277aa44ac3ab5efacb658d4f597569a18a` versus `1c0727f420986a3cde9992af5cf3c4c7b084029f3a3a4c04ad7549e7b01235a4`). The base/inc path is listed by a cached test fixture dependency, not by those production C-VID objects. | **Pending:** do not promote this physical file from a basename match or test fixture. Establish any production consumer and original alternate generated-code profile independently; C-VID execution and failure checks stay in their functional group. |
| `chkmallc.h` | Defines original `check_malloc` as a loop that calls `host_error` while allocation returns null. Cached `obj/host/stubs.obj` has a VALID dependency, but its only `check_malloc` invocation in this translation unit is in the `MONITOR` branch, not the selected CPU40 route. Similar basename `ckmalloc.h` contains another macro used by other selected callers and must not be conflated without resolving includes. | **Pending:** compile inclusion does not establish macro expansion or provider behavior. Trace selected consumer/profile and evaluate failed-allocation retry/termination if relevant; do not silently mark the potentially looping failure path safe. |

The cached worker map proves neither actual BOP execution nor failure behavior. Original caller, selected source, actual object and alternate headers must be checked separately; frozen dependency records characterize only their observed profile. No source/ledger classification was edited by this report.
