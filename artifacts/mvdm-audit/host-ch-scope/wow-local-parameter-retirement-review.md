# WOW local heap and parameter-map retirement

The original `W32LocalReAlloc` is not the parameter-map owner: `wcall32.c:56-89` chooses host `LocalReAlloc` when `LOWORD(hInstance)==0`, otherwise invokes guest `LocalReAlloc16`, then refreshes a supplied mapped flat pointer through `ParamMapUpdateNode`. `wcall16.c:71-89` validates the encoded guest segment/handle and invokes `CallBack16(RET_LOCALREALLOC)`. `wow32.c:537-546` registers these callbacks; the selected EDIT integration obtains registered callbacks in `wow_edit_memory_bindings.h`, with original EDIT realloc uses such as `editml.c:1207`. This is a static path and callback registration, not an actual guest realloc witness.

The original process-wide `gParamMap` in `wparam.c` holds guest 16:16 pointer, current flat pointer, reference count, up to 16 old flat aliases and one owner task. `AddParamMap` finds by 16-bit pointer, increments an existing reference or creates a node stamped with the current task. `ParamMapUpdateNode` refreshes the current mapping and saves an old alias; at capacity it overwrites slot zero, not an unbounded generation history. `DeleteParamMap` removes only on the last reference. `wkman.c:1552` invokes original `FreeParamMap` for a retiring task: the latter unlinks every node stamped with that task, independent of refcount. It does not free an underlying guest allocation; mapping records and guest heap ownership are distinct. Original/current normalized function bodies for `W32LocalReAlloc`, `GetParam16`, `DeleteParamMap` and `FreeParamMap` match; current `FindParamMap` and `AddParamMap` have registered DIV-347 NULL, refresh and unwind changes. No fresh-image equivalence follows from source matching.

Existing `tests/observation/wow_parameter_map_fixture.c:97-114` extracts selected source with test-owned boundaries and checks NULL rejection, refresh failure/exception rollback, nested pinning, 19 simulated moves with the inherited 16-alias policy, and two **different** guest keys owned by two tasks: retiring one preserves the other. It does not establish same-key cross-task borrowing, task-handle reuse, the actual guest local heap, or concurrent retirement. `shard-2/wcall32-release-review.md` binds four original function bodies to one recorded published image, but not live realloc behavior. Prior EDIT/message tests have their own snapshot and narrower contracts.

## Concrete conditions and uncertainty

* Source-established, not yet reproduced as a product bug: if two task contexts add the **same** guest pointer while a node exists, the second increments that node without changing its first-owner task; retiring that first owner purges it even with a remaining reference. Whether such cross-task concurrent access is legal, reachable and must survive retirement is unresolved; forcibly invalidating an active borrowed input is explicitly outside the older T447 guarantee. Do not introduce per-task records before proving the original contract and actual caller/lifetime.
* The key is pointer value and the owner field is a 16-bit task handle; no generation is visible in this map. Successful retirement before task/selector reuse prevents an old same-owner node from remaining, but actual teardown ordering, reentry and handle reuse have not been observed end-to-end. A stale-node failure is not yet established.
* A 17th and later pointer move evicts an old alias by the original bounded policy; this is a demonstrated controlled limit, not proof a real application retains or dereferences the evicted alias. `W32LocalReAlloc` calls refresh after the guest callback regardless of its return; failure/callback teardown cases need explicit evidence before calling that wrong.

Finite S14/S15 validation: bind exact staged WOW32 and immutable guest hashes; exercise real EDIT guest local allocate/lock/realloc movement/unlock/free and normal task exit with live sibling; deterministic test-owned seams for callback failure, map refresh NULL/exception, same versus different keys, balanced nested references, old aliases, retirement during allowed reentry, task/selector reuse and cleanup exactly once. Establish whether a same-key borrow remains valid when owner exits before deciding a fix. Compare the actual callback return, `ppv`, mapping/guest ownership and error path; do not manufacture a second authoritative map. No product, guest or shared ledger changed.
