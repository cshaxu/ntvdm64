The separate original MVDM sample `vdd/samples/mscdex/tsr/mscdexnt.asm` hooks INT 2F and tries to register `VCDEX.DLL`. Its source and package/search-path boundaries are recorded in `../shard-0/mscdex-package-review.md` and `../shard-3/mscdex-guest-vdd-input-role-review.md`: prior snapshot showed MSCDEXNT present in the installed package but not VCDEX by that filename in the inspected package/system32 paths. This is a distinct candidate provider, **not** evidence that it implements the two SoftPC header contracts or that an actual guest load or physical optical request works. Other search paths/providers remain possible.

The original `vdd/samples/mscdex/vdd/sources` explicitly builds the separate `vcdex` DYNLINK target against `ntvdm.lib` with `VDDInitialize` as its entry. Its `vcdex.c` exposes `VDDRegisterInit` and `VDDDispatch` and includes its own `mscdex.h`; this distinguishes the original sample target from both SoftPC declarations above. Source and target identity alone do not establish a current build edge, registration, loading or optical operations. S17 retains original-target applicability and provider selection before real-media acceptance.

`dos/dem/demgset.c`, `demioctl.c` and `demfile.c` contain host drive-type and file semantics for Windows CD-ROM volumes; those checks do not prove MSCDEX VDD registration, raw optical control, media changes, errors or teardown. The S17 recovery worklist retains the VDD path and its negative/real-media tests. No runtime probe was executed for this source audit.
