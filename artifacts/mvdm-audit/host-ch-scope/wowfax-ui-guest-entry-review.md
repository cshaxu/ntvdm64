# WOWFAX UI main entry to Win16 provider

This source-level pass covers pending `fax/wowfaxui/wowfaxui.c` and `wowfaxui.h`, beyond the previously reviewed property-page, helper and shared-driver owners. Both files are byte-identical to the two retained original editions: SHA-256 respectively `D96BF03EBD449B537C25E0126529AF008E5ECC8D7421658497FE35FDE4261CA4` and `88D90B14CEC1EBF6CB08D142F8CCC19B9DCB246CF9FAB6C63124B468284CDF51`. The original `wowfaxui/sources` selects a separate WOWFAXUI DLL, and `wowfaxui.def` exports document properties, device capabilities, upgrade and document event entry points. The current inspected product graph does not select that separate DLL; this is not proof that no external registered provider exists.

| Physical file | Original behavior and present evidence | Recommendation |
| --- | --- | --- |
| `wowfaxui.c` | Spooler-facing `DrvDocumentProperties` and `DrvDeviceCapabilities` populate a shared view then send a WOW request; `DrvDocumentEvent` dispatches document/DC events including ENABLE, STARTDOC, ENDDOC, PRINTPAGE and DISABLE; `DrvUpgradePrinter` delegates to the separately audited helper. | Historical distinct UI provider, keep pending until actual installed provider/guest path and S16 behavior are established. No observed execution of this file. |
| `wowfaxui.h` | Declares UI action values, registry driver name/port record, document event handlers and helper contracts; includes the separate shared FAXDEV ABI from `faxcomm.h`. | Keep pending as original UI-private/shared interface; do not collapse into generic common-dialog declarations. |

The source chain is specific: UI `InterProcCommHandler` sends `WM_DDRV_*` with a mapping ID; selected original WOW32 `WowFaxWndProc` (`wow32fax.c:161-193`) opens the named map, invokes `WOW32FaxHandler`, marks `status=TRUE` meaning **processed**, unmaps and closes it. The handler maps/converts and calls the original WOWEXEC `FaxWndProc` (`wow16/test/shell/wowexfax.c`), whose `WM_DDRV_INITFAXINFO16` allocates a guest record and whose LOAD/ENABLE paths load the 16-bit `.DRV` and resolve its driver entry ordinals. `status` is not the driver's success result; callers must separately inspect `retvalue`. The captured WOW32 graph/map binds the client path, but the source chain alone does not establish the separate UI, driver, guest module or device actually ran.

S16 must first identify actual UI/driver/guest image and provider applicability, then check mapping ID uniqueness/reuse, size and relative offsets, synchronous vs notify/callback completion, processed-versus-result semantics, 16-bit driver load/unload, page/device failure and task/peer retirement. Do not infer compatibility from ordinary printing or create a second mapping owner. This review ran no tests and changed no product, guest or shared ledger.
