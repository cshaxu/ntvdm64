# GLOBALFREEALL: guest owner and WOW32 slot

**Correction:** The `UNIMPLEMENTEDAPI` label at `wow32/wktbl2.h:43` alone does not prove `GlobalFreeAll` is missing. Both retained original WOW32 trees contain the same slot. The original guest kernel provides a real function and has internal direct calls to it; those calls are not shown to enter the host slot.

`wow16/kernel31/kernel.def:65` exports `GLOBALFREEALL` at ordinal 26 (`NODATA`, internal). The original WOW `kernel31/makefile:102-105` defines WOW and PM386 for the 386 configuration, while `krnl386.lnk:2` names `3ginterf`. Its `3ginterf.asm:685-715` defines a FAR guest procedure, enters the arena, selects the supplied owner or `GetDefOwner` when zero, and calls guest `gfreeall`. `3gmem.asm:1198-1275` documents and implements freeing matching-owner objects from the global arena, then scanning selector entries for matching discarded handles and freeing those selector arrays. The interface also performs a DPMI selector operation for the supplied ID; its precise failure behavior is not established here. This is separate from the historical unselected `WK32Global*` thunks.

The original guest `i21task.asm:765-803` arranges the invalid-opcode/DPMI exception-return path and a temporary kernel stack, then directly calls `GlobalFreeAll` with the task owner before `DeleteTask` and `TerminatePDB`. This is a guest exit sequence, not proof of host exception recovery or an observed task termination. `module.asm:370-397` clears/unlinks the unloaded module and directly calls the same guest function with its module owner. `miscapi.asm:153` changes ownership to protect an object from that cleanup. These are explicit internal source callers; a bounded `rg -i '\bglobalfreeall\b'` over current MVDM and both retained originals finds no other named caller outside the kernel source and the table.

The WOW32 dispatch table contains an unimplemented entry with this label at the corresponding ordinal position; `wow32.h:665-670` aliases `UNIMPLEMENTEDAPI` to `WOW32UnimplementedAPI` (and also aliases `LOCALAPI` there in the non-debug configuration), whose release body returns FALSE at `wow32.c:823-839`. A deliberately constructed WOW thunk call ID for that slot would therefore reach a failure stub if admitted by dispatcher; that does **not** establish that ordinary guest `GlobalFreeAll` import or either kernel direct call generates that thunk call ID. Whether an unusual guest manually emits the BOP/call ID or an installed image has a different entry path remains untested. Do not “fix” the table slot merely because of its label; doing so could introduce a competing host cleanup owner.

## Packaged guest export and distinct BOP route

The read-only [NE observer](globalfreeall-ne-observe.py) reads `WINNT/SYSTEM32/KRNL386.EXE` directly from `assets/winnt.zip` without extracting or changing the guest. The member SHA-256 is `D404576899CC11D23F368F2B30554E6108657CD37809837B341FD37E6B1A7AF4`. The NE entry table's ordinal 26 has flags 1, segment 1, offset `0x1059`. A near call at `1:1097` is bytes `E8 0E 46`, targeting `1:56A8`. The retained `retail3/kernel.map` names `GLOBALFREEALL` at `1:1059` and `GFREEALL` at `1:56A8`, matching those addresses. In contrast, the explicit generic thunk implementation `wow16cal.asm:325-347` selects a fast vector or emits `BOP BOP_WOW`. Source describes the owner cleanup call as direct and the packaged export contains a near call consistent with it, not an entry-table forwarding stub. Exact full map/image build provenance, runtime selection and downstream calls remain unproven; address correspondence alone cannot establish every byte of that source built the image. No direct breakpoint or executed task-exit trace was performed.
