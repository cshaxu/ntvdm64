# M0 T335 closure — Original WOW32/Win16 owner-package recovery

## Result

T335 closes the declared non-GUI WOW32/Win16 host/guest profile. It is a
source-backed package closure, not a claim that arbitrary Win16 programs,
WOWEXEC, or GUI/WOW product shells execute.

## Closed evidence

- S1's [source/profile ledger](../etc/operations/m0-t335-s1-wow-source-profile-ledger.tsv)
  gives every selected WOW32 path one disposition.
- S2 through S3/P7 preserve the original callback-frame shape, task binding,
  bounded guest leases and CPU40 selector conversion.
- S3/P8--P10 retain the original `wcall16.c` source binding, guest-return
  boundary and same-shaped local BaseVDM command route.
- S3/P11 proves the existing DOS and Win16 media is consumed through the
  original `-f/-w/-a` activation path and reaches the original DOS/COMMAND
  startup services; it is not missing a guest loader.
- S3/P12 executes the original `CallBack16` transaction through original
  CCPU40 return ordering on x86, without claiming the Win16 callback
  trampoline.
- S4's [package reconciliation](../etc/evidence/m0-t335-s4-wow-package-reconciliation-001.md)
  records fresh x86 and x64 formal product links and the one fixed-container
  x86 observation.

## Explicit boundary

The fixed-container x86 run reaches `50:11`, `50:3B`, `50:0F`, `50:1B` and
`54:05`, then exits `0xC0000005`. Original NTDOS/COMMAND input has therefore
already been loaded and registered. The successor boundary is CPU40/guest
continuity after `cmdSetInfo`, before the next BOP ingress. It is not a guest
loader, BOP leaf-provider, generic WOW callback scheduler, or Bochs repair.

GUI/USER/GDI, WOWEXEC/CSRSS/BaseSrv transport, kernel VDM, cross-process
broker behavior and the actual `WOW16_From_CallBack16` trampoline remain
outside this declared profile and require their own owner-package admission.
