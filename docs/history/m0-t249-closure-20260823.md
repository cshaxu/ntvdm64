# M0 T249 Closure — source-built guest low-memory runtime provenance

## Closed scope

T249 determines whether the runtime modification of the source-built low NTIO
aperture is authored by host composition/Bochs/BOP code or by original guest
runtime.  It does not claim that the following far target is valid, nor that
the source guest completes an ordinary `$Exit/$Abort` parent return.

## Result

- S1 proves no pre-existing selector-blind record can identify an ordinary CPU
  write to physical `0x0A87`.
- S3 registers and verifies the smallest default-off physical-write observer.
  It covers both Bochs' physical slow path and its normal CPU TLB fast path,
  but contains no selector, BOP, DOS or OpenNT interpretation.
- The source-built native checkpoint captures the first write:
  `0x0A87 <- FF`, at sequence `37093`, from
  `CS:base:EIP=9386:93860:7424` (executed physical position `0x9AC84`).
- The primary original `NTDOS.MAP` places `0x7424` within original
  relocatable `DOSCODE` (`0x00000..0x07938`).  The writer is consequently
  original NTDOS guest runtime, not `bx-core`, `bx-mantle`, `bx-vdm`, a BOP
  provider or a host-copy operation.
- Diagnostic-enabled and default-off formal MSVC x64 `/MT`, CPU5/P-MMX Ninja
  graphs both link.  The focused fixture passes; the bounded native run ends
  only at its declared million-instruction budget.

## Explicit transfer

`BOP-DEPENDENCY-115` remains partial because the source guest has not yet
reached ordinary `$Exit/$Abort/reset_environment` parent return.  The next
question is the **original guest runtime publication and consumption of the
far target** used after the attributed NTDOS write (`0000:0A87 -> 5859:5F04`),
including why that target is currently zero RAM.  It must start from original
NTDOS/NTIO source and image/layout evidence.  It must not become a DEM or
COMMAND BOP leaf repair, adapter PSP/PDB workaround, or a new Bochs machine
feature without separately admitted evidence.
