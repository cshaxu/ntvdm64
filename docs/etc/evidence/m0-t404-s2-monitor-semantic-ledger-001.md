# M0 T404 S2 — `MONITOR` Semantic Ledger

## Question

Which semantics are selected by every `MONITOR` preprocessor condition in the
OpenNT MVDM source tree, which of those reach the current formal x86/CCPU40
product graph, and which (if any) may be admitted without turning on the
kernel-V86 monitor personality?

## Inputs And Method

- Source tree: `src/mvdm-host/softpc.new`.
- Build graph: `build/M0-T404/S2/r037-dosx-fd-x86/build.ninja`, generated by
  `tools/build/New-T310OriginalSoftpcNinja.ps1`.
- Search: preprocessor directives containing the token `MONITOR`, restricted
  to C, assembler, and include sources. This found 244 directives in 70
  files. The r037 graph compiles 215 directives in 55 implementation files;
  29 directives in 15 unselected implementation/header files are retained in
  the inventory below.
- Classification is source-semantic, not a claim that every selected branch is
  reached by `WRITE.EXE`. **Retain** means retain the current no-`MONITOR`
  CCPU40 selection; **exclude** means do not enable the monitor branch;
  **local candidate** means a separately proven, translation-unit-local
  contract only.

`MONITOR` is the original NT kernel VDM monitor personality. It is not a
synonym for x86, V86, or CCPU40. In particular, `CPU_30_STYLE` remains
prohibited: it selects the native kernel V86 monitor and is not a CCPU CPU
profile.

## Decision

Do not define `MONITOR` globally. Exactly one local candidate is currently
proven: the BIOS BOP `FD` table entry, paired with the CCPU40 FD provider in
`dpmi32/modesw.c`. All other monitor-side branches either require the native
kernel monitor ABI, deliberately suppress the standalone path, or are device
integration alternatives needing workload-specific proof.

## Result And Follow-Up Gate

- The DOSX failure was a real independent contract omission (MON-01), not
  evidence that the monitor personality should be restored.
- No group is eligible for a global define. MON-05 and MON-07 are directly
  tied to native monitor state; MON-06, MON-10, MON-12 and MON-15 deliberately
  retain standalone behavior.
- MON-08 through MON-11 contain non-V86 device/UI semantics. They are not
  automatically irrelevant to CCPU40, but no current `WRITE.EXE` evidence
  shows their monitor side is needed. They require a separate workload,
  ABI-owner map, and acceptance record before any local facade is admitted.
- `LINKED_INTO_MONITOR` in the DPMI build is a separate declaration/linkage
  macro and is deliberately not counted as a `MONITOR` personality occurrence.

Confidence is high for source selection and occurrence inventory, high for
MON-01/02/03/05/07 ownership, and medium for device/UI reachability because
this ledger intentionally performs no runtime behavior change. A future
proposal must cite this ledger, name exactly one semantic group, and prove its
standalone owner before changing a compile define or source path.
