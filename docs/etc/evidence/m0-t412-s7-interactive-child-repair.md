## Source and cause

1. `adapter-opennt-host/basesrv/source/base_service.c` passed
   `&candidates[0].process` as a packed HANDLE vector, but each candidate also
   contains generation and Console identity. With launcher plus worker the
   second element read by `app/console_query.c::live_pid` is not a process
   handle. Real interactive MEM reached original `cmdExec`/COMSPEC dispatch,
   spawned run16, then Check returned error 6 and the child returned 31.
   A separate borrowed HANDLE vector fixes the stride; the candidate records
   still own handles and post-query identity validation.
2. Each authenticated connection issued the same first parent-wait receipt.
   Original `opennt-host/base/win32/server/srvvdm.c::BaseSrvGetVDMExitCode`
   compares that HANDLE-shaped identity across the Console's DOS record list.
   A nested child's receipt could match the still-active outer record. After
   the stride repair MEM executed but reported STILL_ACTIVE (259). Wait
   delivery now advances a service-locked shared high-water mark, preserving
   the original low-bit tag reservation and connection/generation checks.
   The same real MEM child then returned 0. No raw handle enters the wire.
3. DIV-196's copied async command/environment/std-handle buffer stayed active
   until child termination, rejecting subsequent native EXEC from nested
   COMMAND. Original `cmdexec.c::cmdCreateProcess` consumes those inputs only
   through CreateProcess; its remaining handles and converted environment are
   local. Move the existing finish call after CreateProcess returns and before
   ResumeThread. Do not add a capture stack or rewrite original process/wait
   policy. Nested MEM/VER/MISSING captures are observed after this change.

Original owner comparison: accepted local OpenNT
`base/mvdm/dos/command/{cmdexec.c,cmdmisc.c}` and mirrored
`base/win32/server/srvvdm.c`. The unavailable system boundary remains modern
Console membership and authenticated resource transport, not DOS CPU semantics.

## Nested COMMAND RPC repair delivery

2026-09-15, subsequent sequential delivery based on `c60e1c843`.
The preceding table is historical; this section identifies the newer products.
S7 remains open for COMMAND exit-status acceptance; no full-T closure is claimed.

Two additional transport defects were isolated without changing any mirror:

- Original `vdm.c::GetNextVDMCommand` retries a returned wait; original
  `srvvdm.c` reuses the ConsoleRecord event. The client adapter instead rejected
  a second delivery merely because `worker_wait_event` was already populated.
  It now retains the first local reference and closes subsequent duplicates.
- RPC `[out, system_handle]` transfers ownership of the server handle. The
  server entry returned borrowed receipt handles, destroying resources still
  retained for later original calls. Check/Update parent waits, Get worker waits
  and Get stream attachments now export independent duplicates. Allocation or
  duplication failure closes only newly exported references and resets outputs.
  Null stream slots remain null. Source receipts and original record policy stay
  unchanged. Default-off broker trace records export failures.

The ownership rule is explicit in Microsoft's
[system_handle documentation](https://learn.microsoft.com/en-us/windows/win32/midl/system-handle).
This is an RPC binding correction, not an invented VDM scheduling policy.
