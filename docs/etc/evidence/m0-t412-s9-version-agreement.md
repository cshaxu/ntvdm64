# T412 S9 three-program version agreement

## Contract and original-owner boundary

Owner requires a new S for protocol plus application-version checks, a common
`src/app/version.h`, APP_VERSION `0.0.<T task id>`, full build/test/publication,
commit/push, then wait for confirmation. Baseline: `dc4455afd`, accepted S8.
Current T is T412, so all three products use **APP_VERSION 0.0.412**.
This is a per-T application version, not a commit hash or per-build identity.
Compatible S/P deliveries within that T keep it; incompatible protocol changes
must advance the protocol even when the application version is unchanged.

- `APP_PROTOCOL_VERSION=2`; `service.idl` RPC major is 2.0. Version 1.0 peers
  cannot marshal the new Connect signature. The command-envelope format is
  still version 1 because its payload did not change.
- Connect carries a copied protocol integer and exactly 32 bytes of zero-padded
  application identity in each direction. Exact comparison rejects old/new
  protocol numbers, differing versions, nonterminated and noncanonical strings.
- The server authenticates the process before accepting identity and before
  creating its context/generation. A mismatch returns ERROR_REVISION_MISMATCH
  (1306), with null context/zero generation and a local/peer diagnostic.
- The common client, linked into run16 and ntvdm, validates the server response
  independently. If a peer returns an incompatible successful context, it is
  disconnected before original BaseClient operations become available.
- Legacy unknown-interface/procedure errors become explicit version mismatch.
  run16 does not retry or start another broker for this error. Authentication
  remains required: version equality is compatibility, not trust/authorization.

The shared header contains metadata only, explicitly authorized by the owner;
the adapter calls no application policy. Ninja's recorded include dependencies
contain that header for run16/rpc_client.obj, worker/rpc_client.obj and
basesrv/entry.obj, so changing it recompiles all three consumers.

Recovery ladder: original guest, COMMAND and BaseSrv algorithms remain intact.
The NT4 CSR transport below the original BaseClient is unavailable in the
standalone product. Its already-admitted native RPC boundary must now reject
independently deployed incompatible products. Direct original source does not
implement this three-EXE compatibility contract; the smallest existing transport
adapter/entry extension is selected. No mirror intrusion, overlay, parallel
service algorithm or new generic version manager is needed. Original task
selection, reentry and guest exit statuses are unchanged.

## Mixed-worker failure and repair

Initial negative testing exposed a second reached boundary: new launcher and
broker with the old S8 worker. The old worker exited with RPC unknown-interface
1717 before connecting; the launcher waited only for a task event which that
worker could never produce. `m0-t412-s9-old-worker-direct-mem.txt` timed out at
20 seconds. This was not a successful version-rejection test.

run16 now also waits on **its own created process**, alongside the original
parent event. Version-rejection exits (1306 or the legacy incompatible-interface
codes) return 1306 and take the existing UPDATE_VDM_UNDO_CREATION cleanup.
Every ordinary guest completion still takes the original parent-result route.
There is no worker reaper, arbitrary timeout, forced-success result or change
to the source-defined resident-worker lifecycle.

The same old formal S8 worker was temporarily deployed for the negative control;
`m0-t412-s9-old-worker-fixed-worker-version-rejection.txt` now exits 1306.
Its broker trace shows prepared launch followed by empty-grace and disconnect,
not a stuck pending task. The current formal worker was restored in a finally
block. This negative fixture is opt-in in Verify-CommandExitStatus; normal
matrices never silently replace product files.
