# T473 S13 input-source handoff investigation

S12 was accepted by the owner and S13 admitted. This record is an investigation, not a completed fix. Guest media remains immutable.

## Production path

`frontend_session.c::collect_console` reads physical Console records, applies CAF filtering and appends accepted records to the shared frontend queue. `window_route` drains the Console before changing `window_active`, but neither records nor retires outstanding Console keys; subsequent `collect_console` calls discard the inactive physical source. `frontend_session_read` copies queue records and removes them only for a non-Peek read. `frontend_session_prepend` can put worker-returned records before existing input. The channel serializes operations through the frontend I/O lock. Original `nt_event.c::ReturnUnusedKeyEvents` can return unconsumed keyboard history through that prepend path. Native NTVWM uses the same frontend READ_INPUT stream, but forwards it to its own Console.

Window events have a separate `frontend_window_keyboard_state`: `frontend_keyboard_dispatch` updates it when its sink accepts records into the frontend queue and emits break records on source retirement. That sink is queue insertion, not proof of a worker read. A correction must account for queued versus read versus returned events and owner transitions; the successful enqueue is not itself a worker-delivery receipt.

## Baseline evidence

The current production-source frontend channel fixture was built with `build/.ninja/msvc-x64-release/frontend/run-ninja.cmd console-channel-lifetime-test.exe` (owned build PID 36164, 2026-11-01T06:03:45Z, exit 0). With `MVDM_TEST_SOURCE_HANDOFF=1`, its `--private-desktop-full` case injected actual Console Ctrl/Alt downs, read both from the real frontend queue, and switched to Window through production VIDEO dispatch. Both required releases were absent: the case failed at `tests/app/console_channel_lifetime_test.c:308`; report `build/t473-s13/source-handoff-baseline.txt`, fixture SHA-256 `E948A74AE84002540FE8EBD49D29C5F3B7DD6041D06924FDB90882F9746B026B`. This proves the frontend lifecycle gap for simulated records, not physical keyboard behavior or the separate Win3.1 Alt+Enter symptom.

The historical product probe was reconstructed using current source and, separately, the previous successful observer and hook. Product cases entered a private Window but both COMMAND and CMD ended in observer exit 92 before the first Window keystroke. Diagnostics established `SetWindowsHookEx` failed with Win32 error 126 even when `LoadLibrary` and `GetProcAddress` succeeded; the target was the isolated stage's x64 `ntcon.exe`. The same occurred with the historical DLL and observer, canonical path, an isolated-stage DLL, and the previous successful `O:/winnt` runtime path. These are probe failures, not product input outcomes. Test-owned failed stages remain for diagnosis; do not characterize them as a missing desktop or infer a product result.

Follow-up must preserve Peek, prepend/ReturnUnusedKeyEvents, repeat and scan-less key identity, delayed old-source breaks, source and worker handoff, focus, failure and teardown. No repair or regression pass is claimed by this record.

A second actual frontend-channel baseline used `MVDM_TEST_SOURCE_UNREAD=1` to Peek the two queued Console downs without consuming them before the same switch. The later FIFO read failed the required down/down/release/release assertion at line 312 (fixture SHA-256 `8E6395FDB2097FA3610F1CCD68FEA09269135490848E6F5EB7CDBC26E340F0A4`; private-desktop report `build/t473-s13/source-unread-baseline.txt`). Thus a repair based only on keys already returned by Read would also miss the queued-input boundary; a Peek must not count as a delivery. The control uses the production frontend channel with a test-owned Console, not a complete guest.

A separate controlled API witness created a hidden, test-owned x64 window process on a private desktop and attempted the same WH_CALLWNDPROC installation using the x64 test DLL. It also returned error 126 before any product component was involved (`build/t473-s13/hook-api-control.log`, owned runner PID 28284, 2026-11-01T06:10:49Z). This narrows the observed probe failure to the API/test-host boundary; it does not identify why Windows returned 126 or authorize weakening product validation. The prior in-process experiment with non-null module was not a valid cross-process control and is not used as evidence.

The current original-worker integration makes returned-record accounting material: `nt_event.c::GetHistoryKeyEvent` uses `mvdm_keyboard_history_age`, and `mvdm_keyboard_history_pending` selects pending origins from the controller ring, held entries, output and prefix. Returned records are therefore not necessarily a contiguous suffix of the frontend READ batch. A design that simply rewinds the last N reads, matches duplicate key values as unique identities, or assumes every queued make was delivered to the current owner is not justified. This is a design constraint, not yet a proof that any particular replacement is required.
