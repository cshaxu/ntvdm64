# M0 T404 S5 matching WOW32 provider build 001

## Question

Can the current Win32/x86 CPU40 parent be paired with a same-version, formally
linked WOW32 provider before the public WRITE startup reaches the WOW ingress?

## Inputs and procedure

- Parent import library:
  `build/M0-T404/S5/r014-dpmi-vector-observation/original-softpc-process-import.lib`.
- Provider graph generated by
  `tools/build/New-T404S5Wow32ProviderNinja.ps1` at
  `build/M0-T404/S5/r015-wow32-provider`.
- The graph selected 77 original WOW32 C bodies and six named adapter/CRT
  carriers.  The local Ninja process scheduler did not create compiler
  children in this environment, so the graph's own ordered command list was
  executed unchanged by MSVC; all outputs remain under the r015 build root.
- The generated `wow32.dll` was inspected with `dumpbin`, then staged through
  `tools/build/StageWow32Provider.mjs`.
- Public verification used the sole positional command
  `ntvdm32.exe system32\WRITE.EXE`; raw data is retained at
  `O:\ntvdm64\logs\m0-t404-s5-r015-matching-provider-20260912-095840.*`.

## Observations

- The provider linked successfully as `wow32.dll`, SHA-256
  `446f64073ebeffce151bcaa0591eec928141438bd8020531f36133f4a0b8937c`.
- PE machine is `014C` (x86).
- Exports include `W32Init`, `W32Dispatch`, `GetCommHandle`, and
  `GetCommShadowMSR`.
- Imports include the public parent identity `ntvdm32.exe`, plus the declared
  system DLL boundaries.
- `O:\ntvdm64\WOW32.DLL` was staged with the same hash.
- The public run still timed out after 30 seconds with `loaded-wow32=no` and
  no WOW BOP entry.  It therefore never attempted to load the provider.

## Interpretation

The provider side of the current parent/provider composition is now a real,
same-version x86 build rather than the former stale deployed DLL.  The
remaining blocker is not provider identity or missing exports: the guest
startup has not reached original BOP `51` / `MS_bop_1`.  This result neither
claims a WRITE UI nor treats the matching DLL as a substitute for the missing
KRNL386/DOSX transition.

## Follow-up

Trace the exact original guest transition after successful DOSX/DPMI setup
that must call `WOW16SlowVector` and BOP `51`.  Do not modify WOW32 provider
or DPMI behavior without a source-proven predecessor edge.

## Whole-contract audit: host and guest profile pairing

The current build selects common DPMI32 bodies plus `dpmimemr.c` and
`dpmimscr.c`, with `CPU_40_STYLE` and without `i386`. The original `sources`
file assigns those two bodies to MIPS/PPC/ALPHA; its x86 providers are
`i386/dpmi386.c`, `i386/dpmimem.c`, and `i386/dpmimisc.c`. Running the compiler
as x86 does not select the original x86 DPMI contract automatically.

Two concrete compatibility questions follow from this pairing:

- `dpmiint.c:DpmiPassPmStackInfo` publishes a guest projection of
  `VDM_DPMIINFO`, while `BeginUseLockedPMStack` and `EndUseLockedPMStack`
  modify separate non-i386 globals in `data.c`. The repository has no other
  consumer of `Cpu40PmStackInfoAddress`. Original `dpmi/dxintr.asm` directly
  updates the published lock count and saved stack, whereas the distinct
  `dpmi/486/dxintr.asm` must be assessed separately. The deployed DOSX's
  actual variant must be identified before selecting the shared-state repair;
  a source-level split alone does not establish the current runtime cause.
- `dpmi/486/dxutil.asm` excludes LGDT/LIDT/LLDT/LTR and the ring-transition
  IRET under `WOW_x86`, replacing the entry with the `53:01` frame and
  `epmwow` continuation. Therefore omission of LTR by itself does not prove
  that every entry requires a synthesized busy-TSS/backlink pair. The current
  `modesw.c:cpu40_install_native_task_carrier` needs a specific executed
  task-switch consumer to justify that mechanism.

`dpmi/486/dxfunc.asm` emits `DpmiInUse` (53:0C) only after client selector
creation, first-client count increment, exception-stack allocation and size
initialization. Missing 53:0C consequently does not justify enabling hooks
early at 53:02. The registration batch precedes later observed 53:01 and
53:06 calls and must not be classified as an endless registration loop.

These findings change the next implementation step to a complete audit of
the selected DOSX variant against descriptor, stack, interrupt and context
providers. They do not authorize switching the whole build to `i386` or
deleting transition carriers without replacement. The earlier proposal to
import kernel code wholesale is not supported by this evidence. No runtime
package or execution behavior changed during this audit.

### Deployed DOSX identity and candidate rejection

The deployed `O:\ntvdm64\system32\DOSX.EXE` and mirrored
`src/mvdm-host/dpmi/486/dosx.exe` both hash to
`c5af29a29abf167b243daabf877459e8278b8c9a339bf8e1e2576ead5f6ceeff`.
The non-486 `dpmi/dxintr.asm` shared LockCount increments/decrements are
absent from `dpmi/486/dxintr.asm`. Accordingly the previously suggested
immediate unification of host globals with the guest stack projection is
not justified by that other variant's consumer. Binary/source lineage still
needs verification for individual executed routines; path and hash identify
the retained artifact, not every compiler conditional used to produce it.

The 486 `dxboot.asm:InitIntrDscrTable` explicitly registers vectors in
finite batches: 0..7, 8..F, 10..6F, 70..77, and 78..FE. That is 255 initial
registrations. The retained run has 257 dispatch/return pairs, including two
later registrations at `00C7:3116`; the count is consistent with this finite
initialization and is not evidence of a registration hang.

The next recovery comparison must therefore use the 486 guest's actual
frame and interrupt-return contracts. Neither source-family labels nor the
unreached other guest variant justify a host state-machine rewrite.

### Binary-confirmed virtual interrupt contract candidate

Read-only disassembly of the hash-matched `dpmi/486/dosx.exe` confirms that
the virtual-IF macros are present in the actual retained guest, not merely
in an unselected source conditional. At file offset `0x5A8`, the instruction
tests `word [DS:0314h],2400h`; its taken branch executes CLI without updating
the memory virtual-IF bit. The surrounding instructions load DS with 40h.
At file offset `0x54A3`, another sequence loads that same state word, tests
RI (`2000h`), and, on the no-RI branch, uses bit `0200h` to replace IF in a
saved flags word. Reproduction: `ndisasm -b 16 -e 0x59d` and
`ndisasm -b 16 -e 0x5498` against the retained DOSX, inspecting the first
22 and 42 instructions respectively.

Current `nt_msscs.c:InitialiseDosEmulation` sets MIPS (`0400h`) for CPU40.
Consequently these two macro families can select different interrupt-state
carriers: CPU IF for FCLI/FSTI, memory virtual IF for the no-RI saved-flags
path. The statement in `modesw.c` that all omitted VDM-state operations have
no guest-facing CPU40 contract is therefore too broad. However, this does
not prove that the differing carriers caused the observed stop, nor that
copying RI/RM writes from the kernel profile would repair it: RI selects
VIF semantics, not ordinary IF, in the guest macro.

The next check is the executed interrupt/flags synchronization contract,
including the original kernel owner and any existing CPU40 equivalent.
Do not blindly enable RI, clear MIPS, change CCPU instruction semantics, or
patch guest bytes. No runtime image was changed by this binary audit.

The original `OpenNT/base/ntos/vdm/x86/strtexec.c` supplies that translation:
its no-VIF path copies context IF into `VDM_VIRTUAL_INTERRUPTS` before guest
execution and copies the state-page bit back into context IF on exit. The
VIF-enabled path instead translates IF/VIF. Neither is equivalent to simply
setting RI in the current CPU40 guest. Current CCPU `c_reg.h:SET_IF` updates
`CCPU_FLAGS[9]` (or the SFELLOW interrupt callback), not the state page.

Historical discrimination is important: `ef1c3cb28` has the same MIPS-bit
initialization and substantially the same `modesw.c` transition body as the
current tree. Thus the mixed-carrier concern alone does not explain why that
historical family reached deeper. A separate execution-affecting difference
is present in `dpmiint.c`: that snapshot calls `EnableIntHooks` from
`DpmiSetProtectedmodeInterrupt`; current code waits for `DpmiDpmiInUse`
(`53:0C`). The former enables hardware, software, and fault hooks together,
so restoring it is not merely a harmless registration change. This is a
specific historical A/B candidate, pending verification of pre-client stack
and handler readiness, not an approved production correction or proof that
the original DPMI lifecycle should be moved.

The upstream `public/sdk/inc/ntx86.h` names byte selector 64 (`0040h`)

### Descriptor publication boundary identified

Original `dpmi32/i386/dpmi386.c:DpmiSetX86Descriptor` publishes DOSX
descriptors through `NtSetLdtEntries` (small updates) or
`NtSetInformationProcess(ProcessLdtInformation)` (larger updates). This is
process LDT publication, not replacement of the system GDT. Current
`dpmi32.c` installs `Cpu40LdtShadowAddress` as the LDTR table, while
`modesw.c` also installs that same address as GDTR and writes private TSS
entries into it. Thus the current reconstruction conflates two upstream
owners. A source-derived replacement must preserve separate GDT/LDT
ownership; merely deleting individual selector exceptions cannot do so.

The original external validation owner is
`base/ntos/ps/x86/psldt.c:PspIsDescriptorValid` (lines 951--1068).
Its finite policy permits invalid entries, checks present base/limit and
overflow, rejects system/gate and conforming-code entries, and requires DPL
3 for ordinary entries. It depends on `MM_HIGHEST_USER_ADDRESS`, descriptor
layout and `PAGED_CODE`, not process scheduling. This is a concrete
`opennt-host` candidate for the LDT publication boundary, but not for GDT
entries: applying it to the combined current table would wrongly reject
system descriptors. No import or runtime repair is claimed by this audit.

The exact original `PspIsDescriptorValid` function was subsequently compiled
and executed as a research-only x86 harness at
`build/M0-T404/S5/r016-original-ldt-policy/validator_probe.c`. Its upstream
file hash is `5f9c63eedfedc54e085f938c5befa12bdf9a4584288beb70259cd329d4935072`.
The harness binds only Windows LDT layout, a no-op pageable-code assertion,
and the NT4 2GB-profile user ceiling `7FFEFFFFh`. All nine cases passed:
invalid entry, user data, user code, rejected conforming code, rejected TSS,
rejected ring-0 data, base beyond ceiling, range crossing ceiling, and 32-bit
range wrap. This confirms a finite original validation owner and specifically
proves why a TSS must not be sent through the process-LDT policy. It does not
prove descriptor publication, GDT initialization, or WRITE recovery. No
production source import or runtime binding was made by this test.

### Original profile pairing constrains the replacement

The original `dpmi/makefile` selects `WOW_x86` for x86 and `WOW_MIPS`,
`WOW_ALPHA`, or `WOW_PPC` for software-emulated host platforms; all use the
486 source family. In `486/dxutil.asm`, non-WOW_x86 executes the original
LGDT/LIDT/LMSW/LLDT/LTR sequence. WOW_x86 omits that sequence and uses the
`53:01` passive-context frame instead. Accordingly, the current host's
manually reconstructed IDT/TSS path is not a drop-in restoration of either
complete upstream profile. Its dependencies must be audited as a whole.

Original `dpmimscr.c:DpmiDpmiInUse` explicitly says emulator IRET hooks
cannot be used before a protected-mode address of the correct BOP exists.
It enables both IRET and interrupt hooks together. This reinforces rejecting
the unsuccessful earlier registration-only hook experiment as a product fix.
The deployed DOSX remains hash
`c5af29a29abf167b243daabf877459e8278b8c9a339bf8e1e2576ead5f6ceeff`;
no alternative guest profile was built or deployed. A guest-profile change
is not silently substituted for recovery of the currently selected package.

A follow-up search of the selected OpenNT-4.5 C/assembly/header tree found
`KGDT_VDM_TILE` only in its public `nti386.h` definition, not an initialization
body. This negative search is not proof that no original provider exists.
Current monitor bindings were also inspected: `NtVdmControl` handles only
`VdmQueryDir`, returning `STATUS_NOT_IMPLEMENTED` for other service classes;
`mvdm_vdm_tib.c` binds storage and printer initial state, not execution
context synchronization. Neither constitutes an existing implementation of
the original `strtexec.c` transition contract. No production implementation
of `NtSetLdtEntries` or `ProcessLdtInformation` was found in the selected
adapter/OpenNT-host C/header paths. Thus a future source-shaped publication
binding must be explicit; reusing those names or the current TIB alone would
not restore the original service. This does not identify a currently reached
failing NtVdmControl call: the current CPU40 route bypasses that service.
