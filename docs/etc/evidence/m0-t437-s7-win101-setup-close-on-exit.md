# M0 T437 S7 — Win1.01 Setup PIF completion

## Question

Why did `PATCH\SETUP.CMD` remain blocked after original Windows 1.01 Setup
appeared to finish, and what is the smallest project-owned repair?

## Source finding

This is not a guest `SETUP.EXE` or `COMMAND.COM` modification problem.

- Original `BaseCheckVDM` requires a PIF to have a new Console
  (`opennt-host/base/win32/client/vdm.c`, PIF branch). The project preserves
  that condition in `run16-exe/main.c` by passing `CREATE_NEW_CONSOLE` for a
  PIF.
- Original `nt_pif.c` maps standard PIF `MSflags & 0x10` to `CloseOnExit` for
  a `DosSessionId`.
- Original `cmdmisc.c` intentionally labels a separate session Inactive and
  waits indefinitely when `CloseOnExit` is clear; when set, it calls
  `TerminateVDM` with the task exit code.

The old tool-created Setup PIF left `MSflags` at zero. Therefore the observed
wait was the intended retained-PIF-session path, while `run16` correctly
waited for the independent worker's terminal receipt.

## Repair

`PIF.EXE` now accepts the explicit `--close-on-exit` switch and writes only
standard PIF flag `0x10`. The tool sweep applies it to every generated PIF
whose paired command file synchronously waits for its independent PIF session:

- Win1.01 transient `SETUP.PIF`, installed `SETUP.PIF`, and installed
  `WIN101.PIF` (including its root `WIN.PIF` copy);
- Win3.1 `WINSTD.PIF` and `WIN386.PIF` generated by `win31-launch`.

Generic `PIF.EXE create` remains default-clear, so user-authored or explicitly
resident PIFs keep their original policy. `SETUP.CMD` also writes its small
temporary and installed profiles inline rather than relying on nested batch
subroutine calls after `run16` returns. No guest media or host lifecycle source
changed.

## Focused verification

```powershell
cmd /d /c "call \"...\\VsDevCmd.bat\" -arch=x64 -host_arch=x64 && cl ... src\\addon\\pif\\pif.c"
powershell -NoProfile -ExecutionPolicy Bypass -File tests\component-integration\pif_hash_tool_test.ps1 `
  -Pif build\M0-T437-S7\r001\PIF.EXE `
  -Hash build\M0-T437-S7\r001\HASH.EXE `
  -BuildRoot build\M0-T437-S7\r001\pif-hash `
  -ReleaseRoot assets\release
powershell -NoProfile -ExecutionPolicy Bypass -File tests\component-integration\win101_setup_cmd_test.ps1 `
  -ToolRoot tools\win101-setup -BuildRoot <short-physical-test-root>
```

The PIF/HASH test and the Win1.01 package test passed. They prove the created field is
`STANDARD.MS_FLAGS=0x10` and `STANDARD.CLOSE_ON_EXIT=YES`, that the
Win1.01 tool package carries the exact released utility, and that its
Apply/Setup-wrapper/installed-profile/Unapply contracts remain intact.

The rebuilt Win3.1 finalizer generated both profiles in an isolated
short-path fixture, and its profile assertions reached the new CloseOnExit checks. The
retained historical fixture then failed only because it intentionally contains
stale ambiguous `PATCH\WIN.CMD`/`WIN31.PIF` files that the profile test forbids;
this is unrelated to the generated PIF fields and was not deleted from source
or product media.

The rebuilt `PIF.EXE` and `HASH.EXE` were synchronized to `assets/release/`,
`tools/win101-setup/`, and `O:\winnt\system32`; SHA-256 equality was verified
between release and runtime copies.

## Remaining acceptance boundary

The owner hand-verified the repaired installed Win1.01 launch path. The two
existing generated profiles at the installed root were also updated in place
through `PIF.EXE update --close-on-exit` and re-read as `YES`; no guest binary
or configuration field was changed. The original-Setup UI flow remains a
separate guest-boundary behavior, but no longer blocks S7 closure.
