# OpenNT MVDM BOP Definition Inventory 001

## Question

What are all source-defined BOP identities that the Bochs/adapter route must
be able to recognize and observe before choosing a particular implementation?

## Inputs

The authoritative immutable export at
`artifacts/analysis/opennt-bop-inventory-005-20260811-001/` is generated by
`tools/governance/Export-OpenNtBopInventory.ps1` from these pinned OpenNT MVDM sources:

- `inc/bop.h` and `inc/BOP.INC` for top-level selector parity;
- `inc/{dossvc,cmdsvc,xmssvc,dpmi,rdrsvc,dbgsvc}.h` for service-family IDs;
- `softpc.new/base/inc/bios.h` for BIOS selector definitions; and
- `softpc.new/base/bios/bios.c` for every explicitly annotated `BIOS[]` BOP
  table row, including alternative conditional branches.

The exported JSON SHA-256 is
`893EB8D98A476A4D8A7AE996635B2B2BD24706594DE3666C2E664A1FB97E5C28`.

## Procedure

The exporter refuses an existing output root, hashes every source input,
parses only explicit numeric C definitions and annotated table rows, and
cross-checks every C top-level selector with its MASM `BOP.INC` equivalent.
It does not preprocess the historical sources, infer active compile-time
options, scan arbitrary guest memory, or execute any guest code.

The first exporter invocation is retained in `STATUS.md` as a pre-output
numeric-literal parser failure. Roots `002` through `004` are retained parser
evidence only: review found that their BIOS slice included storage/model
constants. The precise `005` export uses the explicit BOP-definition comment
range and excludes those non-BOP constants.

## Boundary decision

`C4 C4` remains a generic Bochs `#UD` fact. Bochs must capture no more than
the existing bounded instruction window and may apply only a validated typed
CPU result. It has no BOP selector, service, owner, or logging policy.

The adapter owns a static catalogue generated/reviewed from this inventory.
It may identify the copied selector byte and, only for a catalogued service
family, the copied fourth byte. A listener records the identity and returns
pass-through unless that exact catalogue entry has separately obtained a
source/ABI/failure-behavior admission. Pass-through preserves the original
Bochs exception path: it cannot advance RIP, modify registers/flags, write
guest RAM, or synthesize a DOS/BIOS result.

This is a catalogue boundary, not a generic historical `BIOS[]`, DEM, or
CCPU dispatcher. `50:11` remains the existing isolated transaction fixture;
`12h` is source-confirmed but remains inactive until its own admission.
