# T174 S1 paired declared DOS lifecycle provider 001

## Scope

T174 implements the T173 contained no-next-target branch of COMMAND service `54:11` as the return half of the existing declared `54:01` target lifecycle. It changes only `src/bx-ntvdm-adapter/`; Bochs, DOS/COMMAND guest source, host process composition, redirection and CLI result exposure remain out of scope.

## Changed composition

`bx_ntvdm_cmd_get_next_state_v1` now represents one declared guest target across both COMMAND boundaries: `delivered`, `returned`, and a copied 16-bit `terminal_dos_exit_code`. The return dispatch accepts only real-mode CPU vector 6 with the exact four-byte `C4 C4 54 11` window, and only after the launch half committed delivery.

On acceptance it copies low `DX` into state, produces the existing typed resume at `fault_rip + 4`, clears CF, and has no AX delta. It reads or writes no guest memory and consumes neither AL nor BX:CX. A second return, wrong mode, wrong selector/service, or missing launch state declines. Runtime access is through the existing ingress → provider registry → COMMAND plane gate; no new recognizer source file or generic BOP path exists.

## Interpretation

The pair is now one adapter-owned lifecycle provider, rather than two unrelated BOP patches. It preserves the original distinction between guest DOS exit state in DX and historical NT host-process status in AL: T174 deliberately does not set AL. It does not prove that a real guest program reaches normal `54:11`, continuous execution, CLI process exit propagation, or a second target. Those require separate evidence and admission.

## Follow-up

The highest-ROI next package is a CLI-owned fixed-width terminal-result ABI that can expose an already captured terminal DOS status without changing CPU semantics. It must not create an ambient queue or claim `dwExitCode32`/AL compatibility.
