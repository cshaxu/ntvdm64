# Proposal — Windows 1.01 彩色 EGA 运行与 Windows 3.x 非 WOW 路径调研

## 候选包与所有者目标

所有者于 2026-10-03 要求：队尾增加 T 任务，像 Windows 10 的 NTVDM
一样跑通彩色 EGA 的 Windows 1.01，并调研不使用 WOW 那套运行
Windows 3.x 的可能性。本提案是队尾的未编号候选 T，不改变当前
[活动任务](../states/CURRENT.md)，不提前实施或分配数字 T。

两个目标分别验收：Windows 1.01 是实际运行与兼容修复目标；
Windows 3.x 是有证据的可行性调研，不预先承诺全部版本或模式跑通。
“像 Windows 10 的 NTVDM”是所有者提出的体验参照，并非已验证的
版本、驱动或兼容性结论。准入时冻结对照环境、介质和操作，明确
可复现的行为；对照环境不可用则保留限制，不虚构等价结果。

## Windows 1.01 彩色 EGA 实施范围

通过现有 run16 / NTVDM 的 DOS guest 执行路径启动原始 Windows 1.01，
由它自己的 guest 图形与应用环境执行，不把它改走 WOW32 的宿主
USER/GDI 替代路径。保留原始 SoftPC CCPU40、guest DOS 与现有 NTCON
显示通道。先确认介质的 EGA 驱动、启动要求和实际输出模式，再
冻结分辨率、色数、调色板及测试配置，不能将单色或错误颜色冒充
彩色 EGA 成功。

验收至少包括：

- 正常进入图形桌面，彩色 EGA 输出、调色板、文字和窗口重绘正确。
- 键盘、鼠标、菜单、窗口操作及选定随附应用的启动、交互和退出。
- 选定多应用场景、遮挡与重绘，以及空闲后继续交互，持续运行无
  已知崩溃、画面损坏或无界资源增长。
- 正常退出到 DOS，恢复文本模式、光标和输入；再次启动仍可用。
- 通过既有 Window 图形显示路径完成真实交互。核对 Console 显示
  模式的既有图形能力，明确其支持/不支持边界，不将纯文本 Console
  输出当成 EGA 显示证明，也不无依据扩建 renderer。

对启动、DOS 服务、BIOS、中断、内存、EGA 寄存器/平面/调色板、
图形发布和输入的实际阻断点，记录原始 caller、owner、当前 provider
与首个确定的契约差异。按原始源恢复梯级修复完整相关边界，不能
靠 guest 补丁、跳过错误或截图替代真实运行。既有全局审计结论只在
输入变化或反证出现时重开。

## Windows 3.x 不经 WOW 的可行性调研

明确区分 3.0、3.1 与实际取得的其他 3.x 版本，以及它们各自存在的
real、standard、386 enhanced 执行模式。逐个核对真实支持条件，
不得推定每个版本都提供全部模式，或以一种模式的结果代表另一种。

这里的“非 WOW”指 Windows guest 自己的 kernel、USER/GDI、驱动和
应用在 NTVDM guest 内执行，不经 WOWEXEC/WOW32 将 Win16 调用转换为
宿主 GUI。原始 DOSX/DPMI 服务是否仍是某个模式所需的 DOS 边界，
必须单独确认；不能因为禁止 WOW 就盲目移除一切保护模式服务。

调研应产出逐版本/模式的可执行矩阵：

| 调研面 | 必须说明的事实 |
| --- | --- |
| 启动与 DOS 环境 | guest DOS 版本、配置、安装/驱动要求、启动链和实际最深到达点。 |
| CPU 与模式转换 | real/protected/V86 转换、异常、中断、descriptor、特权操作及选定 CCPU40 的实际可用边界。 |
| 内存与服务 | A20、XMS/EMS、DOSX/DPMI、VCPI 或其他实际依赖；哪些已经具备、哪些确实缺失。 |
| 设备与图形 | guest EGA/VGA 驱动、BIOS/端口/显存和键鼠路径；避免混淆 host WOW GUI 与 guest 显示。 |
| 386 enhanced 路径 | guest VMM/VxD 对机器和 DOS 的要求、与现有执行合同的冲突，以及是否能在当前源和架构内满足。不能预设可行或不可行。 |
| 修复归属 | 每个阻断点的唯一 owner、原始源依据、最小完整修复包、依赖、验证入口和架构限制。 |

利用合法取得的原始介质进行有界启动试验和定向观测；列出通过、
失败、未测试及缺少前提的情况。最终对各版本/模式分别给出：当前
可运行、存在明确可修复依赖、需要额外架构准入，或在现有约束下
不可行，并附证据。可行性结果不等于 Windows 3.x 实现交付；后续
实现按所有者决定单独准入，不静默扩大本候选包。

## 建议实施阶段

1. 冻结合法介质身份、配置、对照环境和实际构建；复用现有 CPU、
   DOS、内存、视频与输入证据，建立 Windows 1.01 运行 checklist。
2. 完成 Windows 1.01 启动至彩色 EGA 桌面的完整 host 边界修复，
   正式构建绑定与定向正负测试。
3. 完成 Windows 1.01 应用交互、重绘、输入、退出、模式恢复和重复
   启动验收，保留真实画面及操作证据。
4. 按版本/模式调研 Windows 3.x 非 WOW 启动，形成依赖和可行性矩阵，
   明确未达边界与后续修复归属。
5. 全量回归、源/diff 与介质不可变复核，形成两个目标各自的结论，
   交付 Windows 1.01 成果及 Windows 3.x 调研，提交所有者验收。

这些是提议阶段，不是当前活动 S。准入时根据实际依赖划定有界 S；
新增机器执行行为按项目完整契约组要求验证，不采用 trace 叶子修补。

## 来源、约束与验收

遵循[来源与研究政策](../etc/operations/policy/source-policy.md)及
[架构规则](../rules/ARCHITECTURE.md)。取得介质前确认来源、使用和
再分发边界；保留版本、来源、SHA-256、大小、驱动和配置清单。
所有原始 guest/固件不可重编译替换、二进制修补或运行期热补丁。
正常 guest 执行和工作文件写入遵循政策；测试保留基线和可恢复副本。
Windows 10 对照环境不能变成本产品的链接、运行或发布依赖。

产品继续采用 Win32/x86 /MT CCPU40；不引入 CPU30、第二模拟器、内核
驱动、CSRSS 替代、宿主系统修改或新的 helper。原始源、现有 adapter
和完整依赖合同优先。需要额外架构或资源时记录明确边界并重新准入，
不能以运行目标为由隐式突破源策略。

每个实现阶段补充实际 production caller/provider 的可复现测试和
断言，涵盖正常、失败、模式切换、重复启动与资源清理。运行证据
记录 guest 介质、启动命令、配置、构建身份、操作步骤、画面、返回
和限制。沿用当时正式 x86 构建、Console/Window、DOS/Win32/WOW、
生命周期与协议回归，代码交付遵守一致八文件发布和恢复要求。
图形交互无法实测则相关验收保持未完成，不能用编译成功或 unit
fixture 替代“Windows 1.01 跑通”。本次 proposal 仅规划，不声称已
研究或验证任何 Windows 版本的兼容性。
