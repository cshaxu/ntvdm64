# WOW32 everyday three-application usability acceptance

## Objective and admission

Unadmitted candidate added by the owner's 2026-10-12 approval. The refined
sequence is basic functionality, basic display, comprehensive interaction,
comprehensive display, then comprehensive functionality. This checkpoint
concludes the comprehensive-display phase before extended services.
Queue owns its position; this proposal allocates no numeric T and does not
change the active packet. This is a bounded product milestone, not a second
provider implementation or a claim that all WOW32 capabilities are complete.

## Scope and prerequisites

Use one identified ordinary product package and immutable WINMINE, SOL and
WRITE inputs. Consume the preceding execution, object, loader, file, resource,
graphics, text, input, menu, ordinary-dialog, clipboard, Shell and necessary
error-handling results, plus the window-residue investigation. Require only
actual prerequisites for the tested everyday behaviours. Complete the retained
display stages, including font/metric, palette, resource and metafile contracts,
through their original owners before this checkpoint. OLE and device families
retain their named owners and remain unaccepted;
they must not delay this milestone unless an actual failing call proves a
dependency. Missing required implementation returns to its owner rather than
being hidden inside acceptance code or bypassed by altered guest media.

### Minimum-diff admission gate

This candidate is **Acceptance** under the shared [WOW32 minimum-diff admission
governance](../etc/operations/wow32-queue-minimal-diff-admission-governance.md),
which links its work to the external OpenNT-only seam ledger. Before production
implementation, record the original owner, build condition, ABI and
normal/failure/retirement ownership for every changed edge. consume completed owner evidence only and return each defect to its named owner. Static
ledger closure, a symbol match or a successful link does not prove this
candidate's product/runtime behavior.

## Proposed stages

| Stage | Work | Required evidence |
| --- | --- | --- |
| S1 | Freeze ordinary package and application baseline | Source/package/guest/configuration hashes, actual first failing call for any startup error, and explicit prerequisite/deferred-family ledger. |
| S2 | Display and interaction | WINMINE board, digits, face, reveal/flag, timer, menu/new game; SOL cards, deal, legal movement, draw/options (including the observed Options-route `WOW32.DLL` access violation, source-traced to its actual owner before repair); WRITE readable text, edit/select, menus/dialogs, clipboard, save/reopen and cancellation. Repaint/expose, activation and supported resize preserve correct content without residual frame pixels. |
| S3 | Lifecycle and owner acceptance | Normal close/restart, supported multiple tasks, scoped abnormal cleanup and subsequent DOS use; reproducible tests, reviewed captures and applicable production delivery gates. |

Each application must actually work: a window, process exit or matching old
error dialog is not a functional pass. Record failures separately and do not
offset a regression in one app by improvement in another. Physical observation
limits remain explicit; no full pixel-equivalence claim follows from a probe
that merely compares two already incorrect frames.

## Boundaries and handoff

No printer, serial endpoint, network or multimedia test is imposed merely to
prove these everyday scenarios. This does not remove those selected capability
obligations. The [WOW32 program](proposal-wow32-production-completion-002.md)
continues to own shared source-first, immutable-media, test and delivery rules.
Background-owned probes/builds remain under build; preserve unrelated sessions.

Deliver checked-in reproducible tests and exact content/result assertions,
normal/negative/cleanup evidence and the coherent published package required
by the execution rules. Owner acceptance closes only this everyday milestone.
The later [whole-provider acceptance](proposal-wow32-integrated-acceptance-001.md)
repeats these scenarios after extended capability completion and reconciles
all remaining original obligations; neither checkpoint absorbs unfinished
provider repairs or reports deferred functionality as passed.
