# 1.1 — Guest mirror, build variants, and WOW loading

## Boundary and local closure

This section owns the route from a selected OpenNT WOW32 source recipe through loader entry, module lookup, explicitly bounded dynamic binding, and the publication prerequisites that make later WOW startup possible. It does **not** own task execution (1.2), task retirement (1.3), Guest address translation (2.1), generic call-frame ABI (2.2), callback rundown (2.3), or any device family merely because it is loaded here (Part 5).

The static audit is pinned to OpenNT commit `5c5b979ec08c17d3ca2eb70e8aad62d26515d01c`. The local WOW32 `sources` file names `W32DllInitialize` as `DLLENTRY`, but also depends on a generated DEF and the shared NT build recipe. It establishes selected source-recipe membership; it does not prove the generated DEF, import table, inherited compiler settings, or final binary.

| `WOW32_LOADER::W32DllInitialize` | entry / D | DLL attach, later thread notifications, and detach have distinct source branches and failure effects. | Bootstrap publication: 1.2; callback rundown: 2.3; terminal order: 1.3. |

The ledger marks these bounded source contracts `closed`; this is **static audit closure only**. Their implementation-validation state remains separate and no runtime or emitted-image equivalence is asserted here.

## Loader entry is not session readiness

`base/mvdm/wow32/sources:24-26` selects the DLL entry and declares a generated DEF dependency (recorded SHA-256: `d24767ff50c4c7017e6fcf5f550e120db0f580f7c07c77cbe7e99e4432f52b36`). `base/mvdm/wow32/wow32.c:184-282` supplies the selected entry body (SHA-256: `1dfe9900e6da3bf0e2984c3df42bdd155b177cfe7707bb24e1324037147d292a`). The contract is a private loader callback shaped as `BOOLEAN(PVOID, ULONG, PCONTEXT)`, not `BOOL WINAPI`. The original NTDLL path consumes the low-byte `BOOLEAN` result on x86; a modern adapter must preserve the observed result domain instead of casually converting it to an unrelated Boolean ABI.

The source distinguishes process attach, thread attach, thread detach, and process detach. It also distinguishes attach failures from a critical-string diagnostic path that continues. Therefore a compatibility carrier must:

1. keep its loader-locked portion to module/reason capture and a local state transition;
2. move User, GDI, library loading/unloading, UI, and executor work outside that loader-locked portion;
3. retain the two attach-failure gates separately from the diagnostic-and-continue path;
4. own cleanup after partial preparation instead of assuming that an automatic detach will repair all state; and
5. keep `W32Init`/session bootstrap separate from successful DLL attachment.

This is a minimum-diff constraint, not an invitation to reproduce old loader internals. The valid modern shape is a small typed loader adapter whose only job is to preserve the recorded phase and result semantics. It may not become a second session manager.

Evidence: `base/ntdll/ldrsnap.c:638-650,707,748-839,2839-2868`, `base/ntdll/ldrapi.c:235-245,711-737`, and `base/ntdll/ldrinit.c:1226-1245,1336-1356,1430-1453` explain the selected OpenNT loader-call convention and notification branches. They are evidence for this narrow callback interface, not an audit of all NTDLL or a claim that a modern loader can host an original 32-bit DLL unchanged.

## Dynamic loads: identity, request, invocation, and support are different

The ledger has a specifically bounded WOW32 dynamic-binding inventory: 143 registered source requests in the selected tables, of which 67 are active source requests and 76 are literal `#if 0` exclusions. The active requests occur as 2 WinMM private names, 15 print names, 49 Winsock ordinals, and one OLE name. It separately records 181 active concrete locations and 161 disabled locations. These are request and location counts—not a function count, a linked-image count, or a supported-feature claim.

The following non-inferences are mandatory:

- `LoadLibrary`, `GetProcAddress`, or an ordinal in a source table does not prove that the module loaded, that lookup succeeded, that the callee ABI is valid, or that every caller's semantic contract survives.
- A disabled `#if 0` wrapper is deliberately excluded from the active set. It must not be presented as a supported route merely because its name occurs in source.
- A Guest MMSYSTEM initialization lookup is a separate Guest census. It explains expected call shape or loading order, but cannot inflate the WOW32 table denominator.
- A generic `LoadLibrary` macro call may select A or W through inherited build state. Until an emitted image settles that selection, the two source aliases stay build alternatives rather than two active services.

`WK32LoadLibraryEx32` is a useful example of the required precision. Its 12-byte unaligned Guest wire is flags, file handle, then a Guest virtual string pointer; the selected wrapper also synchronizes the current directory. The Guest export is `LoadLibraryEx32W`, while the provider's selected source call is encoding-neutral. A modern carrier must preserve this named wire, failure and lifetime boundary; it must not expose a native64 module handle or turn an arbitrary host DLL into a callable Guest service. Free/unload while functions or callbacks are still in flight is owned by 1.3/2.3, not implied by successful loading.

## Bootstrap publication is typed, ordered, and not pointer flattening

`WOWNOTIFYWOW32` is a void Guest-to-WOW32 bootstrap publication. The Guest builds seven `VPVOID` fields in `base/mvdm/wow16/kernel31/wow16cal.asm:1140-1178`; the dispatch binding is `base/mvdm/wow32/wktbl2.h:300-306`; the selected WOW32 consumer/provider is `wkman.c:69-75,1349,1643-1648,2813-2831,3484-3509`.

The required semantics are narrow but important:

- retain all seven fields as Guest virtual-address roles, in source order;
- map only the designated two-byte views for current TDB and current-directory owner where the selected consumer does so;
- publish a self-consistent typed registry before dependent task, directory, or file-cache services run; and
- close admission and retire aliases before the relevant Guest storage can be released.

It is incorrect to flatten the seven values into host pointers, export those pointers through a native64/broker boundary, or invent a consumer for the selected-unused interrupt field. The source proves a publication protocol; it does not prove repeated-publication behavior, all concurrent consumers, exact mapping failure behavior, or runtime teardown ordering.

## Implementation constraints and validation receipts

The smallest acceptable modern integration retains immutable Guest bytes and keeps each unavoidable substitution behind a named, typed adapter. The adapter needs a documented owner for loader phase state, module identity, Guest-view lifetime, callback admission/rundown, failure mapping, and terminal cleanup. No broad loader shim, global pointer map, or new scheduler is justified by this section.

Before an implementation can be promoted under 6.3, retain receipts for at least these cases:

1. process attach failures before and after small-heap creation, plus the independent diagnostic-and-continue case;
2. successful attach followed by separate bootstrap failure, with no dispatch advertised as ready;
3. initial versus later thread notifications, without loading UI or executor work under loader lock;
4. an active dynamic request, a disabled request, a missing export, and a valid lookup whose ABI call is intentionally unavailable;
5. seven-field bootstrap publication, including unready and retirement races; and
6. actual emitted entry convention and selected A/W imports.

None of these receipts exists merely because the static source seam is closed.
