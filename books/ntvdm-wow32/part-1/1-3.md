# 1.3 — Session exit, cancellation, and controlled retirement

## Boundary

This section owns selected terminal routes from a live WOW task/session into retirement: normal task exit, failed activation, forced-exit request, task-specific versus all-session notification, and the release-order coordinator. It does not claim every delegated provider has completed cancellation or that a source terminal request alone drained later callbacks.

| Canonical seam | Unit / class | Bounded source conclusion | Not implied |
| --- | --- | --- | --- |
| `NTVDM_WOW_TASK_TERMINATION_ENTRY_AND_SHARED_LIST_RETIREMENT` | protocol / D | Guest exit removes task-visible state before final host-thread retirement. | Shared-map failure may not silently skip the exit route. |
| `WOW32_TASK_RETIREMENT::W32DestroyTask` | entry / D | A local coordinator orders selected destruction phases and delegates providers. | Return does not prove every provider completed cancellation. |
| `WOW32_TASK_RETIREMENT::W32FreeTask` | entry / D | Task-resource release is distinct from the outer destroy path. | It is not a global completion barrier. |
| `KERNEL32_PRIVATE::ExitVDM` | entry / D | Task-specific and all-session notifications have distinct request/acknowledgement roles. | A broker notification is not completed cleanup. |
| `WOW32_TASK_RETIREMENT::W32EndTask` | entry / D | The hung-task route makes a Guest forced-exit request. | Requested forced exit is not observed termination. |

The local static contracts are closed. Late callback admission, actual asynchronous cancellation, thread completion, host handles, image selection, and runtime behavior remain separate validation receipts.

## Request, acknowledgement, and completion are three states

The audit treats these as distinct facts: a component requests termination or cancellation; a peer/broker acknowledges the request; and every admitted producer has stopped using the retiring task, Guest view, and provider state. OpenNT source establishes selected ordering for the first two states. It does not establish the third universally.

The normal Guest terminal route is `base/mvdm/wow16/kernel31/tasking.asm:253-271`: it clears selected task state, performs the zero-payload `WowKillTask` thunk, and jumps to the terminal route. `kthunks.asm:58-64` establishes that thunk form. The selected host-side path is `base/mvdm/wow32/wkman.c:1211-1232,4203-4250`, which reaches `WK32KillTask`, `W32DestroyTask`, shared-list removal, and `host_ExitThread`.

A modern carrier must therefore retire task-visible identity before final host-thread retirement, keep Guest task identity, native thread identity, and native handle lifetime as separate domains, and give each delegated cleanup provider a named completion owner. It must not turn a shared-map failure into a bypass of the source terminal branch.

## Coordinator order and late work

`W32DestroyTask` (`wkman.c:1683-1737`) follows selected InitTask-failure, execution-return, KillTask, and remote-thread routes. `W32FreeTask` (`wkman.c:1435-1561`) is an adjacent coordinator, not proof that callbacks, I/O, native messages, or provider modules are gone. The required modern safety addition is explicit:

1. close admission for new callbacks and asynchronous work targeting the task;
2. cancel or detach each producer under its own contract;
3. await its explicit completion/rundown condition;
4. retire aliases, shared views, and task-visible state in recorded order; and
5. only then release Guest-backed storage, provider code, and final host-thread resources.

This is not a claim that the original source has a verified use-after-free error. It records the limit of static evidence: a notification or terminal request does not itself prove producer drain. Frame restoration belongs to 2.2 and generic admission/rundown belongs to 2.3; USER, DDE, multimedia, serial I/O, and Winsock retain their own producer details in their later sections.

## Forced exit and session notification

`W32EndTask` (`wkman.c:3017-3035`) issues a `RET_FORCETASKEXIT` callback request. Its local source fact is a request boundary, not a final-destruction guarantee. The selected hung-app policy has private USER/server and UI dependencies and is not promoted here to a general callback conclusion.

`ExitVDM` has a separate client/server notification route: `base/win32/client/vdm.c:729-785` creates the selected client request and `base/win32/server/srvvdm.c:457-467` dispatches the WOW server side. A correct modern carrier keeps task-specific and `ALL_TASKS` notification distinct, exposes acknowledgement independently from terminal state, and never leaks a raw wait handle across its Guest or cross-bitness boundary.

## Required validation cases

6.3 receipts must distinguish: normal task retirement and last-task notification; InitTask failure and unexpected execution return; a delayed/rejected/returning forced-exit request; task-specific versus all-session notification; pending callback, posted work, I/O cancellation, and provider-unload races; shared-list/map success and failure; and final thread/handle retirement only after named producer rundown.
