# 1.2 — WOW startup, capability publication, and session entry

## Boundary

This section starts after 1.1 has admitted the loader route and ends at the point where a boot or non-boot Win16 task may enter the original execution domain. It owns capability publication, readiness ordering, task-creation handoff, and the distinction between task creation, task readiness, and execution transfer. It does not audit the CPU/V86 engine, every callback ABI, or all later service behavior.

| Canonical seam | Unit / class | Bounded source conclusion | Handoff |
| --- | --- | --- | --- |
| `WOW32_TASK_ACTIVATION::WK32WOWInitTask` | entry / D | Boot and non-boot activation are distinct; non-boot creates suspended before creator handoff. | In-thread transition: `W32Thread`; ABI: 2.1–2.3. |
| `WOW32_TASK_ACTIVATION::W32Thread` | entry / D | Selected task/USER/creator/idle transitions precede entry to execution. | Engine execution excluded; terminal paths: 1.3. |
| `NTVDM_WOW_SUPPORT::host_CreateThread` | entry / D | The wrapper starts a non-boot thread suspended and transfers startup context once. | Actual thread model and cancellation: 1.3/2.3/6.2. |
| `NTVDM_WOW_SUPPORT::BlockWOWIdle` | entry / D | A typed blocked/runnable transition is not proof of wake or dispatch completion. | Timer/interrupt delivery excluded. |
| `USER32::UserRegisterWowHandlers` | entry / D | Native IN/OUT tables and shared information are a typed, directional publication. | Per-slot behavior: 4.1/4.2; rundown: 2.3. |

All are statically closed within the cited OpenNT slices. This does not mean that a modern session manager, thread carrier, USER provider, image selection, or live execution has been validated.

## Publication before use, not publication as proof of support

The original path publishes several kinds of state: native callback/resource tables, selected Guest views, task-creation capability, and an explicit creator/readiness synchronization. These are not interchangeable.

The USER registration route illustrates the boundary. `wow32.c:521-547` builds a local `PFNWOWHANDLERSIN`, passes it to `UserRegisterWowHandlers`, receives a separate OUT buffer and a shared-info result, then installs the Base GlobalFree-hook path separately. The provider in `windows/core/ntuser/client/client.c:2256-2315` copies the input values into provider-owned storage and fills typed output slots. The selected declaration is in `public/internal/windows/inc/wowuserp.h:30-74,92-143,217-218`.

The resulting requirements are deliberately narrow:

- IN and OUT tables remain separate directional native32 data. They are not a Guest wire layout and must not be flattened into a native64 or broker payload.
- The provider keeps copied values, not a borrowed pointer to the caller's stack-local input table.
- Publication must make either a coherent registered set or the documented pre-registration default visible; it must not expose a torn mixture.
- A registration operation does not validate targets, allocate/free callback state, cancel work, or drain callbacks. Those are later contracts.
- A modern carrier needs an epoch/admission-and-rundown rule before it replaces or retires provider code, aliases, or shared views. That is a modern safety requirement; it is not retroactively asserted as a complete OpenNT guarantee.

`RegisterWowBaseHandlers` is even narrower: the selected original operation is a native slot setter with initial-NULL, replace, and clear semantics. It must not be widened into a cross-process callback registry or used to claim complete DDE support. The synchronous pre-free consumer and its pair-lifetime semantics belong to their own DDE/clipboard owners.

## Task activation has three distinct milestones

For a non-boot task, `WK32WOWInitTask` in `base/mvdm/wow32/wkman.c:514-596` selects a suspended host-thread route and publishes task/creation state. The selected dispatch binding is `wktbl2.h:356`. `host_CreateThread` in `base/mvdm/softpc.new/host/src/nt_thred.c:22-111` confirms the immediate wrapper and its single startup-context transfer. A successful thread-create return is not a runnable-task proof, and a runnable-task transition is not a proof that the Guest execution loop has started.

`W32Thread` (`wkman.c:780-1207`) makes the separation observable: it initializes task-side state, coordinates with USER and the creator, signals readiness, and only then performs the selected execution-domain transfer. A valid modern implementation therefore preserves the following order without duplicating a scheduler:

1. distinguish the boot route from the non-boot route;
2. begin non-boot creation suspended;
3. publish no usable task capability on create failure;
4. transfer the startup context exactly once;
5. expose the creator-ready signal separately from host-thread creation; and
6. enter the execution domain only after the selected task/USER/idle sequence.

The original `host_simulate` and fast callback declarations are evidence for a transfer boundary only. They do not make SoftPC/V86 implementation part of this audit, and they do not permit raw host pointers, thread contexts, or stack tokens to cross a modern carrier.

## A gate request is not a quiescence guarantee

The activation records also separate logical scheduling requests from physical completion. `BlockWOWIdle` in `nt_eoi.c:92-123` changes the selected blocked or runnable state under its local discipline. `TaskTimerActivationGate` records that suspend/resume requests are issued in a conditional task-start order; the selected timer provider explicitly does not prove that a heartbeat has already quiesced. Therefore a modern adapter may record typed request acceptance, but must not treat it as evidence that an asynchronous producer stopped. Shutdown and callback admission remain 1.3/2.3 work.

## Required negative cases

Implementation validation under 6.3 must retain receipts for these different outcomes rather than merge them into “startup failed”:

1. boot activation bypasses host-thread creation;
2. non-boot allocation or thread creation fails, leaving no creation capability;
3. a created but suspended task has not yet signalled its creator;
4. `InitTask` fails after creation, with a terminal handoff but no execution transfer;
5. the execution route returns unexpectedly, with its distinct terminal handoff; and
6. provider replacement or session retirement races with a pending callback, demonstrating explicit admission closure and rundown.

## Evidence and limits

| Evidence slice | Establishes | Does not establish |
| --- | --- | --- |
| `wkman.c:514-596,780-1207`; `wktbl2.h:356` | selected boot/non-boot, creator, and in-thread activation order | full Guest task/selector ownership, emulator behavior, final image |
| `nt_thred.c:22-111`; `softpc.h:194-201` | suspended-first wrapper and one startup-context transfer | all hook, restart, cancellation, and cross-bitness behavior |
| `wow32.c:521-547`; `client.c:2256-2315`; `wowuserp.h` | typed native registration and copied publication values | semantic correctness of each callback slot or provider teardown |
| `nt_eoi.c:92-123`; `nt_timer.c:907-950` | selected logical block/gate request transitions | wake, interrupt delivery, heartbeat completion, or full shutdown |
