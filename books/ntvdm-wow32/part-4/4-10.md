# 4.10 — Clipboard and USER DDE

## Boundary

Clipboard and USER DDE own data conversion, open/close state, delayed rendering, publication/return, DDE message pairing, and task/window loss. These are lifetime protocols, not mere wrappers.

## Semantics that must survive

Preserve payload owner, transfer point, rejected-post/missing-peer behavior, and whether callbacks may run after replacement or exit.

## Modern-host discipline

Use copied/versioned records and bounded buffers as required. Do not create generic payload registry, retain Guest pointers asynchronously, or merge USER DDE with DDEML without proof.

## Handoff boundary

Generic messages are 4.2; DDEML/OLE 5.4; task teardown 1.3/2.3.

## Review questions

1. Which original owner decides success, failure, and cleanup?
2. Which structures, handles, buffers, or callbacks cross the seam?
3. Who is authoritative before, during, and after reentry or retirement?
4. Which normal, negative, reentry, cancellation, and destruction cases prove the route?

## Evidence and current limit

Relevant audit material: Clipboard ownership/materialization/priority, DDE memory, posted-message ownership, and reply-lifetime records.

This page is source-contract guidance; it is not a claim of complete product implementation or runtime support.

## Clipboard cache, delayed rendering, and conversion

`WU32OpenClipboard` converts a Guest window alias then returns a 16-bit
Boolean (`wuclip.c:628-640`). `EmptyClipboard` calls the native operation and
then `W32EmptyClipboard` (`wuclip.c:130-141`). Format registration returns a
`WORD`; the selected source records the historical `0xC000..0xFFFF` result
range and same-name reuse behavior (`wuclip.c:644-684`).

`WU32GetClipboardData` first consults a 16-bit cache for memory formats. On a
miss it obtains native data, allocates `GMEM_MOVEABLE | GMEM_DDESHARE` Guest
storage, copies and flushes it, then stores the 16-bit handle
(`wuclip.c:224-305`). It reacquires the frame and argument view after Guest
allocation because that allocation may move 16-bit memory. Therefore a modern
carrier must revalidate a Guest view after a moving allocation rather than
retain borrowed pointers across it.

The provider uses different representations for `CF_HDROP`, bitmap/palette,
and metafile pictures (`wuclip.c:308-385`). The inverse `SetClipboardData`
route separately converts ordinary global memory, dropfiles, GDI objects, and
metafile pictures (`wuclip.c:813-930`). A null data handle represents delayed
rendering; the source says the owner receives `WM_RENDERFORMAT` when data is
required (`wuclip.c:710-718`). A later read can thus materialise cached Guest
data, but that does not prove callback scheduling or platform behavior beyond
this selected source.

`W32EmptyClipboard` releases cached per-format Guest objects and registered
format nodes (`wuclip.c:1112-1189`). The minimal modern carrier is a
session-owned, format-tagged record with an owner/window generation, carrier
kind, materialisation state, and one retirement transition. It must not retain
raw Guest views asynchronously.

## USER DDE is a pair registry with ordered retirement

`HDDE` records endpoint window aliases, a 16-bit and native memory handle,
message, format, flags, and original 16-bit handle (`wdde.h:23-44`);
`DDEDATA16` and `DDEDATA32` differ specifically in their handle-sized `Value`
field (`wdde.h:73-91`). `DDEAddhandle` persists this context and marks the
Guest object via `RET_WOWDDEFREEHANDLE` (`wdde.c:620-665,818-836`). Pair lookup
uses both endpoints plus the relevant handle (`wdde.c:705-810`).

The release ordering is explicit. `W32DDEFreeGlobalMem32`, called on native
free, unmarks/frees corresponding Guest objects and removes pairs; metafiles
receive a special path (`wdde.c:842-879`). In the Guest-free direction,
`W32DdeFreeHandle16` removes a pair **before** calling `GlobalFree(h32)` so
the native pre-free hook cannot reenter a still-present mapping
(`wdde.c:905-944`). `WM_DDE_EXECUTE` instead sets deferred-free state and
returns false (`wdde.c:917-921`). This establishes a remove-before-free
semantic requirement, not a source-level bug claim.

The source does not prove concurrent access safety for its linked lists. A
modern implementation must provide session serialization or equivalent proof,
while preserving endpoint, format, message, and ownership context.

## Narrow OLE descriptor bridge and validation receipts

Startup registers `Object Descriptor` and `Link Source Descriptor`; first use
lazily resolves `OLETHK32.DLL!ConvertObjDescriptor` (`wuclip.c:1212-1245`).
The get path requests Unicode-to-ANSI conversion and the set path requests
ANSI-to-Unicode (`wuclip.c:244-252,831-838`). This proves neither a general
OLE implementation nor dynamic-import availability in a modern image.

Runtime validation must cover open → empty → set → close → get; delayed
rendering during owner/window retirement; moving Guest allocation and view
reacquisition; each carrier type; both DDE free directions; recursive pre-free
entry; the `WM_DDE_EXECUTE` deferred-free path; missing peer/rejected post;
and conversion allocation failure. A success result alone is not proof that
callbacks, posted messages, or pair records have drained.

remain [1.3](../part-1/1-3.md) and [2.3](../part-2/2-3.md); DDEML/OLE API
contracts are handed to Part 5; cross-cutting carrier traces belong to
[6.3](../part-6/6-3.md).
