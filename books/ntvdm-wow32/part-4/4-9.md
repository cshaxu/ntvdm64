# 4.9 — Shell, launch, environment expansion, and compatibility Registry

## Boundary

This chapter owns the narrow Shell-facing part of Win16 support: the private
Shell dispatch table, `ShellExecute` and its reverse `WinExec` callback, the
separate `WOWLoadModule` / WinOldAp process-lifetime route, environment-string
expansion, and the old Win3.1 Registry request family. It does **not** own a
general Windows shell, a DDE transport, file-system/path conversion, or a
modern process supervisor. DDE is handed to [4.10 — Clipboard, DDE, and OLE
handoff](4-10.md); path identity belongs to [3.2 — Paths, configuration, and
named pipes](../part-3/3-2.md), and callback-frame rules belong to [2.3 —
Callback frames and reentry](../part-2/2-3.md).

The selected OpenNT baseline is commit
`5c5b979ec08c17d3ca2eb70e8aad62d26515d01c`. All source locations below are
static-source evidence only. They do not prove the emitted historical image,
a current Windows carrier, or product runtime support.

These are five distinct ledger identities across entries and a protocol. They

## 1. Private Shell table and its wire frames

The Shell table maps `RegOpenKey`, `RegCreateKey`, `RegDeleteKey`,
`RegSetValue`, `RegQueryValue`, `ShellExecute`, and `DoEnvironmentSubst` to
`WS32*` providers (`wow32/wshtbl2.h:15-20,38,57`). The data crossing that
dispatch is not a native ABI: `REGOPENKEY16` and `REGCREATEKEY16` each carry
two `VPVOID` fields plus a `DWORD`; `REGSETVALUE16` carries three `DWORD` and
two `VPVOID`; `REGQUERYVALUE16` carries one `DWORD` and three `VPVOID`
(`inc/wowshell.h:48-88`). `SHELLEXECUTE16` is likewise a `HAND16`, four
`VPVOID` fields, and a `WORD` (`inc/wowshell.h:132-140`).

Consequently a modern carrier must decode each Guest view, copy or pin it for
the duration actually required, then flush defined output fields before
release. Passing a host pointer, a host `HKEY`, or a host process handle back
as an untyped 16-bit value would invent a new seam rather than preserve the
old one.

## 2. ShellExecute is a two-direction request, not a fire-and-forget launch

`WS32ShellExecute` maps the window alias and four Guest strings, calls the
private `WOWShellExecute`, then converts the returned instance-like value with
`GETHINST16` (`wshell.c:792-822`). Its source comment explicitly says that
the returned value may be either an instance handle or a DDE-server handle
(`wshell.c:786-790`). That ambiguity is evidence against treating every
nonzero result as a process identity or completion signal.

The provider is also given `W32ShellExecuteCallBack`. On callback,
`wshell.c:826-849` first updates the DOS current directory in the NT-to-DOS
direction, allocates a temporary Guest string, copies the command line, and
uses `CallBack16(RET_WINEXEC, ...)` with `fuCmdShow` in `wParam`; it releases
both temporary mappings after the synchronous callback returns. The direct
evidence proves this allocation/callback/release sequence. It does **not**
prove that a private provider always invokes the callback, what thread it
uses, its DDE policy, or that callback entry has already been drained during
task termination.

The minimal-diff carrier is therefore: retain the existing callback-frame and
Guest allocation machinery; represent the launch request separately from any
process record; admit reverse callbacks only while the task is live; and make
the callback data unavailable after its synchronous frame has retired. The
carrier must test success, a provider failure, no callback, a callback while
the target task is exiting, and a result that is a DDE handle rather than an
instance-like launch result.

## 3. WinOldAp process records are a lifetime protocol

`WK32WOWLoadModule` begins by synchronising the DOS current directory
(`wkman.c:1930-1941`). The `lpModuleName == NULL` case is a distinct WinOldAp
wait/cleanup route: it extracts the encoded process handle, blocks WOW idle,
waits while pumping input, obtains the exit code, removes the tracking record,
closes the handle, and unblocks idle (`wkman.c:1943-2008`). That is stronger
than “launch occurred,” but it still is not proof that every external producer
or callback has quiesced.

For a new launch, the source parses legacy command-line forms, chooses the
show state from the two-word parameter block with the Win3.1-compatible
fallback to `SW_NORMAL`, then invokes `CreateProcess`
(`wkman.c:2011-2156`). Success records the process ID, process handle,
upper-cased module identity, and a task-local `WOAINST` list node
(`wkman.c:2192-2262`); it returns a specially encoded command string and
`33` (`wkman.c:2330-2334`). Selected failure mapping is file-not-found `2`,
path-not-found `3`, bad-exe-format `11`, otherwise `0`
(`wkman.c:2336-2355`).

A current implementation needs a session-owned launch-token registry rather
than a raw handle in Guest-visible memory. Its record needs an owner task,
process/wait capability, legacy module identity, launch state, and one
retirement path. It must preserve the result mapping and the distinction
between launch acceptance, input-idle waiting, process exit, tracking-record
removal, and handle release. The source notes that task teardown frees
remaining `WOAINST` records without itself closing or terminating their child
process handles; that observation is not a verified leak or fault claim.

## 4. Compatibility Registry means policy, not system-Registry mutation

The original providers treat `WIN16_HKEY_CLASSES_ROOT` as the native class
root and, for a null root, transform a `Classes`-prefixed path before using the
class root (`wshell.c:123-233,453-521,526-655`). They write returned key or
size fields through Guest mappings and call `ConvertToWin31Error`. These are
observable compatibility rules.

Three details are especially important. First, deleting a null or empty
subkey returns `ERROR_BADKEY` (`wshell.c:261-314`). Second, the helper
recursively removes subkeys because the documented Win3.1 behavior differs
from the selected Win32 deletion behavior (`wshell.c:319-446`). Third,
`RegSetValue` accepts only `REG_SZ`, ignores the supplied byte count, and
normalises null/empty data to the string `"0"`; `RegQueryValue` constrains the
historical value size to below 64 KiB and writes the final size/data back to
Guest memory (`wshell.c:453-655`).

For a modern host, reproduce this narrow virtual compatibility namespace and
its error/value policy under one session owner. Do not write the machine or
user system Registry merely to emulate a Win16 program. This is not a claim
that the OpenNT source used such virtualization; it is the minimal-diff
modern carrier boundary. Validate root mapping, null-root path rewriting,
non-`REG_SZ` rejection, empty-value normalisation, recursive-delete behavior,
short buffer, missing output-size pointer, allocation failure, and per-task
cleanup/isolation.

## 5. Environment expansion has a packed result contract

`WS32DoEnvironmentSubst` receives only a buffer capacity and a Guest string.
It expands into temporary host storage. If the result fits, it overlays the
Guest buffer, flushes it, and returns a packed `MAKELONG(expandedLength, TRUE)`;
if it does not fit or allocation fails, it leaves the original string intact
and returns `MAKELONG(cch, FALSE)` (`wshell.c:46-116`). The returned length
excludes the terminating null on success. Replacing this with an unbounded
string helper or a host exception changes the observable API.

## Closure and handoff

Static audit closure for these five identities means their selected source
wire, provider route, compatibility rules, and explicit limits are recorded.
It does not close effective build selection, private `WOWShellExecute`
implementation, DDE conversation ownership, callback scheduling, current
Windows launch policy, or runtime lifetime safety.

Implementation evidence must include frame-layout decoding, Guest flushes,
callback admission/rundown, launch-token retirement, exact legacy result
mapping, and a session-scoped Registry store. Cross-cutting runtime receipts
belong to [6.3 — Carrier verification and trace evidence](../part-6/6-3.md).
Hand off DDE-specific data/pair lifetime to [4.10](4-10.md), generic task
termination to [1.3](../part-1/1-3.md), and path/current-directory mapping to
[3.2](../part-3/3-2.md).
