# 4.1 — Windows, classes, and private WOW metadata

## Scope and audit state

This section owns the selected source contracts that make a native USER window recognisable as a WOW window: private metadata, create/destroy projection, and procedure-token replacement. It does **not** own the complete modern window tree, all geometry/text/style operations, message delivery, dialog behaviour, or control semantics. Those remain in their named Part 4 sections.

The evidence baseline is OpenNT commit `5c5b979ec08c17d3ca2eb70e8aad62d26515d01c`. Each identity in the table is source-contract closed only. None says an emitted OpenNT image or a modern runtime has been verified.

| Canonical identity | Boundary | Class | Selected result |
| --- | --- | --- | --- |
| `USER_PRIVATE_WOWWORDS_READ` | three private WOW fields, read by mapped native window | D | The original reads class/state, Guest window procedure, and Guest dialog procedure through private WOW storage. |
| `USER_PRIVATE_WOWDWORD_WRITE` | the same three fields, written with ordered publication | D | The original keeps class/state, WNDPROC, and DLGPROC logically distinct. |
| `USER16_WINDOW_CONSTRUCTION::CREATEWINDOW_CREATEWINDOWEX_CLASS_BINDING` | Guest creation frame to HWND16/class binding | C | Class lookup precedes creation; success projects an alias and associated metadata. |
| `USER16_WINDOW_CONSTRUCTION::DESTROYWINDOW` | Guest window alias to native destruction outcome | C | The wrapper maps the handle, projects a 16-bit Boolean, and invalidates a selected cache. |
| `USER16_PROCEDURE_REPLACEMENT::WINDOW_CLASS_AND_DIALOG_TOKENS` | Guest/native procedure identities and prior-procedure result | C | WNDPROC, class procedure, and dialog procedure have different branches and cannot share a raw pointer representation. |

These are five canonical seam identities, not “all USER functions.” [The evidence model](../evidence-model.md) explains why this chapter does not turn lexical matches or callsites into an API-total denominator.

## 1. Private WOW state: metadata, not public window data

The OpenNT private USER indices are negative (`public/internal/windows/inc/winuserp.h:79-82`). The `WW` layout in `wowuserp.h:147-214` defines three DWORD-scale logical values: class/state, `vpfnWndProc`, and `vpfnDlgProc`. `walias.c:187-230` reads the selected private storage through `FindPWW`; selected private USER code maps the three reads through `GWL_WOWWORDS` (`windows/core/ntuser/rtl/getset.c:304-321`). Writes are visible through `wcall32.c:224-248`, `walias.c:204-229`, and `windows/core/ntuser/kernel/getset.c:686-701`.

The important fact is not the old private index itself. It is the separation of the three meanings:

| Logical field | Must not be confused with |
| --- | --- |
| class/state classification | an application-defined window extra word or current public style |
| Guest window procedure identity | a raw host function pointer or the dialog procedure |
| Guest dialog procedure identity | the WNDPROC slot or a general-purpose `GWLP_USERDATA` value |

A modern host cannot depend on NT4-private `GWL_WOWWORDS` storage. The smallest compatible carrier is a typed, session-scoped metadata registry keyed by a window alias plus generation. It must return a defined absence result for invalid, retired, or ordinary native windows; it must never expose the registry address to Guest code. Setters must publish the dialog identity before a relevant callback can be admitted, and retirement must coordinate with callback rundown rather than relying on a handle value not yet being reused.

This source route does not establish all readers, locking, a global callback-drain protocol, or a magic safety guarantee from the original private layout. Those are handoffs to [2.3](../part-2/2-3.md), [4.2](4-2.md), [4.3](4-3.md), and [6.3](../part-6/6-3.md).

## 2. Creation: resolve, call, then publish as one outcome

Guest USER thunks expose the selected CreateWindow/CreateWindowEx routes (`wow16/user/user.asm:389-390`; `user.api:1210-1224`), with direct table slots in `wow32/wutbl2.h:64,557`. The common selected implementation is `wow32/wuwind.c:669-903`; class metadata lookup is an explicit dependency in `walias.c:250-269`.

For a minimal-diff modern adapter, the source establishes this ordering discipline:

1. Resolve a class name or atom and retain a class-generation lease before calling native USER.
2. Decode Guest creation fields as fixed-width meanings, including the difference between a child control ID and a top-level menu handle.
3. On native success, publish the HWND16 projection and the class/callback metadata together.
4. On failure, release preflight state and return zero; do not leave a half-published alias.

“Together” means one compatibility-state commit, not a claim that no native creation message or reentry can occur. Reentrant create, the private/standard/MDI class distinction, atom versus string input, and native failure require runtime cases. Full creation-message ordering belongs to [4.10](4-10.md); later ordinary window state/text/geometry belongs to [4.8](4-8.md).

## 3. Destruction: native success is not enough to free the alias immediately

`WU32DestroyWindow` is directly dispatched (`wutbl2.h:78`) and the selected wrapper (`wuwind.c:997-1010`) maps the HWND, calls `DestroyWindow`, converts the result to `BOOL16`, and clears the `SendDlgItemMessage` cache. That static evidence proves neither the full `WM_DESTROY`/`WM_NCDESTROY` order nor the original location where every alias is retired.

The minimum modern rule is therefore conservative: validate the Guest alias generation and the creator-thread policy before the call; keep mappings if native destruction fails; only on success retire the mapping through a callback-rundown barrier. A reused native handle must never resolve to a stale Guest alias. Test invalid/stale aliases, child/owned cascades, cross-thread policy, reentrant destruction messages, native failure, handle reuse, and a late callback. Do not turn the absence of a proven retirement site into an unproven source-UAF allegation.

## 4. Procedure replacement: capability tokens, not cross-ABI function pointers

Procedure table bindings appear at `wutbl2.h:172-173,176-177`. The selected window/dialog paths are `wuwind.c:1632-1805,2423-2613`; class paths are `wuclass.c:241-355,688-800`. In particular, `WU32SetWindowLong` distinguishes a supplied 16:16 procedure that thunks back to a native procedure from a real Guest procedure (`wuwind.c:2446-2503`), and handles `DWL_DLGPROC` independently (`2535-2581`).

The implementation consequence is direct: no raw Guest FARPROC belongs in a host64 procedure slot, and no raw host pointer belongs in a Guest DWORD/FARPROC field. Use typed, generation-checked procedure tokens and retain their registry binding while nested dispatch might call the prior procedure. When an underlying modern `SetWindowLongPtr`-style operation returns zero, clear/check its error state so a legitimate prior zero value is not silently reclassified as failure.

The selected source does not prove generated thunk retirement—the inspected free paths are `#if 0`—nor full dialog semantics, UIPI policy, or runtime equivalence. Required cases are Guest-to-native and native-to-Guest replacement, old-procedure chaining, nested replacement, zero prior value, denial/failure, destruction, and dialog-token retirement.

## What this chapter does not infer

- Private OpenNT USER indices are not usable public modern APIs.
- A successful `CreateWindow` wrapper does not prove all creation messages or every callback ordering.
- A successful native destroy does not prove alias/callback retirement is already safe.
- A procedure-looking value is not automatically callable in the receiving ABI.
- A `#if 0` cleanup path is negative evidence, not permission to accuse the original source of a verified leak or use-after-free.
