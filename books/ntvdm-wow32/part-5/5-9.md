# 5.9 — ToolHelp, diagnostics, and limited extensions

## Scope and closure statement

ToolHelp is a guest diagnostic facade over the running Win16 world. It enumerates task, module, heap, selector, stack, class, interrupt, and notification state; it also exposes selected control operations. It consumes the existing task/module/selector model and must not become a second scheduler, terminator, or raw host-memory interface. This chapter closes the static ToolHelp export/dispatch inventory and selected notification/enumeration mechanics from OpenNT source. It does not certify debugger compatibility, a safe modern raw-memory reader, or runtime support.

Task creation/exit stays in [1.2](../part-1/1-2.md) and [1.3](../part-1/1-3.md); address and selector meaning in [2.1](../part-2/2-1.md); generic callback reentry in [2.3](../part-2/2-3.md). Clipboard, DDE, Shell, and WinHelp have their own chapters and are not silently absorbed here.

## Evidence and inventory

The basis is OpenNT `5c5b979ec08c17d3ca2eb70e8aad62d26515d01c`: `wow16/toolhelp/{toolhelp.def,toolhelp.h,task1.c,notify1.c,notify2.asm,signal.c}`, `wow16/kernel31/context.asm`, and `wow32/{wthtbl2.h,wthman.h}`. `TOOLHELP.DLL` exports groups for global/local heap walking, module/task walking, stack tracing, class enumeration, memory/system information, notification/interrupt registration, termination, memory read/write, timers, and task CS:IP/switch functions. That export list is an inventory, not proof that every export has a complete WOW32 route.

## Enumeration is a snapshot-shaped guest protocol

`toolhelp.h` uses packed, size-tagged output records. `TaskFirst`, `TaskNext`, and `TaskFindHandle` require a nonnull `TASKENTRY` whose `dwSize` exactly matches the structure. `TaskNext` additionally rejects a null `hNext`. The returned task record carries handles, module/instance identity, stack fields, queue handle, module text, PSP offset, and next handle. It is a diagnostic view of mutable guest state, not a leased object whose lifetime survives later task rundown.

In WOW, `TaskFindHandle` contains a special OLE BusyDialog case: a nonzero value in the ordinary 16-bit handle range whose bit 2 is clear is projected into `hInst` and succeeds, rather than being passed to the normal task lookup. This is a narrow compatibility exception. It must not be generalized into a rule that any low-valued number is a live task; [5.4](5-4.md) owns the OLE-side context.

Module, global, and local walkers use analogous explicit records and first/next state. The structures expose 16-bit addresses, selectors, owners, flags, and legacy heap categories. A 64-bit carrier may offer a bounded diagnostic projection, but it must not hand raw host pointers, process-wide handles, or an unsafe memory capability to a guest merely because the original record had an address field. Stale entries after task/module disappearance must fail or terminate enumeration according to the selected original protocol, rather than dereference a modern object after rundown.

## Notification registration and dispatch

`NotifyRegister` first requires ToolHelp to be installed, installs the Kernel notification hook on first use, substitutes the current task for a null task argument, registers a termination signal helper, rejects a duplicate task registration, then appends a callback record. `NotifyUnRegister` removes one task record, removes its signal helper only when no interrupt handler needs it, and unhooks the global notification mechanism after the final record disappears. This gives registration ownership a task identity, but does not make it task termination.

`NotifyHandler` saves a register frame, translates selected Kernel/PTrace notifications into ToolHelp IDs and data, then traverses callbacks in registration order. Zero matching flags means delivery; otherwise a callback record’s flags must intersect the decoded notification flags. A nonzero callback return stops further dispatch. It saves the next pointer in `npNotifyNext` before entering the callback, and unregister updates that global when removing the current record. This is direct evidence of one self-unregister accommodation, not proof of safety for nested notification, removing a future record, concurrent mutation, callback faults, or arbitrary reentrancy.

Notification decoding has version and hook-mode branches: old versus new PTrace access paths differ, some new notifications require the advanced hook, and a static `ReturnStruct` is sized for the then-largest notification record. Consequently, a modern adapter must retain exact notification identity/payload and ordering only where it implements that family. It must not promise a generic debugger stream because ToolHelp exists.

## Signal and Kernel-hook ordering

Signal registration installs `HelperSignalProc` for the selected task and retains the prior signal procedure. The source comment says the helper runs when a task is about to terminate and chains to the previous USER signal procedure rather than simply returning. That is an ordering observation interface, not a replacement task terminator. Task exit and forced termination decisions remain owned by the audited lifecycle path.

Kernel `ToolHelpHook` maintains a ToolHelp-installed flag and exchanges the callback pointer; context/debug paths call it before selected ordinary tracing paths. This proves a hook relationship, not universal debugger priority or a guarantee that every exception/interrupt is observable. Interrupt registration, `TerminateApp`, `MemoryRead`, `MemoryWrite`, and task-switch exports need their own implementation contracts before being enabled; an export declaration is insufficient.

## Modern-host policy and closure

Recreate ToolHelp, if needed, as a read-mostly compatibility facade over the authoritative guest task/module/selector registry. Copy fixed-width records, validate input record sizes and guest buffers, state snapshot/rundown rules, and keep task termination out of the diagnostic layer. Notification callbacks require explicit registration lifetime, mutation, ordering, and fault policy. Unsupported destructive/debugger features should report failure at the corresponding API boundary, not appear to succeed or access host memory.
