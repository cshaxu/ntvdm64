# 5.7 — Printing

## Scope and closure statement

Printing is one observable contract with two distinct carriers in OpenNT: GDI document/page APIs operate through an HDC, while legacy spool APIs operate through a separate Win16 printer handle. WNet queue operations are a third, provider-selected route documented in [5.6](5-6.md). This chapter closes the static source inventory and the explicit conversion/lifetime behavior of the GDI and spool routes. It does not certify a physical printer, a contemporary spooler, a successful job, or a product implementation.

Printer discovery and `PrintDlg` are intentionally handed to [4.6](../part-4/4-6.md); DC identity and ordinary GDI objects to [4.7](../part-4/4-7.md); font/resource choices to [4.8](../part-4/4-8.md). The scope here starts once a printer-facing API is called, and ends at the returned status or released job/handle.

## Evidence and audit identities

The source basis is OpenNT `5c5b979ec08c17d3ca2eb70e8aad62d26515d01c`: `wow32/wspool.c`, `wow32/wgdi31.c`, `wow32/wgtbl2.h`, `inc/wowgdi.h`, the Win16 GDI definition/assembly files, and `wow16/inc/winnet.h`. The following are audit identities, not a count of functions or a runtime-support claim.

| Identity | Category | Direct evidence | Static conclusion |
| --- | --- | --- | --- |
| `WOW32_GDI_PRINT_DOCUMENT` | entry family | `WG32StartDoc`, `WG32EndDoc`, `WG32AbortDoc` | HDC document lifecycle is explicitly forwarded |
| `WOW32_GDI_PRINT_PAGE` | entry family | `StartPage`/`EndPage` table and wrappers | page lifecycle is distinct from document lifecycle |
| `WOW32_SPOOL_JOB_HANDLE` | handle mapping | `WG32OpenJob`, `GetPrn16`, `Prn32`, `FreePrn` | a Win16 job handle represents a host printer handle through a mapping |
| `WOW32_SPOOL_IO` | protocol | start/end page, write, close, delete wrappers | job operations have independent host calls and error paths |
| `WOW16_WNET_PRINTING_CAPABILITIES` | provider protocol | `winnet.h` `WNNC_PRINTING` flags | network print support is negotiated, not implied |

These are **A** source facts. The audit does not infer that a table row creates an operational printer or that dynamic loading of `WINSPOOL.DRV` proves every requested endpoint resolves; such questions remain **U** until a carrier is tested.

## GDI document and page lifecycle

The guest GDI export surface includes `StartDoc` ordinal 377, `EndDoc` 378, `StartPage` 379, `EndPage` 380, and `AbortDoc` 382. OpenNT registers the document endpoints as dedicated WOW32 handlers rather than a generic name-only forwarder. `WG32StartDoc` converts the 16-bit `DOCINFO16` name/output pointers into a native `DOCINFO`, sets the native size, and forwards the already-mapped HDC to `StartDoc`.

An important source-specific semantic is current-directory synchronization. Before native `StartDoc`, the wrapper calls `UpdateDosCurrentDirectory(DIR_DOS_TO_NT)`, with a comment explaining that printing to `FILE:` may prompt for a filename. This does not make print-to-file equivalent to an ordinary file-open seam; it is a print-dialog/path interaction. A modern carrier must preserve the appropriate Win16-visible output-path basis or return the original kind of failure, rather than silently choosing a host working directory.

`WG32EndDoc` and `WG32AbortDoc` are not interchangeable. For tasks carrying `WOWCFEX_FORMFEEDHACK`, EndDoc first sends buffered data streams to the printer, while AbortDoc removes them. Only then does each call its native GDI operation. The flags are task compatibility policy, not a universal print protocol; a replacement must not generalize the hack to unrelated applications. The wrappers return the converted native integer result and expose a negative abort result rather than manufacturing success.

Page boundaries are separately forwarded by `WG32StartPage` and `WG32EndPage`. A document may therefore exist without a valid page sequence in the evidence, and a page operation must not be treated as implicit document completion. The source here does not show task-exit cleanup of an active HDC document or host-spool cancellation ordering. Those are open lifecycle questions, not a confirmed leaked-job or use-after-free defect.

## Legacy spool-job carrier

`wspool.c` handles the DDK-style Win16 spool APIs. It lazily obtains a table of named `WINSPOOL.DRV` procedures through `LoadLibraryAndGetProcAddresses`; loader failure makes `WG32OpenJob` return zero. Thus module loading is only a prerequisite, not evidence that a job was opened.

On `OpenJob`, the wrapper resolves a driver name, optionally obtains a default native `DEVMODE` through the dynamically loaded `ExtDeviceMode`, opens the native printer, and starts a native document. It sets `DOC_INFO_1.pDocName` from the guest document string and `pOutputFile` from the guest output string. A successful `StartDocPrinterA` is then converted into a 16-bit job handle by `GetPrn16`; an open/start failure returns the relevant last-error value. Driver/default-mode allocation is freed before return. This makes selection, open, start, and handle publication separate observable transitions.

The mapped handle is crucial. `WG32StartSpoolPage`, `WG32EndSpoolPage`, `WG32WriteSpool`, `WG32CloseJob`, and `WG32DeleteJob` recover the native printer handle via `Prn32`. `WriteSpool` reports the requested 16-bit byte count after a successful native `WritePrinter`; it returns `GetLastError` on a false native result. A short write is not independently represented in this wrapper, so a modern equivalent must not claim a stronger partial-write guarantee than this source shows.

Close first calls `EndDocPrinter`, then `ClosePrinter`, and releases the Win16 mapping only when its final result is nonzero. Delete calls `DeletePrinter` using the mapped handle but does not itself free that mapping. These direct branches are enough to establish that close, delete, and map release are different operations; they do not prove a safe retry policy after one host operation fails. Do not collapse the handle into an HDC, or free it merely because an abort/delete request occurred.

## WNet print jobs and provider absence

The USER `WNetOpenJob`, `CloseJob`, `WriteJob`, abort/hold/release/cancel, queue-watch, and queue-data calls are separate from the GDI spooler. `winnet.h` declares its own `WNNC_PRINTING` capability bits and job/queue statuses such as queued, spooling, printing, complete, and error. Its active network-driver selection machinery is documented in [5.6](5-6.md). A modern local printer does not automatically satisfy an active WNet provider capability, and a WNet printer queue is not evidence that `StartDoc` should succeed.

The guest `winnet.asm` has a network-information table with one slot per driver entry point. Its documented no-function outcome is `WN_NOT_SUPPORTED`. Therefore a minimum-diff carrier should express no selected provider, missing provider function, and native printer failure as distinguishable results wherever the original interface distinguishes them. It must not add a global redirector, synthetic queue, or automatic network mapping to make one application pass.

## Modern-host design and closure

The narrow design is to retain two lifetimes: an HDC-owned GDI document/page state and a separately mapped spool-job state. A backend may support neither, one, or both, but its advertised capability must match its error, path, buffer, and release behavior. Preserve the `FILE:` current-directory context, host-error propagation where source exposes it, task-specific flags only where their predicates are known, and the distinction between completion, abort, close, and delete.

It remains open for actual modern endpoint discovery, `WINSPOOL.DRV` replacement binding, printer-driver DEVMODE compatibility, job cancellation races, and task-exit quiescence. Those are implementation-validation tasks; they do not require expanding into device drivers, raw transport, or the entire print UI.
