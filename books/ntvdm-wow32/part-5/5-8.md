# 5.8 — Drivers, VDDs, and devices

## Scope and closure statement

This chapter is deliberately narrower than the phrase “VDD support.” It covers host-side extension contracts that directly affect a Win16/WOW program: the VDD user-hook registry and the public WOW32 ISV helper surface. It excludes the CPU/V86 machine, general device-driver implementation, and DOS redirector mechanics. Those are not Win16-to-modern-host seams merely because they execute in NTVDM.

The static interface and local lifetime behavior of the selected VDD registry are closed from OpenNT source. The effective binary ABI, module retention, caller policy for all events, and any current-system VDD replacement remain unverified. This chapter therefore provides a constrained integration baseline, not a claim that arbitrary historic VDDs can be loaded.

## Evidence and identities

OpenNT baseline `5c5b979ec08c17d3ca2eb70e8aad62d26515d01c` supplies `public/sdk/inc/nt_vdd.h`, `base/mvdm/softpc.new/host/src/nt_msscs.c`, `base/mvdm/dos/dem/{demmisc.c,demsrch.c}`, and `base/mvdm/wow32/isvwow.h`. The stable identities are:

| Identity | Kind | Direct source fact | Limit |
| --- | --- | --- | --- |
| `VDD_USER_HOOK_REGISTRY` | host callback registry | install/deinstall and four notification traversals | native calling convention and module lifetime are not proved |
| `VDD_DOS_PDB_CREATE_TERMINATE` | protocol | create/terminate pass a 16-bit DOS PDB | not a Win16 task callback |
| `VDD_SESSION_BLOCK_RESUME` | protocol | block/resume take no argument and synchronously invoke registered callbacks | not guest task scheduling or a host suspend API |

The table records entry/protocol/mechanism separately. All listed source facts are **A**. Contemporary carrier availability and implementation verification remain **U**.

## VDD user-hook registration

`nt_vdd.h` defines a record consisting of a VDD handle, optional create/terminate/block/resume function pointers, and a next link. Create and terminate callbacks receive `USHORT DosPDB`; block and resume receive no argument. These are native host callbacks, not Win16 FAR procedures. Reproducing guest Win16 execution is therefore insufficient evidence that a historic VDD pointer can safely be invoked.

`VDDInstallUserHook` rejects only a null VDD handle, returns `ERROR_INVALID_PARAMETER` in that case, allocates a record, copies every supplied callback pointer, and prepends the record to the list. Allocation failure returns `ERROR_OUTOFMEMORY`. It contains no duplicate-handle, module, or function-address validation; even four null callbacks create a record. Its successful path does not explicitly clear last error. Those are local implementation facts, not requirements to copy an unsafe registry verbatim.

`VDDDeInstallUserHook` rejects null and removes only the first matching node before returning. Since registration prepends, repeated registrations using one handle retire newest first, one call at a time. The source comment says “all events,” but its body does not remove all duplicate nodes. A compatibility adapter must decide whether it preserves this observable duplicate order; it must not claim a broader original all-record removal guarantee.

## Notification and lifetime boundary

Create, terminate, block, and resume traversal walk head to tail; each invokes the matching nonnull function and then reads the current node’s `next` pointer. Unchanged-list order is consequently newest registration first. There is no visible lock, snapshot, dispatch reference, deferred retirement, exception boundary, or module pin in these bodies.

This establishes a critical boundary without declaring an unverified crash: self-deinstall during a callback can free the current node before the subsequent `next` read. Removing a future node, inserting a new head, nested dispatch, and concurrent mutation are distinct cases. The source is enough to require a modern registry to state its mutation and code-lifetime policy explicitly; it is not enough to report an original reproduced UAF or race.

The calls are synchronous on the notifying thread. The source comment assigns worker-thread blocking and cleanup to a VDD’s block hook; the registry does not itself stop every worker. Similarly, a return from resume does not prove all input, timers, or devices have resumed. A safe modern adapter should use host-owned nodes and deferred retirement or equivalent lifetime protection, avoid holding a non-reentrant global lock while entering arbitrary extension code, and separately pin or broker callback code if module unload is allowed. Those are safety extensions, not claims about the original implementation.

## Event meanings are not Win16 task meanings

OpenNT invokes `VDDCreateUserHook` from DOS DEM entry after a first-call gate and invokes `VDDTerminateUserHook` for a DOS PSP termination path. The passed PDB identifies a DOS process domain. It is not a notification for every `CreateTask`, task switch, or Win16 module unload. [3.5](../part-3/3-5.md) owns DOS/DEM semantics; [1.2](../part-1/1-2.md) and [1.3](../part-1/1-3.md) own Win16 task lifecycle.

The block/resume call sites are console/session handoffs. Source order places block notification before later shutdown/stall handling, while the non-WOW resume path prepares some event and console state before notifying, then restores additional display/input/timer state after the callback. The WOW branch is explicitly different. Do not reuse the entire console event-thread protocol as a Win16 scheduler, and do not infer complete device quiescence merely from a hook return.

## WOW32 ISV extension helpers

`isvwow.h` declares three extension helpers for multimedia-style WOW thunk extensions: `WOW32ResolveMemory`, `WOW32ResolveHandle`, and `WOW32DriverCallback`. Handle resolution supports explicit 16-in/32-out and 32-in/16-out direction flags and a defined family of USER, GDI, wave, and MIDI handle types. Its presence means an extension can request established WOW mappings; it does not license raw host handles inside guest records, nor prove every type has identical ownership rules.

The callback declaration carries a callback value, flags, two WORD identifiers, and three DWORD payload values. It is a defined scalar interface, but does not by itself establish queueing, guest callback execution, cancellation, or teardown. Those concrete multimedia rules belong to [5.1](5-1.md) through [5.3](5-3.md) and the general reentry/lifetime boundary belongs to [2.3](../part-2/2-3.md). An ISV extension must not be treated as proof that the fixed multimedia callback bridge or its ring queue is universally available.

## Modern-host policy and closure

Use named, copied records at the compatibility boundary; keep VDD identity, event domain, callback ABI, and module lifetime separate. A service not deliberately implemented should fail at a documented registration/load boundary, rather than accepting an arbitrary native pointer or emulating device success. Do not import unrelated V86-machine work, publish raw host resources to guest structures, or turn a DOS PDB event into a Win16 task event.

This chapter is statically closed for the selected VDD registry and ISV helper scope. It remains open for compiled ABI, module pinning, callback mutation behavior under execution, exact modern carriers, and device-specific protocols. Implementation acceptance must include null/all-null registration, allocation failure, duplicate removal order, callback-time mutation, nested/concurrent dispatch, module unload during callback, PDB width, and block/resume ordering. Device-specific work hands to [5.1](5-1.md) for multimedia and to [6.3](../part-6/6-3.md) for optional-service policy.
