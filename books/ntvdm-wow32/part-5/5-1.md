# 5.1 — Multimedia initialization, bridges, and drivers

## Boundary

Multimedia initialization starts with Guest dynamic loads and private name resolution, then crosses a fixed bridge into WOW32/provider code. Source evidence distinguishes module resolution from a successful ABI call and provider availability.

## Semantics that must survive

Preserve loader failure, private-export selection, current-directory argument, procedure identity, five DWORD parameter order, device-ID placement, and bridge calling convention. Keep fixed WMM32 bridging separate from variable WK32ICallProc32.

## Modern-host discipline

A named adapter may bridge unavailable private provider edges, but resolved names never prove device support. Define callback admission and teardown before accepting asynchronous paths.

## Handoff boundary

General call frames are 2.2; callback/rundown 2.3; audio/MIDI 5.2; timer/MCI 5.3.

## Review questions

1. Which original device, table, provider, or task owner decides this result?
2. Which data, callback, or handle crosses the seam and who releases it?
3. What happens on cancellation, device loss, task exit, or a late callback?
4. Is an unavailable service reported explicitly rather than simulated as success?

## Selected evidence and the correct denominator

The OpenNT source baseline is commit `5c5b979ec08c17d3ca2eb70e8aad62d26515d01c`.
The scoped multimedia evidence contains entry, shared-structure, protocol, and
callsite identities; none of those categories is a function count or a build

## The fixed bridge is not WK32ICallProc32

The Guest `MMCALLPROC3216` frame has seven DWORD fields in this order:
`fSetCurrentDirectory`, `lpProcAddress`, then `p1` through `p5`
(`wowmmed.h:762-771` and `WOWMMED.INC:515-523`). `p1` carries `dwParam2` and
`p5` carries `uDevId`; the host calls in reverse stack order, `p5` through
`p1`. `WMM32CallProc32` therefore has a fixed five-DWORD multimedia-message
shape, optionally synchronises the DOS current directory, and calls the
selected procedure (`wmmedia.c:135-170`). `wmmtbl2.h:18` binds this handler;
the Guest thunk uses `MMCALLPROC32`.

This must remain separate from KERNEL's `WK32ICallProc32`, which is a
variable-argument bridge with address-translation masks and calling-convention
logic. Similar words such as “call procedure” do not make their wires
interchangeable. On x64, a Guest DWORD procedure identity cannot be passed as
a native function pointer; a typed bridge or registry resolution is required.
No source evidence here establishes a fault in either original bridge.

## Callback transport: publication is not shutdown

`Notify_Callback_Data` uses the fixed bridge, with real callback data in the
fifth native argument (`thunks.asm:787-814`). The selected callback structure
defines 16 slots. Each record has flags, a Guest far-function identity,
16-bit handle and message, instance, and two parameters; the Guest-visible
layout is 24 bytes per slot with `recv`/`send` WORD indices, not a host-aligned
replacement (`inc/wowmmcb.h`; `stack.asm`).

The interrupt consumer snapshots `send`, copies all callback parameters from
the current slot onto the Guest stack, advances `recv`, then calls
`DriverCallback`; it stops at the saved `send` rather than chasing new
production indefinitely (`stack.asm:610-709`). A null target is guarded on a
selected path (`stack.asm:774-810`), but a destruction guard sits in a
conditionally disabled block. This proves the local ordering and a bounded
consumer batch; it does not prove target-task ownership, global queue drain,
or that a callback already copied to the Guest stack can be cancelled.

At termination the Guest first terminates the interrupt stack and removes the
interrupt handler, then invokes `Notify_Callback_Data(NULL)`, then unlocks and
frees Guest callback storage (`init.c:649-669`). That sequence proves Guest
withdrawal happens before Guest-memory release. It does not prove a provider
has stopped producing, that an already admitted callback is drained, or that
the original code has a verified use-after-free defect.

## Minimal modern carrier

Keep the original Guest ISR and `DriverCallback` ABI. A device/provider thread
must publish a typed completion record into an owned transport and trigger the
established delivery mechanism; it must not directly invoke a Guest far
pointer on a native callback stack. The carrier needs a callback-generation or
admission state, a fixed 16-slot-compatible overflow policy where that route
is retained, and a retire protocol: close admission, cancel producer work,
account for in-flight delivery, drain or explicitly discard remaining records
under the original semantics, detach the Guest mapping, then release it.

For the nine private endpoints, model each device instance with an opaque
Guest token and pointer-sized private storage. Preserve exact message/device
number/parameter mapping only when its original contract has evidence. Modern
public wave, MIDI, timer, joystick, or mixer APIs may be useful typed
adapters, but their native handles, `DWORD_PTR` values, and callback modes do
not prove equivalence and must never be truncated into the Guest ABI.
