# 5.5 — Winsock

## Boundary

Winsock includes ordinal/name resolution, startup/cleanup, socket operations, address/data conversion, async notification, blocking-hook behavior, cancellation, peer loss, and task teardown. The ordinal inventory is navigation, not compatibility proof.

## Semantics that must survive

Preserve operation result/error mapping, buffer/address layout, notification identity, unhook behavior, cancellation, and cleanup after peer or task loss.

## Modern-host discipline

Reach modern sockets through one explicit ABI boundary. Do not create another callback carrier or leave notifications targeting a released Guest task.

## Handoff boundary

Async callback lifetime is 2.3; task retirement 1.3; file/path policy only when an actual caller requires it.

## Review questions

1. Which original device, table, provider, or task owner decides this result?
2. Which data, callback, or handle crosses the seam and who releases it?
3. What happens on cancellation, device loss, task exit, or a late callback?
4. Is an unavailable service reported explicitly rather than simulated as success?

## Evidence and current limit

Relevant audit material: Dynamic Winsock binding coverage, callback-registration, unhook source note, and task-lifetime records.

This page is source-contract guidance; it does not certify a product image or runtime implementation.

## Async context is a typed ownership record

The selected `winsockp.h` declaration describes a global asynchronous-context list containing a native/Guest task-handle pair, Guest buffer address and length, and native buffer storage. Completion routes look up and remove that context under their shared critical section. Only after successful result conversion do they map the Guest output buffer, post the Guest task handle, and free the native buffer and context (`wsdata.c:500-565,1060-1125,1563-1628,1798-1845`).

That ordering is the source contract: a modern carrier needs an opaque operation token with logical Guest-task owner, native operation identity, Guest buffer descriptor, copied or pinned native storage, result state, and one retirement transition. It must not substitute a raw Guest buffer pointer for the operation record or infer that a post result equals delivery to a live Guest task.

The selected cancellation wrapper does not itself remove the context. The shared per-thread cleanup route releases Guest database storage and owned sockets but does not traverse the declared global async-context list (`wsext.c:566-730`). Task termination calls that cleanup only when the thread was initialized (`wkman.c:1473-1491`). These facts leave cancellation completion, late post ordering, and task-exit quiescence open; they do not by themselves prove a leak, stale post, or use-after-free defect.

## Posted routing is bounded, and blocking hooks are reentry

At startup, the selected route registers `WWS32DispatchPostMessage` through private ordinal 1000 (`wsext.c:503-512`). The callback selects one of four internal dispatch-table entries based on the low word of an encoded message. For async select it maps native socket identity back to a Guest socket handle before the post (`wsext.c:770-837`). This table is a private routing mechanism, not a license to add arbitrary message handlers or proof that every native socket event maps cleanly to a Guest event.

The modern implementation should use the existing USER message route and Guest handle registry, tagging each post with socket generation and target task/window generation. It must close notification admission before retiring a socket mapping, then either drain or drop already queued events according to the specific legacy contract. A native readiness notification after close, a reused Guest socket token, and target task/window exit are separate tests.

`WWS32CallBackHandler` is registered as a native blocking callback. It either pumps the default message path or uses `CallBack16` to a retained Guest blocking-hook procedure (`wsext.c:841-891`). Therefore it cannot be flattened into the async-post carrier: it may reenter Guest execution synchronously and has callback-frame, task-liveness, and return-value requirements distinct from an event queue.

A carrier must retain a typed hook token while it is installed, reject or detach it before Guest task retirement, and prevent a native blocking call from targeting a released code address. The selected source does not establish unhook cancellation behavior or final-thread retirement; those are explicit implementation validation obligations, not grounds to alter Guest code.

## Required receipts and closure

Runtime evidence must separately cover startup/cleanup failure, socket open and close, async operation success/error/cancel, completion after cancel, completion after logical task exit, output-buffer copy failure, post failure, native socket-to-Guest-token lookup failure, token reuse, blocking-hook install/unhook, and blocking reentry while task retirement is requested. Each trace should identify operation token, task generation, socket generation, admission, post/callback attempt, completion, and final release.

Static closure here records selected routing, context ownership, and the blocking-hook boundary. It does not prove all ordinal wrappers, external provider profiles, final image selection, Winsock version negotiation, cancellation drain, or modern API equivalence. Generic callback and task rundown remain [2.3](../part-2/2-3.md) and [1.3](../part-1/1-3.md); carrier runtime receipts belong to [6.3](../part-6/6-3.md).
