# 5.6 — WFWNET, RAS, and network redirectors

## Scope and closure statement

This chapter separates two source-proven Win16 network seams which must not be collapsed into a claim that "networking works": the Windows for Workgroups-era `WNet*` USER service family, and the separately shipped `RASAPI16.DLL` bridge. The first is a run of ordinary WOW USER dispatch identities. The second is a guest DLL which loads a named 32-bit RAS module and calls named `*Wow` entry points through the generic call bridge. The original source is sufficient to close the static interface inventory for these two seams. It does not establish that either historic provider is present, callable, or semantically equivalent on a current host.

Redirector, NetBIOS, DOS network-drive, or transport internals are deliberately outside this chapter unless one of these two interfaces hands a concrete object to them. They are not evidence merely because a Win16 program uses a UNC path. File/path conversion belongs to [3.2](../part-3/3-2.md), generic far-pointer and call-convention mechanics to [2.1](../part-2/2-1.md) and [2.2](../part-2/2-2.md), and window-message delivery to [4.2](../part-4/4-2.md).

## Evidence boundary

The source basis is OpenNT baseline `5c5b979ec08c17d3ca2eb70e8aad62d26515d01c`. `base/mvdm/inc/WOWUSR.INC` and `wowusr.h` assign USER thunk numbers; `base/mvdm/wow32/wutbl2.h` supplies the corresponding dispatch entries; and `base/mvdm/wow16/inc/winnet.h` supplies the Win16-facing WNet contract. The RAS side is `base/mvdm/wow16/rasapi16/{ras.h,rasapi16.c,rasapi16.def}`. Those paths establish interface shape and selected conversion behavior. They do not prove a modern operating system retains `RASAPI32.DLL` or its private `Ras*Wow` exports.

The identity names below are audit labels, not assertions that a current binary has an exported function of the same spelling:

| Audit identity | Kind | Evidence | Static result |
| --- | --- | --- | --- |
| `WOW32_WNET_USER_DISPATCH` | entry family | USER IDs 499–532 and the contiguous `wutbl2.h` table region | closed as a dispatcher inventory |
| `WOW32_WNET_CONNECTION_FRAMES` | shared argument structures | `WNET{ADD,GET,CANCEL}CONNECTION16` | closed for three explicitly framed calls |
| `WOW16_WNET_ACTIVE_DRIVER_EXTENSION` | provider-selection protocol | `winnet.h` capability/ordinal documentation | closed as an availability protocol, not a provider implementation |
| `WOW16_RASAPI16_TO_RASAPI32` | guest DLL bridge | `rasapi16.c` and `.def` | closed for loader, named resolution, allocation, conversion, and error mapping visible in source |
| `WOW16_RAS_DIAL_NOTIFICATION` | message protocol | `ras.h`, `rasapi16.c` | closed for the registered-message parameter path; host delivery/lifetime remains unverified |

No item here is an implementation verification. In the audit vocabulary, the source facts are principally **A** (direct source), with a few **B** inferences about table continuity; provider availability and runtime behavior remain **U**.

## WNet is a USER-dispatch family, not a universal redirector

The OpenNT table puts `FARCALLNETDRIVER` at 500, then the WNet jobs and queues at 501–511, connection and capability calls at 512–520, and enable/restore/write/dialog calls at 521–529. Directory calls and property text occupy 530–532. `wutbl2.h` registers most of them as `LOCALAPI` under `MOD_USER`. That is valuable negative evidence: the table declares which Win16 ordinal identities reach the WOW USER dispatcher, but it does not show a family-specific WOW32 conversion routine or prove a particular modern network-provider call.

`winnet.h` divides the Win16 contract into groups whose state and failures should remain distinct:

- spool/job operations: `WNetOpenJob`, `CloseJob`, `WriteJob`, `AbortJob`, hold/release/cancel, queue watch, and queue-data lock/unlock;
- connection operations: `WNetAddConnection`, `CancelConnection`, `GetConnection`, and `RestoreConnection`;
- capability and identity queries: `WNetGetCaps` and `WNetGetUser`;
- interactive UI: device mode, browse/connect/disconnect/connection, queue and property dialogs;
- directory administration and error reporting: `WNetGetDirectoryType`, `WNetDirectoryNotify`, `WNetGetError`, and `WNetGetErrorText`.

This classification is semantic, not an API count. A modern adapter must not return success for connection creation merely because it can display a dialog, and must not describe a local filesystem mapping as an active legacy network driver. In particular, `WNetGetCaps` contains feature bits for connection, printing, dialogs, administration, errors, and user lookup. Capability negotiation is the source-defined way to express absence or partial support; claiming a capability commits the adapter to the corresponding operation's original result convention.

### Connection frames

Three dispatch records carry explicit 16-bit frame sizes: `WNETGETCONNECTION16` at USER 512, `WNETADDCONNECTION16` at 517, and `WNETCANCELCONNECTION16` at 518. The corresponding host-side records in `wowusr.h` use virtual-pointer fields rather than host pointers: add has three `VPSTR` fields, get has a source string, output string, and output-size pointer, while cancel has a string plus `BOOL16`. The table records a call-frame size; it does not itself prove buffer length validation, string encoding, or ownership after the dispatcher returns. Those must be made explicit in a replacement adapter.

For `GetConnection`, preserve the caller-supplied capacity/result-length protocol and distinguish `WN_MORE_DATA` from “not connected.” For add/cancel, preserve the boolean force/disconnect choice and the legacy `WN_*` status vocabulary. `winnet.h` names, among others, `WN_NOT_SUPPORTED`, `WN_NET_ERROR`, `WN_BAD_PASSWORD`, `WN_CANCEL`, `WN_NOT_CONNECTED`, `WN_OPEN_FILES`, `WN_ALREADY_CONNECTED`, and `WN_CONNECTION_CLOSED`. Mapping every unsupported route to success, or flattening all errors to one host error, would be a new compatibility seam and violates the minimum-diff rule.

### Active-driver extensions

The same header explicitly documents a second, narrower selection protocol. `WNetGetCaps(0xFFFF)` may return an active network-driver instance; a caller may then request a private ordinal with `GetProcAddress`. A null instance means no driver was loaded, and a null ordinal result means that the installed driver lacks that extension. The documented ordinals include share and server-browse dialogs, cached-password APIs, and interactive logon functions. This is neither evidence that every extension exists nor permission to fabricate a single synthetic provider with all ordinals.

For a modern carrier, retain the two-stage observable outcome: no selected provider versus selected provider without a requested extension. If support is intentionally absent, return the source-defined unsupported/no-driver result at the corresponding stage. Do not install a system-wide redirector, capture credentials, or invent a password cache solely to satisfy an old ordinal request. Password data in this extension area is a particularly strong reason to keep the compatibility adapter narrow and opt-in.

## RASAPI16 is a distinct guest-to-host contract

`RASAPI16.DLL` is not a USER thunk row. Its definition file imports four Kernel WOW helpers: `LoadLibraryEx32W`, `FreeLibrary32W`, `GetProcAddress32W`, and `CallProc32W`; it exports `LibMain`, `WEP`, `RasDial`, `RasEnumConnections`, `RasEnumEntries`, `RasGetConnectStatus`, `RasGetErrorString`, and `RasHangUp`. This source shape means a modern solution must preserve a DLL-level loading/failure boundary separate from WNet provider capability negotiation.

`LibMain` first rejects a non-NT WOW environment, then loads `RASAPI32.DLL`. Load failure makes the DLL initialization fail. On success it registers the `RasDialEvent` window message, retaining the default `WM_RASDIALEVENT` only if registration does not produce a positive replacement value. `WEP` frees the loaded module if one was acquired. The static evidence therefore proves module ownership at DLL lifetime boundaries; it does not prove that an in-flight dial notification is drained before `WEP`, nor that any private RAS worker stops before unload.

Each public operation resolves a named private entry point when invoked: `RasDialWow`, `RasEnumConnectionsWow`, `RasEnumEntriesWow`, `RasGetConnectStatusWow`, `RasGetErrorStringWow`, or `RasHangUpWow`. A missing resolution returns `ERROR_INVALID_FUNCTION`. Loading the module in `LibMain` consequently does not establish that all operations are usable. This is the same general distinction between module presence and endpoint resolution used in [5.3](5-3.md), but the RAS evidence has its own DLL and names.

### Conversion and lifetime evidence

`RasDial` allocates aligned temporary Win32-shaped dial parameters and a temporary connection-handle cell, copies the six visible strings, invokes `CallProc32W`, copies the resulting handle back, then frees both temporary allocations. Its address-mask argument marks the phonebook-path field as a far/16-bit argument and invokes a five-argument target. This is direct evidence for short-lived call marshalling; it is not proof that the target retains none of the passed data after the call. A replacement needs an explicit asynchronous-retention contract before freeing converted data.

Enumeration operations validate the incoming `dwSize`, convert the caller's byte capacity between 16-bit and 32-bit structure sizes, allocate a substitute buffer, call the `*Wow` routine, convert returned lengths, and copy entries back. `RasGetConnectStatus` similarly rejects a bad 16-bit structure size, uses a substitute `RASCONNSTATUSA`, then copies state, error, device type, and device name back. These are concrete structure-layout obligations, not invitations to pass a 16-bit pointer directly to a modern API.

The bridge maps only four observed Win32 RAS error numbers (709, 710, 713, and 714) to their differently numbered Win16 equivalents; all other codes pass through deliberately. Preserve that information-bearing behavior where a compatible carrier is offered. It is not justified to substitute a generic error merely because a code lacks a modern semantic counterpart.

## Notification, cancellation, and modern-host policy

`ras.h` defines a dial state sequence, `RASCS_PAUSED`/`RASCS_DONE` markers, `RASCS_Connected` and `RASCS_Disconnected`, plus a window-message notification convention. The `RasDial` wrapper sends the registered message number and notification window to `RasDialWow`; it does not itself post a message, track a pending request list, or implement cancellation. `RasHangUp` is a separate resolved target. Therefore the source does not establish cancellation ordering, the validity of a notify window after task exit, or a race/UAF. Those are open implementation questions and must not be reported as a confirmed original defect.

The minimal-diff design choice is per-family:

1. Treat WNet as a capability-selected provider interface. Expose only capabilities whose success, error, buffer, and dialog behavior can be represented; report unsupported/no-driver states faithfully for the rest.
2. Treat RAS as an optional DLL bridge. Support it only with a deliberate replacement for its loader, named endpoint, 16/32 structure conversion, error mapping, and registered-message lifetime rules. If there is no such carrier, make load or entry resolution fail in the original observable place rather than silently emulating a connected service.
3. Keep network credentials, global mappings, redirector installation, and unrelated NetBIOS machinery out of the WOW adapter. They are policy and security choices, not implied compatibility work.

## Closure and handoff

This chapter is statically closed for its limited scope: the WNet dispatch/table and provider-selection shape, plus the RASAPI16 loader/endpoint/conversion contract, are identified and bounded. It is not closed for real provider availability, RAS private endpoint ABI on a current system, notification quiescence, or end-to-end network operation. Those gaps are implementation validation work, not justification to enlarge this chapter into a redirector audit.

The next recipient is [5.7](5-7.md) for printing/spool semantics that are not specific to WNet queue identity; [6.3](../part-6/6-3.md) owns optional-service availability and feature policy; and [2.3](../part-2/2-3.md) owns any general callback/task-teardown rule. Before implementing either carrier, test the exact unsupported, more-data, disconnect, resolver-missing, late-notification, and task-exit paths.
