# 5.2 — Audio, MIDI, and mixer

## Boundary

Audio, MIDI, and mixer include device open/close, capabilities, buffer submission, completion, cancellation, window/function callbacks, and task exit. The meaningful unit is a device/buffer lifecycle, not an exported name.

## Semantics that must survive

Preserve buffer ownership, completion order, cancel result, queue-full/drop behavior where specified, notification semantics, and refusal after device/task close.

## Modern-host discipline

Modern APIs may require copied buffers and host-thread callbacks. One completion admission/rundown path is required; it may not retain Guest buffer addresses or invoke released tasks.

## Handoff boundary

Bridge mechanics are 5.1; shared callback behavior 2.3; generic retirement 1.3.

## Review questions

1. Which original device, table, provider, or task owner decides this result?
2. Which data, callback, or handle crosses the seam and who releases it?
3. What happens on cancellation, device loss, task exit, or a late callback?
4. Is an unavailable service reported explicitly rather than simulated as success?

## Evidence and current limit

Relevant audit material: Multimedia callback transport, cancellation, notify-window lifetime, exit-timer, and task-exit records.

This page is source-contract guidance; it does not certify a product image or runtime implementation.

## 1. Open and close are distinct publication states

For both Wave and MIDI, the Guest source obtains/locks a per-device Guest
identity before the private open message. That identity participates in the
opening description as the callback identity. An open failure releases or
unlocks it; only a successful open publishes the driver user value and the
visible Guest handle. Query opens are a separate operation: they must not
allocate an ordinary instance merely because a modern API offers a query mode.

Close is not synonymous with retirement. In the selected Wave route, the
Guest identity is released only when the close endpoint returns zero. A close
request or a failed close must therefore preserve the mapping and its buffer
state. This is a Wave-local source constraint; it must not be falsely
generalised to every multimedia family. MIDI follows the same broad delayed
retirement discipline in its selected Guest lifecycle, but the source does
not provide the private provider's asynchronous completion or close behavior.

The modern representation should use an opaque, generation-bearing Guest
token mapped to pointer-sized private state. It needs explicit states such as
query, opening, open, closing-pending, close-failed, and retired. A raw native
device handle or callback pointer cannot fit a Guest DWORD safely and cannot
serve as the stable identity.

## 2. Prepared and queued headers are ownership boundaries

Wave output write, Wave unprepare, Wave input add-buffer, MIDI long data, and
MIDI input add-buffer are not generic byte-array calls. The selected Guest
paths gate these operations on prepared and/or queued header state. MIDI-out
`LONGDATA` additionally checks its selector word, exact length, and flags.
The B-class structure conversion helpers in `wow32/wmmstruc.c` and
`wmmstruc.h` are the shared wire boundary; they do not by themselves prove
that a provider no longer holds a submitted buffer.

A carrier must copy or pin the payload according to the original operation's
ownership state, record its Guest header identity and generation, and return
completion through the established Guest callback transport. It must not
retain a raw Guest buffer address on an arbitrary device thread. Reset, stop,
and unprepare are separate selectors; neither a successful request nor a
modern native cancellation call alone proves that all queued completion work
has stopped.

## 3. Mapper and mixer remain separate routes

The selected Wave source keeps mapper routing distinct. Its wave-in mapper
branch has a source condition naming `wodMapper` while calling `widMapper`.
That exact observation is retained as source text, not elevated to an original
defect claim. It is insufficient to substitute a generic modern default
device without preserving the message/device-ID selection rule.

Mixer is adjacent but not another Wave/MIDI call alias. The Guest mixer route
initializes a fake driver, uses `MXDM_INIT` and `MXDM_GETNUMDEVS`, projects a
device count into Guest widths, and forwards open objects using device ID and
saved `dwDrvUser`. `MXDM_CLOSE` must return zero before the Guest list is
unlinked, use count decremented, and the Guest handle freed. The source has no
OpenNT private `mxd32Message` provider body here, so nested payloads, callback
behavior, unload, and producer stop remain explicit unknowns.

## 4. Validation requirements and closure

Implementation evidence needs independent receipts for query open, failed
open, successful publication, close failure, successful close, prepared-but-
not-queued header, queued header, reset/stop with pending work, and callback
arrival during logical-task retirement. Test two Guest tasks using the same
native execution thread so ownership is a logical task token rather than a
thread ID. Also test one task's exit does not retire another task's device or
completion route.

Static closure here records the Guest selector families, their selected
payload/lifecycle gates, and the shared structure boundary. It does not close
private provider bodies, device availability, effective build images, host
callback restrictions, buffer drain, cancellation, or late notifications.
Timer/MCI/joystick policy is handed to [5.3](5-3.md); fixed bridge and callback
publication are [5.1](5-1.md); generic callback/task retirement remain
[2.3](../part-2/2-3.md) and [1.3](../part-1/1-3.md); runtime carrier receipts
belong to [6.3](../part-6/6-3.md).
