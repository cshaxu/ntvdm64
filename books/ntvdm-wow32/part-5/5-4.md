# 5.4 — OLE, MCI/OLE, and DDEML

## Boundary

OLE, MCI/OLE, and DDEML contain dynamically resolved interfaces, registration surfaces, callbacks or conversations, and data lifetime distinct from USER DDE. Each selected interface is its own contract.

## Semantics that must survive

Preserve activation/registration result, ABI, conversation identity, payload ownership, cancel/failure behavior, and cleanup. Dynamic lookup proves a request only, not an implemented interface.

## Modern-host discipline

Use a bounded facade only when a public modern interface preserves the selected behavior. Do not merge OLE/DDEML with USER DDE or fabricate success for unavailable interfaces.

## Handoff boundary

USER DDE is 4.10; callback ABI 2.3; MCI ownership 5.3.

## Review questions

1. Which original device, table, provider, or task owner decides this result?
2. Which data, callback, or handle crosses the seam and who releases it?
3. What happens on cancellation, device loss, task exit, or a late callback?
4. Is an unavailable service reported explicitly rather than simulated as success?

## Evidence and current limit

Relevant audit material: OLE dynamic-binding coverage, DDE memory/ownership, MCI table, and callback records.

This page is source-contract guidance; it does not certify a product image or runtime implementation.

## Scope, selected table, and denominator discipline

This chapter is about DDEML, not the `WM_DDE_*` paired-handle machinery in
[4.10](../part-4/4-10.md), and not MCI routing already owned by
[5.3](5-3.md). The source baseline is OpenNT commit
`5c5b979ec08c17d3ca2eb70e8aad62d26515d01c`. Its DDEML dispatch table has
explicit numbered slots with `sizeof(...16)` frame declarations in
`wow32/wddetbl2.h:17-58`. These are individual B-class entry identities; they
must not be collapsed into one “DDE supported” claim, nor counted as a
general COM/OLE completion metric.

| Contract group | Selected table / provider evidence | Required distinction |
| --- | --- | --- |
| Instance and conversation lifecycle | slots 2-10, `wddeml32.c:53-343` | initialize/uninitialize, connect/list/disconnect, and user handle have separate identity and cleanup behavior. |
| Transactions and data handles | slots 11-20, `wddeml32.c:358-761` | transaction, abandon, advise, create/add/get/access/unaccess/free data differ in ownership and cancellation. |
| String handles and callback control | slots 21-27 and 36-37, `wddeml32.c:768-913` | string-handle reference, query, callback enable/name service, comparison and reconnect are separate state operations. |
| Reverse callback registry | `DDEML_CALLBACK_AND_BINDING_REGISTRY::W32DdemlCallBack`; `wddeml32.c:53-124,623-725,918-1029` | native callback binding and Guest callback delivery are a protocol, not just a function pointer. |

Slots explicitly bound to `UNIMPLEMENTEDAPI` in the table remain unsupported
selected-source slots. A modern carrier must return the chosen unavailable
result rather than turn their presence in a header into fabricated success.

## 1. Instance lifetime precedes conversation and callback lifetime

`WD32DdeInitialize` receives its packed Guest frame, invokes native
`DdeInitialize` with `W32DdemlCallBack`, and writes the resulting instance
identity back to Guest-visible storage (`wddeml32.c:53-90`).
`WD32DdeUninitialize` is a separate slot and native call (`97-124`). The
selected source proves that the reverse callback entry is registered while an
instance is initialized. It does not prove that uninitialization drains every
callback already admitted by native DDEML or that an incoming callback cannot
race task retirement.

Connection-list, next-server, disconnect-list, connect, disconnect,
conversation-info, and user-handle requests each have their own fixed frame
and provider route. A modern facade therefore needs opaque instance,
conversation-list, conversation, string, and data tokens scoped to a logical
Guest session. It cannot expose pointer-sized native `HCONV`, `HSZ`, or
`HDDEDATA` values directly through a 16-bit integer.

## 2. Data access and transactions need ownership states

`WD32DdeClientTransaction` converts/copies its selected data input before
calling native `DdeClientTransaction` (`wddeml32.c:358-413`); abandoning a
transaction is a separate request (`419-431`). The data-handle family then
creates, appends, retrieves, accesses, unaccesses, and frees data through
separate table slots and frame types (`473-744`). Access and unaccess are not
synonyms for create/free: an adapter must track whether a Guest view is
currently borrowed, whether its backing data is still owned by the provider,
and whether cancellation or uninitialization may retire it.

The minimal carrier keeps copied, bounded buffers under a data-token record
and maps them to a Guest view only for the documented access interval. It must
not preserve a raw Guest pointer as a native DDE callback payload. Required
negative cases include conversion failure, transaction abandonment before
completion, double/unbalanced access, free while accessed, disconnected peer,
and task exit with a pending transaction.

## 3. Strings and callback enablement are independent registries

The string family provides create, free, query, keep, and compare operations
(`wddeml32.c:768-844,886-896`); callback enablement and name service are
separate slots (`850-880`), as is reconnect (`902-913`). A string token's
reference behavior cannot be inferred from a data-handle token merely because
both use native opaque handles. The token registry needs type admission,
generation, owner instance, reference/borrow state, and one retirement path.

`W32DdemlCallBack` is the native-to-WOW bridge (`918-1029`). Its existence
establishes a reverse-callback protocol and binding registry, not permission
to invoke Guest callbacks on arbitrary native DDEML stacks. Callback delivery
must pass through the same admission/rundown discipline as other Guest
callbacks: task live → record admitted → Guest frame established → completed
or discarded → token retired. Source inspection alone does not prove an
original race or a fully drained shutdown.

## 4. OLE boundary and handoff

The limited clipboard OLE descriptor conversion is already covered in
[4.10](../part-4/4-10.md): it is a lazy `OLETHK32.DLL!ConvertObjDescriptor`
request for two descriptor formats, not an OLE automation implementation.
MCI command routing is in [5.3](5-3.md). Neither proves general COM activation,
registration, marshaling, or a modern host replacement.

Static closure for this chapter records table slots, selected provider calls,
and the reverse-callback identity. It does not close native DDEML availability
on a modern host, all payload semantics, callback thread/scheduling, build
image selection, conversation cancellation, or runtime drain. Implementation
receipts must cover initialize/fail/uninitialize, connection refusal,
transaction completion/abandon, access/unaccess/free ordering, string-token
reuse, callback disable during delivery, and task exit. Cross-cutting callback
and teardown proof belongs to [2.3](../part-2/2-3.md),
[1.3](../part-1/1-3.md), and [6.3](../part-6/6-3.md).
