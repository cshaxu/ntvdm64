# 3.3 — Communications and device sessions

## Boundary

This section owns the selected Win16 COMM/serial session: port token, packed
COMDEB16 allocation, configuration conversion, queued I/O, event/notification,
close, crash/task cleanup, and reopen boundary. It is not a full audit of the
physical serial stack, V86 device internals, or generic message delivery.

| Canonical seam | Unit / class | Static conclusion | Handoff |
| --- | --- | --- | --- |
| `USER16_COMM_PORT_SESSION::PORT_TOKEN_COMDEB16_ASYNC_IO_AND_CLOSE_RUNDOWN` | protocol / D | The 17 selected USER entries share one session/token/COMDEB16/worker lifetime contract. | Posted UI notification: 4.2; generic rundown: 2.3. |
| `KERNEL16_EXPORT::WOWCLOSECOMPORT` | protocol / D | KERNEL close is a one-WORD void bridge with selected TX, DCB, RX-worker, resource, and reopen order. | Device completion policy: 6.3. |
| `USER16_COMM_ENTRY::FLUSHCOMM::ORDINAL_215` | entry / C | Local TX reset and RX state have distinct purge/error branches. | Per-entry carrier validation: 6.3. |
| `USER16_COMM_ENTRY::ENABLECOMMNOTIFICATION::ORDINAL_245` | entry / D | Worker publication and notification have a bounded close/wake/wait route. | HWND/post semantics: 4.2. |

Static closure does not prove a physical device exists, that the selected driver
will cancel reliably, or that a bounded source wait proves worker quiescence.

## The port token and COMDEB16 are Guest-visible state

Guest `IOpenComm` allocates a `COMDEB16` area and `ICloseComm` frees only the
allocation returned by the WOW close route (`wow16/user/wowcomm.c:23-59`). The
selected 17 `MOD_USER` dispatch entries are recorded in `wutbl2.h:255-272,308`.
`wowcomm.h:21-92` fixes the packed shared layout, including the observable
event-word/MSR-shadow relationship; `wucomm.h:112-151` defines selected port
session ownership and worker state.

The modern carrier therefore needs a session-scoped logical port registry,
distinct from host handles, with exclusive-open, generation checking, validated
Guest shared allocation, and exact Guest result translation. A host serial
handle, DCB structure, or worker address must never be written into `COMDEB16`.
DCB conversion is field/bit conversion (`wucomm.c:1490-1658`), not a binary
layout cast between a native structure and a 16-bit Guest structure.

## Close is a protocol, not a single API call

The selected KERNEL close path is one WORD `wPortId` and returns void:
`wowkrn.h:1030-1033`, `wkman.c:3377-3391`, and `nt_com.c:638-738`. Its selected
source order is: validate the logical slot, drain pending TX under its policy,
restore a valid saved DCB, signal/wait for RX worker progress, close
device/synchronization resources, clear adapter state, and allow later reopen.

The required separation is crucial:

- graceful pending-write drain is not cancellation-completion drain;
- a source timeout is not evidence that RX has stopped touching Guest/session
  state;
- void Guest return does not permit silently changing error/result behavior;
- suspend/null/reopen are explicit states, not accidental handle values; and
- resource reuse waits for worker/I/O quiescence or a documented isolation rule.

The selected source does not establish all post-timeout or physical-device
outcomes. The book therefore requires explicit modern admission, cancellation,
completion, and lease policy rather than claiming an original race or a
verified use-after-free.

## Queue, purge, and notification behavior remain observable

`FlushComm` has an intentional C-class nuance: local TX-ring reset occurs
before host purge, even when purge fails; the RX pending byte is retained until
a successful input purge. A subsequent error-query failure has no deterministic
source output proof, so a modern fallback must be recorded as a compatibility
decision rather than asserted as equality. `PURGE_TXABORT` alone does not prove
all pending writes completed.

`EnableCommNotification` publishes worker state and may post the selected
`WOW_WM_COMMNOTIFY` route. The selected close path wakes the worker and waits
only bounded intervals. Thus notification must be stopped or refused before
task/COMDEB16 retirement, and the actual HWND/alias/post ordering belongs to
4.2. Do not infer a late-post guarantee from source bounded waits.

## Validation receipts

6.3 validation must include COM/LPT collision and invalid mode; zero/nonzero
queues; DCB field conversion; partial write/read/unget; event-mask inspection;
notification disable/re-enable; purge success/failure with distinct TX/RX
state; close during pending I/O; RX timeout quarantine; task crash cleanup;
stale token and stale 16:16 address rejection; and reopen after a completed
close. A missing/unsupported device must project an explicit source-compatible
failure, not synthetic success.

## Evidence and limits

| Evidence slice | Establishes | Does not establish |
| --- | --- | --- |
| `wowcomm.c:23-59`; `wutbl2.h:255-272,308`; `wowcomm.h:21-92` | Guest allocation/free, selected dispatch family, packed wire layout | emitted Guest/USER image or every entry's full semantics |
| `wucomm.h`; `wucomm.c:162-2555` selected ranges | selected token/session, worker, I/O, notification, close and crash-cleanup roles | actual driver cancellation, scheduling, all failure paths |
| `wowkrn.h:1030-1033`; `wkman.c:3377-3391`; `nt_com.c:638-738` | bounded KERNEL close bridge and selected host order | post-timeout RX quiescence or physical-device policy |
| `wucomm.c:402-462,1490-1658,1673-1727,1906-2139,2164-2199` | purge/error, DCB conversion, notification and worker source branches | runtime post ordering, deterministic provider failures |
