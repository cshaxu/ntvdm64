# 3.2 — Files, paths, profiles, and configuration

## Boundary

This section owns Win16-visible path/string conversion, current-directory and
short-path effects, bounded profile/configuration presentation, and selected
file/named-pipe routing. It does not own module identity (3.1), DOS DTA search
state (3.5), shell launch (4.9), or generic mapping/callback lifetime (Part 2).

| Canonical seam | Unit / class | Static conclusion | Handoff |
| --- | --- | --- | --- |
| `KERNEL16_THUNK::GETSHORTPATHNAME` | entry / D | A Guest wire has explicit input/output views, capacity, aliasing, and returned count. | Path namespace/runtime: 6.3. |
| `WOW16_LOADER::KNOWNDLL_PATH_QUERY_AND_RELEASE` | protocol / D | Known-DLL path lookup and paired NULL-input release are one bounded policy. | Module/service behavior: 3.1/4.1. |
| `VDMREDIR_EXPORT::VrReadNamedPipe` | entry / D | Named-pipe I/O has per-session metadata, buffer lease, error/count conversion, cancellation, and final-close requirements. | Device/async completion: 3.3/2.3. |
| `VDMREDIR_EXPORT::VrWriteNamedPipe` | entry / D | Write is a separate operation with its own timeout/cancel/byte-count result. | Same lifetime owner as read. |

The source closures are not a claim that arbitrary host paths, the modern
Windows directory, a raw host handle, or a native filesystem/provider result can
be exposed directly to a Win16 program.

## Path data is bounded, encoded Guest state

The selected `GETSHORTPATHNAME` wire is a 16-bit capacity plus input and output
Guest string views. The original wrapper can accept output/input aliasing,
converts a selected C string, invokes the encoding-neutral native route, flushes
`returned-count + 1`, and returns the count in AX. That establishes a bounded
Guest-buffer contract; it does not prove short names exist on a modern volume or
that the selected A/W macro reached a particular image import.

Every path bridge needs an explicit policy for Guest code page, conversion
failure, supplied capacity, exact fit/truncation, NUL termination, current
directory, drive/UNC forms, and a source-shaped error projection. A package or
application root may be selected narrowly where the source contract names it.
It must not silently become a host-wide search policy or redirect unrelated
profile/file paths merely because they share a familiar basename such as
`SYSTEM.INI`.

The known-DLL route provides a second example: initialization queries a named
path policy, Guest loading consumes the rewritten path, and a NULL input performs
the paired release. A successful initialization lookup is not proof that a
later service call, module load, or teardown is equivalent.

## Named-pipe routing retains both metadata and completion

The selected WOW32 layer (`wkfileio.c:71-271,405-565,751-828,1001-1049,
1509-1526,1756-1814`) distinguishes named-pipe from ordinary-file routes and
uses a separately published VDMREDIR binding. The provider evidence in
`vrnmpipe.c:1762-1798,2343-2458,2461-2739,2746-2975,3156-3306` records
per-pipe metadata, queued I/O cancellation, synchronous waiting, and final
close/removal.

The compatibility carrier must keep a per-session handle-to-pipe metadata map;
Guest code never receives a host handle. It retains the Guest buffer lease until
completion is observed—even when cancellation was requested—and preserves
selected `ERROR_MORE_DATA`, zero-byte, timeout, and byte-count conversions.
Task retirement identifies the owner, requests cancellation, drains completion,
then permits buffer or slot reuse. A cancellation request alone is not a safe
reuse point.

The VDMREDIR loader itself is a typed publication boundary. Missing module or
export produces the selected failure latch/result without half-publishing a
function table; a native code pointer must not be cached in Guest or long-lived
WOW state. Redirector service availability remains its own later owner and is
not inferred from readiness.

## Profile and configuration discipline

Configuration is presentation data with original selection, defaults, and
failure behavior. Modern registry/filesystem access may serve as a carrier only
behind one named adapter that defines encoding, key/path scope, capacity,
default, write/rollback, and cleanup semantics. API existence proves neither
legacy profile parsing nor original search/merge order. In particular, profile
compatibility must remain narrow enough that an intentional compatibility alias
does not capture unrelated absolute/relative profile files.

## Validation receipts

6.3 validation must cover current-directory change, input/output aliasing,
zero/exact/truncated capacity, conversion failure, absent short name, drive/UNC
and path-normalization cases; known-DLL query plus paired release; named-pipe
versus ordinary file, missing-provider publication failure, `ERROR_MORE_DATA`,
zero-byte, timeout, cancel, final close, and task exit during pending I/O;
profile defaults/missing sections/keys, narrow aliasing, write failure and
rollback. No one successful `ReadFile` or path query is sufficient.
