# 6.3 — Minimum mirror diff, acceptance, and implementation validation

## Purpose and current truth

This is the promotion gate between a source audit and a claim about an implementation. It owns the evidence required to say that a selected route preserves original semantics with a minimal mirror/image difference. It does not make untouched candidates pass, and it cannot convert a static source conclusion into runtime support.

The current audit ledger explicitly records a static acceptance baseline: 553 registered confirmed OpenNT source seams are statically closed in its limited ledger scope, while implementation validation is zero and no product source, emitted image, binary, archive, trace, dump, or route-execution artifact has been admitted for this audit. That statement is not an overall WOW32 completion percentage, does not redefine the wider frozen source denominator, and does not certify NTVDM64.

## Minimum-diff rule

Preserve upstream-relative source structure and original algorithm ownership. A compatibility change is legitimate only if a named original owner or a necessary, explicitly bounded modern adapter owns it. Each changed mirror expression needs a stable divergence identity, adjacent reason, owner, and register row. Unrelated behavior may not share a divergence identity, and a broad rewrite may not be excused as “modernization.”

“Minimum image diff” is narrower than “few source lines changed.” It requires evidence about the effective selected build and emitted image; a clean source patch does not prove that a different conditional file, generated table, loader binding, namespace attachment, or runtime interception did not change behavior. Conversely, a byte-identical guest image does not prove zero runtime intervention: namespace resolution, a provider, or a broker can still alter the observed route. Source, image, attachment, and runtime evidence must remain separate.

## Required receipt classes

Every promoted route needs four distinct receipts. A green build, one manual success, or `auditctl check` cannot substitute for any of them.

| Receipt | Minimum contents | Does not prove |
| --- | --- | --- |
| Effective-build manifest | exact source commits, configuration, conditional inputs, generated tables, toolchain, selected files and hashes | that the emitted image has the intended route |
| Image-diff manifest | baseline and produced artifact identities, byte/section/export/metadata differences, plus each intentional divergence | semantic correctness or runtime reachability |
| Route acceptance receipt | original seam ID, inputs, expected observable result, carrier/adaptor choice, ownership/rundown outcome, positive and boundary cases | unrelated seam completeness |
| Negative-path receipt | unsupported/provider-missing, malformed/capacity, cancellation, late callback, teardown, and error behavior | that a listed case was executed merely because it exists in a plan |

Receipt provenance must say whether it is source inspection, build output, image inspection, controlled runtime trace, or an unexecuted acceptance obligation. This keeps static audit closure, implementation verification, and experimental evidence from being conflated.

## Route-level acceptance contract

Before promotion, bind one original seam to one implementation route. Record its source commit/path/function and build predicates; guest ABI and record layout; declared input/output and error channels; chosen A/B/C/D/U disposition; named adapter/provider; identity maps; allocation, cancellation, callback, and rundown rules; known loss; and the receiving Part owner. If any functional prerequisite is missing, reopen the earliest owning Part rather than placing an unexplained TODO in tests or a generic adapter.

Acceptance must test both positive and discriminating negative behavior. Examples include buffer-too-small versus not-found, provider loaded versus endpoint missing, close success versus failure-retained state, cancellation request versus completion, callback before versus after task exit, and session-local versus host-global namespace behavior. A successful happy-path call proves only that case. It does not prove layout, ordering, ownership, teardown, or modern equivalence.

For asynchronous work, retain a request lease through final completion/retirement. `CancelIoEx`, module unload, callback deregistration, and process detach are not drain receipts. A broker must additionally prove copied-record bounds, protocol versioning, result/error projection, callback delivery/retirement, and no cross-session leakage. A native32 island needs a process/bitness/load manifest as well as its local behavioral tests.

## Build and image discipline

Original OpenNT evidence must remain pinned by version, absolute source path, function/line span, hash, and build condition. A selected mirror must identify precisely which original source is retained, altered, replaced, or bypassed. When an adapter replaces an inaccessible private provider, record that as a named divergence rather than silently claiming a public API is identical.

Generated tables, `.def` exports, import resolution, conditional compilation, and DLL search/namespace policy are part of effective image identity. A source export declaration proves neither a linked export nor callable ABI. Dynamic lookup proves neither successful resolution nor safe call lifetime. Do not report a missing artifact as evidence that no change occurred.

## Closeout decision table

| State | Permitted statement |
| --- | --- |
| Original/source and modern disposition explained; no product receipts | statically audited/closed at stated scope only |
| Build and image receipts present; no route execution | image/build evidence present; semantic/runtime validation pending |
| Route cases run but teardown/negative gaps remain | partially implementation-validated; list exact unproven dimensions |
| All four receipt classes and stated acceptance obligations satisfy the route | route implementation-validated, not a blanket system claim |

An audit-wide completion claim additionally requires the frozen source and direct-candidate denominator rules in the audit ledger, not merely a collection of closed routes. No report count, queue batch, lexical hit, or number of claims is a completion percentage.

## Closure and handoff

6.3 is statically closed as the finite receipt and promotion contract. The authoritative ledger currently proves only that this contract has been specified; it provides no image/runtime receipt. This book likewise does not inspect or certify the product implementation. When a route is implemented, return missing semantics to its earliest Part 1–5 owner, add the four receipt classes, then reopen/close only that bounded route. This preserves the book’s purpose: a navigable evidence baseline rather than an unearned compatibility claim.
