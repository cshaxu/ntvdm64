# 6.1 — Modern public Win32 APIs

## Purpose and non-claim

This chapter is the carrier-classification layer: it determines whether a documented current public API can participate in a particular original WOW contract. It is not an API catalogue, a name-matching exercise, or a declaration that an API has been implemented. The original source establishes the observable baseline; public documentation establishes only what the candidate carrier promises. A complete connection also needs explicit conversion, ownership, scheduling, failure, teardown, and validation evidence.

The source-of-truth working materials are the audit’s `modern-api-matrix.csv`, `modern-readfile-connection.md`, and `local-memory-modern-connection.md`. They contain scoped evidence and links to official documentation; they are not a product runtime receipt. Functional semantics remain with their Part 1–5 owner, adapter architecture belongs to [6.2](6-2.md), and mirror/image/runtime proof belongs to [6.3](6-3.md).

## Classification vocabulary

Each original operation receives a carrier result, not a blanket support label:

| Class | Meaning | What it does not prove |
| --- | --- | --- |
| **A direct** | the public API may be called with the same relevant contract after ordinary width/encoding adaptation | complete guest integration or runtime acceptance |
| **B candidate** | a documented primitive can carry part of the original behavior behind a named adapter | semantic equivalence or safe forwarding |
| **C non-equivalent** | a tempting direct substitution changes an observed original contract | that no compatible adapter can be built |
| **D absent/directly unavailable** | the required execution or ABI route has no direct modern public carrier | that the feature is impossible by an emulator/broker design |
| **U** | evidence is insufficient to classify a carrier | absence of an implementation path |

This classification is per seam, not per function name, module, or report count. It must preserve the audit’s separate evidence classes, build conditions, static closure, and implementation/runtime verification. A public function’s mere existence cannot change an original entry from U to B without the required contract comparison.

## Required comparison dimensions

Before assigning A or B, record the original caller, result owner, build condition, and all cross-boundary values. Then compare at least these dimensions:

1. **Representation:** 16-bit selector/offset, handle alias, packed record, string encoding, count/length width, alignment, and sign/return channel.
2. **Admission and failure:** invalid/null forms, buffer capacity, `GetLastError`/legacy status projection, partial results, and unsupported-service outcome.
3. **Time:** synchronous return, pending completion, message/interrupt delivery, ordering, reentry, cancellation, and late completion.
4. **Ownership:** who owns input/output buffers, handles, callbacks, registry state, and module/code lifetime before and after return.
5. **Scope:** task, VDM/session, desktop, process, provider, or global state; no host-wide behavior may be smuggled in for a guest-local operation.

If a dimension is unknown, record the unknown and choose B or U rather than silently asserting equivalence. A loss must be named in the family chapter and attached to a concrete adapter decision.

## Worked boundaries from the current matrix

`ReadFile` is a B candidate for ordinary native file transfer, not for the entire Win16 file service. Current documentation provides a native handle, buffer, DWORD count, actual-byte result, synchronous position behavior, overlapped completion rules, and pipe `ERROR_MORE_DATA`. OpenNT’s `wkfileio.c` also resolves DOS-handle identity, distinguishes mapped-cache/native/named-pipe paths, performs compatibility EOF/error work, and notifies guest memory changes. A valid carrier therefore requires handle resolution, bounded guest-buffer mapping, I/O-mode dispatch, result translation, and completion ownership. Passing a guest far pointer or DOS WORD directly to `ReadFile` is not a carrier.

Native `LocalAlloc` is C non-equivalent for the full guest LOCAL* contract. Current documentation says several legacy flags are ignored and the functions use the process default heap; `LocalHandle` accepts a native local allocation pointer, not a guest DS:offset. The original guest system has segment-local arenas, movable handle backlinks, layout consumers, callback ordering, and visible accounting. Native allocation remains useful for private adapter buffers, but must never be published as a guest local handle. This distinction prevents a superficially “minimal” same-name forwarder from creating a large semantic diff.

`BitBlt`, `CallWindowProc`, `UnregisterClass`, and selected clipboard APIs are B candidates only at narrower seams. For example, `CallWindowProc` has native internal-value and ANSI/Unicode behavior that do not establish guest message/ABI equivalence; direct `DestroyWindow` is C non-equivalent for the selected deferred WOW class cleanup because it sends destruction messages. Current clipboard documentation supplies useful ownership and conversion facts but does not reproduce original cache identity, serial publication, or NT-era format policy. Each stays owned by [4.1](../part-4/4-1.md), [4.2](../part-4/4-2.md), or [4.10](../part-4/4-10.md), rather than being “solved” here.

Native x64 execution of a 16-bit NE image is D direct: official Windows documentation states that x64 Windows does not support 16-bit programs. This is not an impossibility claim. It tells the design to retain a guest execution environment/loader boundary and connect modern APIs outside it, rather than attempting a direct host loader substitution.

## Carrier discipline

A proposed carrier must be a named, narrow adapter. Keep the guest export/ordinal, original thunk layout, and original state owner where source supports them; translate only at the host boundary. Never widen guest fields into raw pointer-sized host storage, expose host handles as guest identities, or replace a provider negotiation with host-global setup. If a private OpenNT entry has no current public equivalent, record D or U and provide a targeted facade/broker design only after its observable contract is defined.

For asynchronous APIs, cancellation is not completion and return from a cancel request is not permission to release guest buffers or callback code. For conversion APIs, successful conversion does not prove original encoding, mapping, capacity, or ordering semantics. For lifecycle APIs, module unload is not a session-reader barrier. These are recurring carrier limits, not isolated special cases.

## Closure and acceptance

6.1 is statically closed as a classification method and for the bounded examples recorded above. It is deliberately not a claim that the entire matrix is complete or that any candidate is implemented. Every implemented connection needs: a source receipt for the original seam; official API evidence; an explicit adapter/mirror-delta record; tests for success, capacity, failure, cancellation, teardown, and late events; plus image and runtime receipts where claimed. [6.2](6-2.md) turns a selected class into a design, while [6.3](6-3.md) prevents source reasoning from being mislabeled as product proof.
