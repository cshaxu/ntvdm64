# 5.2 Keyboard, Mouse, and Input Events

## Boundary and current qualification

This module owns host input acquisition, keyboard scan/translation boundary,
mouse events, focus, Ctrl events, queues and delivery toward the DOS-visible
consumer. The retained module record is intentionally not closed: 13 candidate
identities are admitted (ten protocols, two structures, one mechanism), zero
are statically closed, and the full denominator is not frozen. This contradicts
the dashboard's broad 24/24 headline; the unresolved local record takes
precedence for claims about this chapter.

## What has been identified, but not promoted to closure

The source reading has traced client wait/read chains, host keyboard helpers,
action and scan-code conversion, pause/resume/flush/INT15 routes, private PIF
leaves, mouse queue/IRQ entry, and focus/menu coordinates. It also identifies a
possible dynamic `ReadConsoleInputExW`/NOWAIT route. Those findings establish
research leads and ownership, not a chosen modern ABI or a complete event
contract.

Keyboard input must retain exact encoding and make/break/extended-key semantics,
queue capacity and ordering, focus and cancellation behavior, Ctrl delivery,
mouse coordinate/button mapping, and IRQ/EOI relationship. Postulating a modern
event queue, translating all input to Unicode, or treating an input API's
presence as equivalent would invent observable behavior. Late input during
session retirement is a lifecycle question, not merely a read failure.

## Required next closure before implementation

Freeze the finite source-contract denominator, classify each identity, identify
the concrete provider and its failure/cancellation semantics, and reconcile
consumer/IRQ/retirement handoffs with 2.3 and 6.1. Only then can a minimum-diff
adapter be designed. It must keep source-owned queue/consumer semantics and
avoid guest modifications or a new global input manager. Provider/object/ABI
and runtime receipts are Part 8 work.
