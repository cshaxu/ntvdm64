# 3.4 Volumes, Disks, and IOCTL

## Boundary and result

The volume module covers volume labels, space reporting, DASD/absolute-disk
routes and the IOCTL host boundary. It has 21 statically closed local contracts:
13 protocols, five mechanisms and three shared structures. It explicitly does
not audit a disk emulator or assert that raw-device access is available on a
modern host.

## Contract shape

DOS volume behavior is not one modern storage query. Label creation/lookup,
space units, removable-media state, drive classification, absolute I/O and
IOCTL packets have individual flag, error and side-effect rules. A successful
modern storage API cannot authorize a different DOS drive object, broaden
permissions, or turn unavailable raw access into an emulated virtual disk
without a separately admitted provider.

Particular source paths share file handles and paths yet have different error
interpretation. A creation path may preserve earlier external effects even when
a later size check fails. That is why this chapter uses the Part 3 object
authority but does not merge its protocol with 3.2. Packed request/response
carriers remain guest-visible and must not contain native pointers.

## Minimum-diff direction

Keep original IOCTL layout, bytes/units, DOS error and flag behavior, route
selection and cleanup order. Connect only a supported public leaf or a bounded
compatibility service after its capability and privilege semantics are proven.
Do not expose host disks by default, create a second drive namespace, or replace
the original route with a generic storage subsystem.

Path/object ownership is retained from 3.1–3.2; removable-media and VDD routes
go to 6.3; errors/localization to 7.3; provider selection and operational
validation to Part 8.
