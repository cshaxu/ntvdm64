# 3.3 Search, FCB, and Metadata

## Boundary

This module owns find-first/find-next and FCB-facing search behavior together
with attributes, timestamps, rename/delete/lock-adjacent metadata semantics.
Its 22 fixed identities are statically closed (17 protocols and five
mechanisms). The count does not imply that every filesystem function or every
directory tree has been executed.

## Why this cannot be collapsed into file open

Search state, DTA/FCB representation, wildcard/OEM behavior, DOS attribute
projection, timestamp encoding and enumeration termination form a protocol
that differs from ordinary create/open. A host enumeration API can expose a
name but still fail the original contract by changing ordering, wildcard rules,
attribute filtering, end-of-search indication, buffer persistence, or partial
state after error. Rename/delete/lock effects also belong to their exact source
phase; an adapter must not make them transactional because the modern interface
would allow it.

Metadata is a cross-boundary representation problem. Fields and packing are
guest-visible, while the source's native names and internal structures do not
license reuse of modern private layouts. File time/attribute conversion must
keep explicit unit, range, error and code-page policy rather than infer it from
one matching API name.

## Minimum-diff direction and handoff

Preserve source-owned find/FCB state machine, buffer fields, error/EOF-style
termination and side-effect order. Bind a finite modern enumeration/metadata
leaf only through the established DOS object domain. Do not invent a directory
cache, generic lock coordinator, or new wildcard engine.

Drive mapping remains 3.1, normal file objects 3.2, volumes 3.4, codes/errors
7.3, redirector-specific operations 7.1, and modern provider/runtime proof
Part 8.
