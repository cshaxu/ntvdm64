# 3.2 File Handles and Read/Write

## Boundary and result

This module follows create/open/read/write/seek/close/commit, DOS JFT/SFT
representation, native file-object association, named-pipe paths, inheritance,
and DOS error/flag return. Its local denominator is ten identities and all ten
are statically closed. It does not certify compiled ABI, native-object validity,
or actual I/O behavior.

## Details that are semantically significant

The Guest JFT is byte-indexed and an SFT has packed, fixed-width fields. A DOS
slot, SFT reference count, 32-bit stored native handle value, and the actual
native object are separate identities. Allocation, association, retrieve and
release are separate actions; release of a slot does not automatically close
the underlying native handle. A native 64-bit pointer must never be put in a
Guest field merely because a nearby handle is 32 bits.

Read and write preserve route-specific behavior. Named pipes are tested before
ordinary positioning; a pipe zero-length write is not necessarily the same as
a regular file's `SetEndOfFile` path. Broken pipe, disk full, short transfer,
commit, seek-origin, sentinel values, carry flag, and AX output each have
source-defined effects. `FlushFileBuffers` is attempted while DOS commit can
still report success; its failure cannot simply become CF=1, nor may the call
be deleted as an optimization. CDFS fallback, font-removal retry, and inherited
handle settings are likewise individual protocols, not generic CreateFile
defaults.

## Minimum-diff direction

Retain DEM/OEM/VDD source shape, packed structures, native-handle numerical
domain, flag/error mapping, partial effects and original cleanup sequence.
Use a bounded provider only to bridge a true host incompatibility. Do not add a
universal handle-token service, a read-full/write-full loop, automatic rollback,
or a per-DOS-handle seek table.

Path/name policy comes from 3.1; FCB/metadata from 3.3; volumes from 3.4;
Guest mapping from 4.1; pipe/redirector behavior from 7.1; provider/object/ABI
and lifecycle validation from Part 8.
