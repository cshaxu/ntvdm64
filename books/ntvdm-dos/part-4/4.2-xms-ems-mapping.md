# 4.2 XMS, EMS, and Mappings

## Boundary and result

This module covers host-facing XMS/EMS allocation, moves, map/remap and release
semantics, not CPU execution. Its frozen denominator contains 27 contracts:
18 protocols, three mechanisms, four shared structures and two variants. All
27 are statically closed, while implementation validation remains zero.

## Contract implications

XMS/EMS operations are lifetime protocols: allocation identity, handle/value
width, move source and destination, mapping visibility, partial failure,
unmap/release ordering and asynchronous exposure must be retained separately.
A successful modern allocation is not a substitute if it changes the original
move validation, aliasing, map count or release behavior. Architecture-specific
sources prevent same-named entry points from being merged mechanically.

The audit identifies contracts rather than claiming every historical allocator
detail is desirable. A host-only safety correction, if later needed, must name
the original defined normal trajectory, exact unavailable boundary, bounded
diff and negative/lifecycle validation. It cannot be justified as a casual
rewrite or by modifying guest code.

## Minimum-diff direction

Preserve original managers and consumer-facing structures. Use a bounded
session mapping/allocator seam only where required; retain handle semantics and
release sequencing instead of creating a replacement extended-memory service.
Address mapping is anchored in 4.1, DPMI consumers in 4.3, and build/provider/
runtime evidence in Part 8.
