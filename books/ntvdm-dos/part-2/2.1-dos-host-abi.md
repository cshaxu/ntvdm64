# 2.1 DOS/Host Call ABI

## Boundary and closure

This module owns the DOS-to-host call shape: BOP/DEM dispatch, service-number
identity, registers, segment-offset carriers, return flags, and selected
declaration/profile evidence. It excludes the meaning of every individual DOS
service, CPU/V86 execution, and a guessed native calling convention. Its fixed
local denominator is eight identities, all statically closed; build/object ABI
and runtime validation remain unperformed.

## What must not be normalized away

The original source has tables and C/assembly carriers whose numeric values,
register ordering, and success/error flags are protocol, not implementation
detail. A BOP number plus a similarly named C function does not prove that the
stack, macro profile, argument width, or return state matches. Segment:offset
input is a guest-domain address; it cannot be collapsed into an arbitrary native
pointer, and a 32-bit field cannot be upgraded silently into native-width
identity.

Declarations also distinguish data from callable code and explicit calling
conventions from unspecified historical declarations. Preprocessor profile
changes can select a different address-mapping macro or a no-op flush/free
form. Thus a successful compile under an assumed `i386` environment would not
alone prove the historical ABI.

## Minimum-diff direction

Keep BOP numbers, table positions, register and flag rules, field widths,
segment semantics, and source-level call shape. Put unavoidable pointer/object
translation at one named bounded seam and make its lifetime explicit. Do not
install a general token scheme, reinterpret all DWORDs as pointers, or rewrite
the dispatcher because a modern API is wider.

Service-specific behavior transfers to 2.2/2.3 and Parts 3–7. Mapping and
extended-memory carriers transfer to Part 4. The selected compiler profile,
objects, decoration/calling convention, object ownership and runtime witness
are Part 8 work.
