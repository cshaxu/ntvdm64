# 8.2 Minimum Diff and Implementation Validation

## What this final module owns

8.2 turns a static audit conclusion into an implementation-admission and
validation plan. It owns source/image/runtime evidence separation, exact-diff
review, provider/object/ABI/lifetime/fault acceptance, and end-to-end witnesses.
It does not authorize product changes merely because a source module closed.

## Minimum-diff acceptance baseline

For each proposed connection, retain the original source owner and state why a
public modern route cannot express the precise contract. Name the exact
unavailable dependency, the smallest facade or binding, interface/field widths,
conversion, ownership, normal and negative behavior, cancellation, cleanup and
handoffs. A product diff must neither modify guest binaries nor reconstruct a
new DOS/CPU/CSR/handle/path subsystem behind an original-looking name.

Validate in layers: selected source and build identity; generated/import/DEF and
actual image facts; compiled calling convention/layout/width; provider/object
ownership; normal path; source-matched error/partial-effect path; teardown/
late-callback/concurrency path; then real DOS-program observation. Preserve
hashes and configuration conditions. A passing unit API probe is insufficient
if it bypasses the original caller or cannot show the same object and lifetime.

## Current status

The audit dashboard's implementation-validation denominator is 0/66. This is
the useful honest frontier: static module closure has created a finite list of
routes to prove, not an implementation completion claim. The unresolved 5.2
input denominator must be reconciled before any assertion that all static source
modules are complete. No overall percentage is published because the global
candidate denominator is explicitly unfrozen.

## A practical review checklist

1. Verify exact source revision/path/hash and the chapter's fixed scope.
2. Preserve original bodies and guest media; state every non-original line.
3. Prove selected build/profile/object/export facts rather than infer them.
4. Demonstrate representation, error, ownership, cancellation and late-work
   behavior at the real caller/provider boundary.
5. Record normal, negative, cleanup and restart/reuse outcomes, plus explicit
   remaining limitation or handoff.
