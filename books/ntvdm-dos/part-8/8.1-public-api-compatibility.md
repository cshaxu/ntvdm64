# 8.1 Public APIs and Required Compatibility Services

## Purpose

Part 8.1 is the synthesis boundary. It does not search for a superficially
modern equivalent for every historical name. Instead, for each closed source
contract it must decide whether a public API preserves the named local semantics,
whether a conversion/adaptation is sufficient, or whether a finite compatibility
provider is required. No public direct interface does not mean the behavior is
impossible; it means the provider boundary must be explicit.

## Provider-selection rules

Select by observable contract: data representation and width, ordering,
success/failure/LastError mapping, partial effects, ownership, aliasing,
thread/process identity, cancellation and late completion. Modern APIs are
evidence for a leaf operation, not proof of the surrounding OpenNT service.
Never use their names to infer private layouts, build exports, or lifetime
guarantees.

The preferred ladder is: retain a direct qualified public leaf; preserve the
source call shape through a smallest facade; admit a specifically bounded
compatibility provider; otherwise retain an explicit unsupported/failure
disposition. A provider may not become a generic subsystem for paths, handles,
input, devices, or identity. Guest changes, private CSR/Win32k emulation and
new global token registries are outside the route.

## Required output per route

Record the original owner and source range, exact selected provider, conversion,
object/handle/pointer domain, error and cancellation behavior, load/build
requirements, rejected alternatives, and Part 8.2 acceptance evidence. A route
does not become valid solely by compiling or by an API test that bypasses the
original caller.
